# 协作与文档：踩坑与经验

> 本页是 docs 提炼的经验记录，**非现行规则**；与 `AGENTS.md`、`docs/development-conventions.md` 或代码冲突时，以现行文件与代码为准。归档来源已标「历史」，旧数值/旧口径不得当作现状引用。

## 结论先行

- **交接不是写张卡就完**：接手人真正需要的是「当前基线 + 未推送清单 + 别人在改什么 + 下一步挂账」四件套；缺一项就会重复开工或误删他人在途成果。
- **状态词是会骗人的**：文档里的「进行中 / 待裁决 / 待实施 / 已确认」必须逐份对代码与验收状态核实；一次文档体检曾查出 33 份早期稿与代码矛盾、27 份「进行中」里 22 份其实只是等验收。
- **旧记录默认禁读是硬纪律**，而且要落到工具：索引生成器、默认搜索、封存流程都必须在读取前排除 `archive`，否则规则只约束人、不约束自动化。
- **清理不等于办结**：把旧内容搬进归档区，不表示相关事项已被船长关闭；未决与待复核摘要必须留在现行文档（roadmap / 跟进页）。
- **合并不是「并集」两个字**：两侧同名条目可能内容不同，自动合并还会把两条粘成一行；每次合并后要按父提交逐字比对、扫「一行里出现 ≥2 个条目开头」。
- **生成件永远重生成，不手改**：`docs/INDEX.md` 冲突就重跑 `docs:index`；CSS/布局类生成件漏跑生成器会表现为「改了看不见」。
- **写文件先定编码**：`write` 工具产 LF，本仓约定 CRLF 无 BOM；PowerShell 的 `Set-Content` / `Out-File` 会毁中文，批量改文件必须写脚本并当场校验字节数与内容。
- **审查与盘点要能收口**：范围、只读边界、并发写风险、子代理是否真交付，都要在报告里如实登记；不冒认未交付的产出，也不把读数当成观感验收。

## 一、交接与多工作树：先对表再动手

### 坑 1.1 交接卡里的基线与「未推送数」互相矛盾

- **现象**：接手人按交接卡上的 commit 与「本地未推 N 条」开工，发现与实际不符；同一时段的四份交接件分别写 120 / 123 / 126 / 172 条，无法判断哪份可信。
- **根因**：交接卡是手写的时点快照，工作树还在继续提交，没人负责刷新；「未推送数」本来就应该现算而不是抄。
- **解法 / 规避**：交接卡只写「怎么现算」——`git log --oneline -1`、`git status --short`、`git rev-list --count origin/main..main`；基线一律以现场命令输出为准。开工与合入前各对一次表，主树 `git status --short` 不为空就停手报告，不硬 merge、不替对方清理（附属树完成改动后若主树有他人在途修改，冲突先在任务树解）。
- **复发检查点**：接手第一件事跑三树对表；发现卡片数字与现场不符时，以现场为准并顺手在卡片标注「已过期」。
- **来源**：`docs/archive/retired-docs-20261029/doc-health-20260911.md:147-154`（历史：四份交接件未推数矛盾）；`docs/design/archive/handoff-20260927-main.md:12-15`（三树对表与闸门清单）。

### 坑 1.3 替别人归档 / 动他人在途工作文档

- **现象**：收尾归档时把整个 `docs/design/` 当作自己的批次清理，删掉或改写了别人正在写的文档；或者主树有在途清理时仍去碰重叠区域。
- **根因**：收尾动作以「目录」为单位而不是以「自己的交付清单」为单位；缺少「谁在改什么」的显式清单。
- **解法 / 规避**：交接卡列出「别人在改什么，别替他们归档/删除」；跨树同步遇到主树在途清理时，停止触碰重叠区域，等同步完成再继续。
- **复发检查点**：归档前先列本批文件清单与归属；发现无法判断归属的文件一律不动并报告。
- **来源**：`docs/design/archive/handoff-20260927-main.md:61-67`（别人在改什么）；`docs/design/guoqing-audit-closeout-20261029.md:42`（主树在途文档清理时停止触碰重叠区域）。

### 坑 1.4 交接件用历史叫法命名，派活派错人

- **现象**：文件名写着 `handover-d3-20260910.md`，但三号工作树实际叫 `…-verify`（分支 `verify`），新接手人按名字找 `d3` 找不到；另有交接件把「d3」当成现行工作树称谓。
- **根因**：旧命名沿用，交接件之间互相抄，没有以现行工作树表为准。
- **解法 / 规避**：交接件正文里以「工作树路径 + 分支」为准，历史叫法要显式标注「历史叫法」；新写交接件不复制旧称谓。
- **复发检查点**：交接卡头部检查工作树路径/分支是否与 `AGENTS.md` §4 一致；文件名含 `d1/d2/d3` 时补一句映射说明。
- **来源**：`docs/archive/retired-docs-20261029/doc-health-20260911.md:111-117`（历史：d3 是历史叫法、易派错人）。

## 二、工作文档状态与验收闭环

### 坑 2.1 状态词停留在开工时，文档与代码长期漂移

- **现象**：文档体检时发现 33 份早期稿的机制/数值与现行代码矛盾（超时判负、无人机损毁、池量、装备件数、蓝图耗时等），部分旧行还标着「定稿」；另有 27 份「进行中」工作文档里 22 份其实已经落码、只在等船长验收。
- **根因**：状态靠人工记忆更新，没有「验收 + 合入后归档」的固定动作；文档头部的状态词一旦写下就没人回头改。
- **解法 / 规避**：文档体检必须以「文件:行 / grep 命中 / 代码现值」为据，禁止凭感觉判旧；修高危项 + 给其余稿挂「立稿留档」横幅；工作文档在验收后按归档三步处理，不留「进行中」假象。
- **复发检查点**：每次交接/盘点扫一遍 `docs/design/*.md` 头部状态；「已确认」必须区分「已确认未实现」与「已确认并实现」。
- **来源**：`docs/archive/retired-docs-20261029/doc-health-20260911.md:4-7`（只读审计方法）、`:52-56`（33 份漂移与判据）、`:111-125`（状态标注候选）；`docs/design/inventory-20260927.md:43-49`（27 份进行中文档里 22 份等验收）。

### 坑 2.2 待裁决清单堆积，口头拍板没有落档

- **现象**：盘点稿一次列出 Q1–Q13 件待船长拍板事项，横跨玩法、数值、Steam、手册文案；另有旧「待船长裁决清单」在不同批次反复追加，收尾时还要再补一节「裁决结果」。
- **根因**：讨论结论停留在会话里，没有当场写进清单并标注「谁批的、批了哪条」；新问题不断加进同一份清单，旧条目又不关闭。
- **解法 / 规避**：盘点按「① 待拍板 ② 可立即做 ③ 等验收 ④ 已并入/留档」四分类；每条给出处与建议方案；船长拍板后在原清单记「裁决结果 + 日期 + 落地状态」，能关的当场关。
- **复发检查点**：接手时先读 roadmap 活面与最新盘点稿；发现「口头已同意但文档无记录」的条目，先补记录再执行。
- **来源**：`docs/design/inventory-20260927.md:13-31`（Q1–Q13 四分类）；`docs/review/pending-decisions-20260910.md:9`（裁决结果节）、`:26`（总览）。

### 坑 2.3 「等验收」积压，归档被阻塞

- **现象**：大量已落码并合入的批次卡在「船长看一眼」；工作文档不能归档，roadmap 活面越来越长，下一次盘点还要重新解释每份文档做了什么。
- **根因**：验收与归档没有打包成清单，船长需要逐份翻工作文档；执行者也没有主动把「看哪里、怎么算通过」整理出来。
- **解法 / 规避**：按线整理「逐份验收清单」（每份一行：做了什么 → 在游戏里看哪里 → 通过就归档），一次走完、一次性归档；盘点稿本身也要请船长裁定「留/删/并入 roadmap」。
- **复发检查点**：每轮收尾统计「等验收」数量；超过约定批次就主动提出验收清单，而不是继续堆新功能。
- **来源**：`docs/design/inventory-20260927.md:43-49`（等验收清单）、`:62-66`（盘点稿自身请裁三件）。

## 三、旧记录与归档：禁读、冻结与「清理≠办结」

### 坑 3.1 旧记录被当成现行依据

- **现象**：旧方案、旧数值、旧权限散落在 `docs/archive/` 与 `docs/design/archive/`，日常检索时被当作参考，甚至被用来「证明」当前该怎么做。
- **根因**：归档只意味着「不再现行」，文件本身仍在仓库里且可被 grep；没有禁读入口与工具级排除，历史内容就会混进当前依据。
- **解法 / 规避**：归档区入口写明「没有船长明确查阅要求，平时禁止阅读、检索、批量扫描或自动载入，禁止用 Git 历史绕过」；获准后只查指定主题或文件，结束恢复禁读；历史结论仍要核实现行实现，不自动取得实施许可。
- **复发检查点**：默认搜索/索引必须显式排除所有 `archive`；发现自己在无授权情况下打开归档页，立即停止并报告。
- **来源**：`docs/archive/README.md:3-10`；`docs/archive/retired-docs-20261029/README.md:3-7`；`docs/design/history-doc-cleanup-20261029.md:12-13`。

### 坑 3.2 把「已清理」误当成「已办结」

- **现象**：旧内容被搬走或从常用文档里删掉后，相关未决事项被默认关闭；下次盘点时发现没人记得它其实还没做完。
- **根因**：清理动作处理的是「文档位置」，不是「事项状态」；两件事被同一个提交完成，看起来就像办结。
- **解法 / 规避**：清理前明确「当前有效定义与未决摘要留在现行文档，过程、旧读数及已办结流水才进归档区」；未核实办结的事项保留为待复核，不擅自关闭。
- **复发检查点**：清理提交的说明里必须写「哪些事项仍开着、留在哪份现行文档」；盘点时对照现行文档里的未决摘要，而不是看归档目录是否干净。
- **来源**：`docs/archive/README.md:16`；`docs/design/history-doc-cleanup-20261029.md:6`、`:30-35`。

### 坑 3.3 自动化工具有意无意绕过了禁读纪律

- **现象**：索引生成器为了统计引用去读取历史正文；默认文档搜索仍会命中 `archive` 下的旧文件；旧封存流程还能把旧格式写回常用文档。
- **根因**：禁读规则先写在人读的入口说明里，工具实现没有同步；「规则只约束人」的漏洞在自动化里最危险。
- **解法 / 规避**：索引遍历前跳过 `archive`；默认搜索用 `docs/.rgignore` 与显式排除；退役会把旧格式写回常用文档的封存入口（旧 `docs:seal` 滚动封存），原工具代码留档但调用直接失败。
- **复发检查点**：改文档工具后跑一次「无授权路径是否仍会读 archive」的自检；索引 stats 无写入、生成幂等、过期检查都要有用例。
- **来源**：`docs/design/history-doc-cleanup-20261029.md:19`、`:33-34`、`:39-42`；`docs/design/guoqing-audit-closeout-20261029.md:42`（索引生成器因读取历史正文未运行，改用遍历前跳过 archive 的新版）。

### 坑 3.4 归档搬迁制造悬空引用，删件抹掉决策记录

- **现象**：把设计稿搬进 `docs/design/archive/` 后，roadmap 与其他文档里的相对引用悬空；有人主张「零删件、能删就删」，但被删的文件里记录着当时谁批的、为什么否。
- **根因**：搬动前没有统计引用面（当时 `docs/design/*.md` 全仓 282 处引用，其中 112 处在 roadmap），删除 vs 归档的边界也没写清。
- **解法 / 规避**：先查引用再搬；归档候选要列理由与引用数，等船长点头再动；结论已吸收、引用为零的早期稿才考虑删；「搬运不等于事项解决，也不授权重新执行旧方案」。
- **复发检查点**：搬迁后用链接检查/索引生成验证无悬空引用；删除件前确认其结论已在现行文档留痕。
- **来源**：`docs/archive/retired-docs-20261029/doc-health-20260911.md:95-109`（历史：282 处引用、零删件判定）；`docs/archive/retired-docs-20261029/README.md:7`。

## 四、合并、生成件与编码

### 坑 4.1 「并集解冲突」把两条目粘成一行

- **现象**：合并 `main` 时用「并集」策略解 roadmap 冲突，自动合并把一号与三号两条批次记录粘成一行（2729 字符，行内出现 2 个 `- 2026-`）；`git status` 干净、四连全绿、肉眼扫前几行也看不出。
- **根因**：`git` 按行合并，两侧相邻条目被当成同一行的不同片段拼接；「保住两侧每一行」不等于「保住一行一条」。
- **解法 / 规避**：解冲突后做三项检查：① 与两侧父提交比「父提交有的行是否还在」；② 扫「一行里出现 ≥2 个条目开头」与异常超长行；③ 拆回时以行内第二个条目开头为接缝切开，两条各自与来源提交逐字比对，再做 BOM/行尾/乱码/往返解码自检。
- **复发检查点**：每次文档合并后跑上述三项；不要以「CI 绿」代替行级核对。
- **来源**：`docs/design/archive/wrapup-20260914-verify.md:39-43`、`:70-71`、`:118-122`。

### 坑 4.2 roadmap 追加方向写反，自己的条目被当成最旧封存

- **现象**：按「追加到末尾」写 roadmap 最近批次，结果本轮 5 条被 `docs:seal` 当成最旧记录封存掉；已 `git checkout` 还原并改成前插后重跑。
- **根因**：roadmap 的「最近批次」是新的在最前，`docs:seal` 的窗口 = 文件里前 20 条，多出来的从末尾封存；写作者凭直觉追加。
- **解法 / 规避**：新条目一律插在「## 最近批次」说明行之后（最新在最上面）；跑 `docs:seal` 前先 `--dry-run` 看「不保留的段头」，窗口区一行都不许丢由工具守恒校验兜底。
- **复发检查点**：每次改 roadmap 后检查新条目位置与 `docs:seal --dry-run` 输出；封存后核对被搬条目确实是最旧的。
- **来源**：`docs/design/archive/handoff-20260927-main.md:76-79`。

### 坑 4.3 手改生成件，或改了源文件却漏跑生成器

- **现象**：`docs/INDEX.md` 冲突时手工编辑；改 CSS 后页面「看不见变化」，因为渲染层用的是 `ui/layout-css/styles-{modern,classic}.css` 生成件。
- **根因**：生成件的头注/说明没人读；冲突时的第一反应是修文本而不是重跑生成器。
- **解法 / 规避**：`docs/INDEX.md` 冲突的固定解法是 `npm run docs:index` 重生成再 `git add`；改 CSS 必跑 `npm run ui:layout-css`（并跑 `:check`）；索引/布局生成件不手改。
- **复发检查点**：提交前看 diff 是否碰到生成件头注；CI/钩子里有生成器检查的，先本地跑一遍。
- **来源**：`docs/design/archive/handoff-20260927-main.md:80-81`。

### 坑 4.4 编码事故：LF/CRLF、PowerShell 毁中文、0 字节覆盖

- **现象**：`write` 工具新建文件默认 LF，而本仓工作树约定 CRLF 无 BOM；`Set-Content` / `Out-File` 直出中文乱码；PowerShell 内联 `.Replace()` 传三参（.NET 无该重载）把 `encounters.ts` 写成过 0 字节。
- **根因**：工具默认值与仓库约定不一致；PowerShell 的文本管线不是 UTF-8 安全通道，内联脚本又缺少写后校验。
- **解法 / 规避**：中文/批量写入用 .NET `WriteAllText` + `UTF8Encoding($false)` 或 Node `fs.writeFileSync(..., 'utf8')`；写完自检 BOM=False、LF-only 行数=0、字节数/内容符合预期；批量改文件一律脚本化并当场校验，不裸调内联替换。
- **复发检查点**：`git diff --check`、UTF-8/替换字符/冲突标记扫描、与基线逐字比对；发现 0 字节文件立即从 HEAD 还原重做。
- **来源**：`docs/design/archive/handoff-20260927-main.md:82-88`；`docs/design/archive/wrapup-20260914-verify.md:104-109`；`docs/archive/retired-docs-20261029/agent-rules-audit-20261027.md:39`。

## 五、文档体检与规则维护

### 坑 5.1 凭感觉判旧，权威文档自身也有新旧口径并存

- **现象**：文档体检若凭印象判断「这份过时了」，会误伤仍有效的决策记录；反过来，`docs/glossary.md` 的 B3 节被发现 4 组新旧口径并存，其中 3 组旧行还标着「定稿」。
- **根因**：没有把「与代码现值矛盾」作为唯一判据；权威文档更新时只加新行、不标旧行作废。
- **解法 / 规避**：逐条以「文件:行 / grep 命中 / 代码现值」为据，禁止凭感觉判旧；修高危项（会被后人照抄进代码的）并给其余挂「立稿留档」横幅；权威文档更新时旧行标「作废」并指向新行。
- **复发检查点**：体检报告必须给可核依据；词典/架构类文档改完后 grep 是否还有未标作废的旧口径。
- **来源**：`docs/archive/retired-docs-20261029/doc-health-20260911.md:4-7`、`:10-20`、`:52-56`。

### 坑 5.2 过期规则不清，或把「未被代码自动强制」当删除理由

- **现象**：仓库入口里积累了一批与现场不符的旧规矩（每轮跑全量 core、新文案当批中英双语、视觉物件一律 SVG、pwsh 就是 5.1、测试档一律真档、arch-guard 自动发现未登记实现、后台任务旧接口等）；反过来，有人以「代码没自动拦」为理由想删掉确认、隔离、发布审核、真档保护等规则。
- **根因**：规则与代码现状脱节后没人复核；「自动强制」与「人的责任」被混为一谈。
- **解法 / 规避**：逐条核对现场依据后删除失效要求，保留的每条补一句「为什么」；明确「不把未被代码自动强制当成删除理由」——人类审批、数据保护、发布闸门仍有效。
- **复发检查点**：规则文档改动后跑 typecheck / content:check / arch:guard 与 `git diff --check`；统计「每条是否都有原因」，遗漏数应为 0。
- **来源**：`docs/archive/retired-docs-20261029/agent-rules-audit-20261027.md:10-22`、`:24-29`、`:33-39`。

### 坑 5.3 同一事实在稿、代码注释、玩家文案三处各写一个值

- **现象**：市场采样周期在稿子、`market.ts` 注释、玩家可见的 `MarketPage.tsx` 三处都写「30 分钟」，只有 `balance.ts` 的 `tickMs = 60s` 不同；另有「点防 PD 六参数」被四处引用为「二号设计稿 §八」，但 `docs/design/` 检索不到该定稿件。
- **根因**：数值/口径更新时没有「单点来源」意识，注释与文案各自留了一份副本；引用链没有核实到源文档。
- **解法 / 规避**：发现三处不一致先定案「改稿、改代码还是改文案」，涉玩家可见文案必须请船长定；引用他稿前先定位源文件，找不到就登记为存疑并说明，不硬造依据。
- **复发检查点**：体检清单里单列「同一事实多副本」项；改数值后 grep 稿/注释/文案三处是否同步。
- **来源**：`docs/archive/retired-docs-20261029/doc-health-20260911.md:147-154`（历史：30 分钟采样与 PD 六参数源文档缺失）。

## 六、审查、盘点与协作纪律

### 坑 6.1 审查范围蔓延与并发写冲突

- **现象**：全库审查报告给出重构清单（重复效果代码、死代码约 420 处、core 36 处运行期模块环、工业页两外壳双写），但直接大搬迁会撞上二号/三号正在写的 combat/wormhole 区；耦合体检也因「三号正在重构同域规则与护栏」而只留数据与建议、不动手。
- **根因**：审查结论是全局最优顺序，执行却受并发写限制；把「报告里的清单」直接当成「可以立刻做的批次」。
- **解法 / 规避**：审查全程只读、探针用完即删；重构按「改到哪个文件就顺手拆该部分」小步合入，不做专项大搬迁；与同域在途工作重叠时挂起，避免两套口径/两套工具并存；存档兼容与 UI 观感红线先列进风险清单。
- **复发检查点**：动手前确认目标文件没有他人在途修改；报告里写明「可立即做 / 需排期 / 等他人先落地」三档。
- **来源**：`docs/design/code-review-20261002.md:107-123`、`:127-128`；`docs/design/coupling-audit-20260927.md:76-81`、`:83-87`。

### 坑 6.2 子代理没有交付，却被写成「已完成」

- **现象**：代码审查按技能流程起了 Standards / Spec 两个并行子代理，两代理连跑 4 轮无交付；若直接写「子代理已完成审查」，报告就是假的。
- **根因**：把「派工」当成「完成」，没有核对子代理的产出；交接与汇报里也容易把编排过程写成结果。
- **解法 / 规避**：如实登记「子代理未交付、已中断，两轴由主代理按同一简报直接完成」；子代理产物一律由主代理复核结构与来源后才算数。
- **复发检查点**：汇报前对照任务清单确认每个子任务的交付物在本机可打开、可核对；没有就写「未交付」，不冒认。
- **来源**：`docs/design/code-review-20261002.md:17-29`。

### 坑 6.3 临时探针不清理，或把读数当观感验收

- **现象**：一次性探针留在 `tools/` 变成死工具；UI 类改动拿几何读数/截图当「改好了」，忽略观感验收权在船长；自动化工具误判时，有人改业务判据去迎合工具。
- **根因**：收尾清单没有「探针/临时件」项；把客观读数与主观观感混为一谈；工具与业务判据的边界不清。
- **解法 / 规避**：一次性探针用完即删、有复用价值的转正式入库并写用途；观感由船长在本地过目，执行者只交读数与几何；工具误判时修正取证顺序，不改业务判据迎合工具。
- **复发检查点**：收尾 grep `tools/_*` 与临时产物；UI 汇报里明确「这是读数，不是观感结论」。
- **来源**：`docs/design/archive/wrapup-20260914-verify.md:100-101`、`:117`；`docs/design/guoqing-audit-closeout-20261029.md:32`、`:34`；`docs/design/code-review-20261002.md:127-128`。

### 坑 6.4 汇报口径不一致，船长无法判断交付是否完整

- **现象**：汇报只写「改好了」，没有列修改文件、行为变化、验证结果与已知取舍；跨域/未决事项混在小修里带过；桌面结果被冒称移动端实机验收。
- **根因**：没有固定汇报模板；执行者默认「对方知道自己做了什么」；验证范围与结论范围不一致。
- **解法 / 规避**：每次汇报第一行写「报告老大喵」（船长指定），结论先行，列修改文件、行为变化、验证结果与已知取舍；小修可三行内，涉及验收/发布/跨域/未决时按完整口径；验证范围写清（桌面 ≠ 移动端实机）。
- **复发检查点**：提交/汇报前对照四要素自查；跨域与未决事项单独成段，不藏在「其它」里。
- **来源**：`docs/design/archive/handoff-20260927-main.md:20`、`:108-115`；`docs/design/guoqing-audit-closeout-20261029.md:34`。

## 校验回归清单

- 交接前：三树 `git log --oneline -1` / `git status --short` 对表；`git rev-list --count origin/main..main` 现算未推数，不抄旧卡。
- 合并文档后：与两侧父提交比「父提交有的行是否还在」；扫「一行里出现 ≥2 个 `- 2026-`」与异常超长行；拆行后逐字比对。
- 生成件与编码：`npm run docs:index`（冲突时重生成，不手改）；改 CSS 后 `npm run ui:layout-css` + `:check`；`git diff --check`；UTF-8 有效、无 BOM、CRLF、无替换字符与冲突标记；批量写文件后校验字节数与非空。
- 禁读与归档：默认搜索/索引排除 `archive`；工具改动后验证「无授权路径不读历史正文」、索引 stats 无写入、生成幂等；manifest 登记原路径/字节数/SHA256 并与基线逐份核对；搬迁后检查无悬空引用；未决摘要留在现行文档。
- 状态与规则：工作文档头部状态与代码/验收状态一致；「已确认」区分是否已实现；「等验收」有逐份清单；每条规则含「原因」；「未被代码自动强制」不作为删除理由；规则改动后跑 typecheck / content:check / arch:guard。
- 收尾与汇报：`tools/_*` 与临时产物清零，有复用价值的探针转正式入库并写用途/用法；第一行「报告老大喵」，列修改文件、行为变化、验证结果、已知取舍，读数与观感分开写。
