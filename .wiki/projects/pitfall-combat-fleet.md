# 战斗与舰队：踩坑与经验

> 本页是从 `docs/` 提炼的经验记录，不是现行规则。与 `AGENTS.md`、`docs/` 现行正文或代码冲突时一律以它们为准；标「历史档案」的条目只作复盘，不得当作现行口径。具体数值不在此页复述，需用时回查对应文档与代码。

## 结论先行

1. **收场判定比开火更容易漏**：超时、撤退、沉船、全灭这类"结束态"分散在远征 / 虫洞 / 遭遇三个战斗宿主里，任何一处各写一份判据，就必然有一处漏。
2. **"能装"不等于"能存"**：槽位、格数、容量只要有一处没走同一个换算单点，装备就会"重启就丢"或"套用方案静默少装"。
3. **纸面火力不是难度**：名义 DPS、威胁值这类纸面列与实际建档火力之间没有守卫；难度守恒必须按**实收**判定，不按纸面。
4. **射程一动，一切跟着动**：射程带同时决定命中折减、期望交距、开战距离、冲锋触发门槛；"某机制没效果"常常是射程变了导致它压根不触发。
5. **战斗必须是纯模拟**：战斗内写玩家库存（复活、补货、扣料）会引出预算、超补、双扣一连串问题；正确做法是开战拍快照、战后一处结算。
6. **仪表读数不等于体感结论**：Node 引擎毫秒数、单场胜率、无头浏览器坐标都只证明各自那一层，不能宣称"窗口不卡顿""难度没变""演出没问题"。
7. **报障先复现、再收口判据**：本域历史修复的共同套路是"把散落的判据收成一个函数 ＋ 补一条真能抓住 bug 的用例 ＋ 把旧口径改回去看它变红"；接线漏项则靠闸门兜（`typecheck`、`content:check`、存档白名单常能再捞四类漏）。

## 1. 战斗判定与收场出口

### 1.1 超时按剩余血量比判胜 ⇒ "平局算我方胜"

**现象**：一架无技能护卫舰带远程导弹，对多档威胁悬赏卡打满 10 分钟、我方满血、敌人未死，却全部记为 100% 胜率并照发赏金——零风险"白刷"高威胁悬赏。
**根因**：结束判定的超时分支是 `meRatio >= bestFoe ? 'me' : 'foe'`，平局（双方都满血）天然落在我方胜；而结算侧 `won = battle.ended === 'me'` 直接发全额奖励。
**解法·规避**：打满上限一律判负，并复用"被迫撤退"既有通道（`ended='foe'` ＋ `autoEscaped` ＋ `escapeReason='timeout'`）走轻损撤退；删掉血量比死代码，不新增机制、不动 `maxBattleMs`。
**复发检查点**：`npm run battle:calibrate` 不应再有 `600s` 格记为"胜"；单测把双方血量都拉到 1e9 强制超时，断言 `ended==='foe'`、`escapeReason==='timeout'`、钱包不增反减。
**来源**：`docs/design/timeout-defeat-20260910.md:11`、`:24`、`:34`、`:44-48`、`:113-121`

### 1.2 维修脉冲只查"是否已满"、不查存活 ⇒ 把尸体修活

**现象**：生物损管腔之类的修理装置让已经损毁的船复活；更糟的是后勤舰每跳优先修"剩余比例最低的队友"，而尸体比例恒为 0，活着的重伤队友一点血都拿不到。
**根因**：`battle.units` 里的尸体永不摘除（多波增援、战报、敌方"在场过=存在"都依赖它），但两条维修脉冲只判"甲＋结构是否已满"，没有 `isAlive` 检查；被动护盾回充、护盾充能脉冲、结束判定本来都查了，属同一把尺上的缺口。
**解法·规避**：四处各补一行 `isAlive`——自修入口直接让该装置永久停机（尸体不会回场，无需再排程）、后勤选靶跳过阵亡者、敌方供血方与选靶同样过滤；不改"尸体留场"口径，也不改数值与文案。
**复发检查点**：`rg -n "pulseRepairsFor|pulseFoeRepair" packages/core/src/combat.ts` 逐个确认都有存活判据；跑 `tests/dead-ship-no-revive.test.ts`（修前 6/6 红、修后全绿）。
**来源**：`docs/design/dead-ship-revive-20260919.md:9`、`:11-18`、`:20-22`、`:29-34`

### 1.3 沉船判定只在虫洞写过一次 ⇒ 遭遇槽（旗舰战）漏判

**现象**：玩家在入侵旗舰战里沉船后撤退，沉船被"复活"带回港、还能花钱修好。
**根因**：`persistFleetHullDamage` 如实写出 `durability = 0`，但全仓没有任何一处把"0% 结构"当"已沉"（只有 `< 0.5` 的自动修理/返港判据）；遭遇战收场只落盘承伤、从不判沉船，而虫洞那条路是判沉船并 `loseShip`。
**解法·规避**：判据收口成单点 `sunkShipIdsOfBattle`（我方三层血合计 ≤ 0；多舰走 `myFleet`、单船回落 `units['player']`），虫洞 / 遭遇战（撤退＋分胜负两支）/ 战报三处共用，删掉虫洞那份私有实现。判据是"≤ 0"而不是"很惨"——剩 5% 不丢船。
**复发检查点**：新增战斗宿主时补两张清单——①"在不在打"的三口径（`inLiveBattle` / `battleFoeAnomaly` / 距离条 / 撤退 / 逐舰承伤与机群战损）；②"收场怎么结"的逐项对齐。`content:check` 的结算口径契约必须写成**带左括号的调用式**（第一版写成 `body.includes(名字)`，把调用改成 `void 名字 // 注释` 就能骗过闸门），并补一次"故意改坏 ⇒ 闸门必红"的反向探针。
**来源**：`docs/design/encounter-sunk-ship-20260928.md:10`、`:13`、`:16-18`、`:22`、`:28-32`、`:42`；`docs/design/settlement-contract-desire-drone-20260928.md:9-13`、`:17-27`；`docs/design/weekend-invasion.md:299`

## 2. 舰船插件与装备槽位

### 2.1 槽位数只按船型基础布局算 ⇒ 扩槽件"重启就丢"

**现象**：玩家报障「船插增加的中槽和低槽上的装备无法保存进配置，重启游戏后会丢失」。
**根因**：一次"扩槽插件生效"改造只改了装配校验与装配页格数两处，漏了另外三处同样按"船型基础布局"算槽位的地方：读档修复链把 `fitted.mid/low` 截回基础长度（扩出的那格连同装备退回装备库）、套用方案时 `Math.min(src.length, slots[rack])` 静默不装、明细显示把那格当 `overflow` 报出来。
**解法·规避**：三处全改走**槽位单点** `plugs.shipSlotsWithPlugsOf`（船型布局 ＋ 插件扩槽），与装配校验、装配页格数、`ensureRackBays` 同一把尺；并全仓审计 `shipSlotsOf` 每个调用点该用哪把尺（`shipInfo.slotListText` 收的是船型、显示"船型布局"，语义正确不改）。
**复发检查点**：`rg -n "shipSlotsOf|shipSlotsWithPlugsOf" packages/` 逐个判"船型还是实例"；用例必须做**存档往返端到端**（存→读→跑修复链⇒装备仍在），并把旧口径临时改回去确认用例真的会红。
**来源**：`docs/design/plug-slot-persist-20260928.md:6`、`:11-18`、`:22-29`、`:32-39`

### 2.2 装卸分流写 id 前缀判据 ⇒ 插件卸货后"不见了"

**现象**：玩家把插件放到货仓再卸进仓库后插件不见了。
**根因**：`isModuleCargoId` 原先 `return id.startsWith('mod-')`，而舰船插件的 id 是 `plug-*` ⇒ 卸货时被当物品扔进 `state.warehouse.items`，而物品页只列物品目录里的东西 ⇒ 装备躺在物品仓库里**任何界面都没有入口**（东西一直在存档里，不是真丢）。
**解法·规避**：判据改成**查装备目录** `ctx.modules.has(id)`，不看 id 命名；两个卸货入口收 `ctx` 并同步全仓调用点；再补一个幂等的存量修复 `repairMisplacedWarehouseModules` 挂在每次读档的载入修复链上（这是"归位"不是发放，所以不做一次性标记）。
**复发检查点**：跑"真目录全量对照"护栏——装备目录每一件都必须判成模块、物品目录每一件都不许判成模块；`rg -n "startsWith\('mod-'" packages/` 确认只剩有意为之的家族过滤（`mod-lair-` 窝点、`mod-wh-` 虫洞族）。
**来源**：`docs/design/plug-cargo-and-fit-slot-20260926.md:12-15`、`:19-25`、`:49-55`

### 2.3 装配页插件槽区块读错船 ⇒ 所有舰船显示同一套插件

**现象**：玩家报障「所有舰船的舰船插件都是同一个」。
**根因**：`FitPage.PluginSlotsSection` 里写的是 `const shipId = state.shipId`（主控船），而调用点根本没传本页目标船 ⇒ 从舰船页点别的船进装配台时，插件槽整块显示主控船那一套。同页其它区块（弹药档位 / 无人机舱 / CPU 条 / 槽位组）都读 `effectiveTarget`，只有这一块漏了。
**解法·规避**：调用点传 `target={effectiveTarget}`、组件签名收 `target`、体内改用 `plugInfoOf(state, ctx, target)`；这是只读区块、无数据损坏（插件一直挂在各自船上，只是显示错）。
**复发检查点**：补**装配页源码契约**用例——调用点必须传 `target`、组件签名必须收 `target`、区块体内不得再出现 `state.shipId`；把调用点改回不传 ⇒ 契约例必须当场红。
**来源**：`docs/design/plug-cargo-and-fit-slot-20260926.md:29-35`、`:53-55`

### 2.4 插件全部声明 `rack: 'low'` ⇒ 能真装进低槽并可拆卸

**现象**：部分船插出现在装备栏，且能被装进低槽。
**根因链**：① 13 件插件全部声明 `rack: 'low'`（注释写明"为满足体检契约"）→ ② `labels.rackOf()` 优先返回 `def.rack`，插件被判成低槽 → ③ 装配页低槽候选按 `rackOf(m) === rack` 过滤，插件因此出现在候选里 → ④ core 装配校验只查同舰唯一 / 位可用 / CPU，**没有"这件允不允许装这个槽"的判断**，插件真被写进 `fitted.low`。
**解法·规避**：`labels.ts` 立单点 `isRackModule(def)`（= `slot !== 'plug'`，不引 `plugs.ts` 以免成环）、装配入口拒收插件（插件只走 `installPlug`）、装配页两处过滤加拉黑、读档修复把误装低槽的插件搬回插件槽（槽满退回装备库）。
**复发检查点**：任何"槽位候选过滤"改动都要问一句"这件是不是根本不该出现在槽位候选里"；用例覆盖"低槽装不进插件"与"读档搬回（含槽满退回）"。
**来源**：`docs/design/plug-loss-20260927.md:29`、`:35-42`、`:44-50`

## 3. 无人机与点防

### 3.1 点防"无单场上限"＋回收名额"逐型各自取整" ⇒ 白丢名额

**现象**：引入点防后机群规模随战斗递减；但首版回收按"每型各自 `round(损坏数 × 回收率)`"，四型各坏 1 架、回收率 20% 时四型各 `round(0.2)=0` ⇒ 总名额 `round(0.8)=1` 被白丢。
**根因**：单场上限从 50% 放开到无上限（战斗内可 100% 损坏）后，回收总量与逐型取整不再天然对齐。
**解法·规避**：总回收数**不变**（仍是 `round(总损坏 × 回收率)`，只改"分给谁"）：每型先 `floor`，余数名额按机型基准价从高到低补满，某型补到"损坏数"就换下一型；价值用 `ctx.items` 的 `baseSellPriceIsk` 现算，不写死顺序。战报显示回收/净损失明细，时长 6→12 秒。
**复发检查点**：用例断言改**不变量**（总数 = `round(总损坏×回收率)`、每型 `floor ≤ back ≤ lost`、"低价值拿到余数 ⇒ 更高价值已用满余量"）；把价值排序反过来，用例必须如实失败。
**来源**：`docs/design/drone-losses-20260910.md:36`、`:121-141`、`:227-241`、`:259-263`

### 3.2 储备甲板初版在战中扣库存，且战损账战后会被清空

**现象**：无人机储备甲板（被摧毁后按周期补一架）初版"从仓库补充"，等于每次复活当场写玩家库存；真实节拍跑完整场后读 `b.droneLost`，又得到"被击落 0 架、却补回 13 架"这种自相矛盾的读数。
**根因**：① 把取货放在战斗过程里，让纯模拟的战斗直接改玩家档，并引出多舰同时从同一仓库超补、以及"复活扣一次、战后 refill 再扣一次"的双扣；② 远征结算后 `settleDroneLosses` 按既有幂等口径把战损账**清空**；③ 结算报告的"损坏数"按清单实有数封顶，而复活计的是**事件数**（一架可以"打掉→补回→再打掉→再补回"）⇒ `revived > killed` 是正常的。
**解法·规避**：改为**开战预算快照**（`battle.droneReviveStock`，机型→可补架数）：战中只扣预算、库存一分不动；扣货全部收在战后一处，顺序 = 扣复活架数 → 扣净损失 → 按出发快照补货。快照是**全队一本**（按舰各拍一份会超补），扣不满记 warn 不静默吞。战后展示改读结构化 `state.droneLossReport`，只在当前驾驶船结算里写入并配 `battleStartedAtGameMs`，避免 AI 副船损失串进战报。
**复发检查点**：`rg -n "takeDroneUnit|droneReviveStock" packages/core/src` 确认战斗路径里没有直接写库存的调用；任何"战后展示战斗内部计数"的需求，先确认该账是否已在结算时清空，跨场读数一律走报告快照而非运行态字段。
**来源**：`docs/design/drone-deck-20260927.md:22-48`、`:158-167`；`docs/design/drone-losses-20260910.md:227-253`

### 3.3 僚舰的常驻型无人机：开火起点用的是主控布局

**现象**：舰队战里僚舰的无人机"攻击没有动画"——机体挂在僚舰自己的伴飞位，弹道却从主控的伴飞位射出（两个偏移量完全相同，根因肉眼可判）。
**根因**：常驻型（`model.resident`）无人机的开火起点走的是 `droneHomeStation(dm, …, layFx)`（主控布局）而不是发射舰自己的锚；同一批还有一处对称缺陷——我方无人机被点防击落时的坠落/爆炸点，其"自家机库口"同样写死 `layDown.me`。
**解法·规避**：新增 `droneOwnerAnchor`（`ally-N`→它自己的锚；`player`/缺 tag/单船→主控锚）与 `residentDroneFrom`，开火起点与坠落点都改走逐舰取锚口；单船/主控路径回落主控锚 ⇒ 逐像素不变。补 `content:check` 契约：`BattleScreen` 剥注释后必须 ≥2 处调用逐舰取锚口，且不许再出现旧写法。
**复发检查点**：`rg -n "droneHomeStation|layDown.me" apps/desktop/src/renderer/src/panels/` 应为 0；`npm run battle:bolt` 覆盖僚舰/主控/缺 tag/单船四种锚点。
**来源**：`docs/design/escort-drone-anchor-20260929.md:43-53`、`:55-61`、`:88-90`

## 4. 敌舰火力、射程与距离

### 4.1 名义火力与实际火力脱节 ⇒ 按纸面重锚会翻数倍

**现象**：A 族整编后，蜃影导航劫持令从 100%/残血 50% 掉到 20%/残血 1%，赤潮劫掠舰队残血 88% → 30%。
**根因**：这两张卡原有逐卡伤害压制倍率（旧 `foeDmgMul` 0.27 / 0.30），而重锚公式取的是基线"**总DPS**"列——那一列对这两张卡从来不是实际火力 ⇒"名义 ×1.6"实际等于把压制无声取消，`×1.6 ÷ 0.27 ≈ ×5.9`（实测 5.97）。船长定性：**这是公式错误，不是执行错误**。
**解法·规避**：`foeDmgMul` 整体退休且**不得恢复**（类型上已删除），改用卡上 `dmgMul` 重锚，锚点 = "改造前的实际火力"；并确立口径——**难度守恒按「实收」判定**：N 个单位逐个被击毁 ⇒ 整场实收 ≈ 纸面 × `(N+1)/(2N)`，所以纸面锚要按改动前单位数换算（本例纸面 ×1.6 要收到 ×1.2 才实收守恒）。
**复发检查点**："威胁 × `foeDpsPerThreat`"与实际建档火力的偏差表当时**仍是独立待办**，`content:check` 与用例都不会报警，只能靠实测发现；`battle-calibrate` 的"总DPS"列对舰级路径卡必须取逐舰级读数，单取 `specs[0]` 会静默只报头目。
**来源**：`docs/design/foe-faction-a-numbers-20260911.md:198-209`、`:216-230`、`:251-260`、`:270-276`、`:289`

### 4.2 kite 卡头目射程带太短 ⇒ 纸面 60% 火力一次都没落地

**现象**：三张 kite 卡的残血始终高于锚点，怎么调都调不动。
**根因**：头目舰是近战舰级（射程带 1~2210 m），被覆写为 `kite` 后实际行为是"想拉距但打不远"；探针实测交战距离 3.2~3.8 km > 2.21 km，**头目一次都没开火**，即"纸面 60% 火力"完全没落地。
**解法·规避**：先分清"清场过快"与"射程带太短"两种 0 开火——边境/碎晶那边是玩家 21~23 秒就打完、敌人从未进入接触窗口，**写射程覆写只会更打不到**（把 2210 m 缩成杂鱼的 1883/1932 m）；只有"杂鱼能打、只有头目打不到"的 kite 卡才写覆写。
**复发检查点**：调敌舰难度前先看校准表的"敌方头目开火次数"列，0 次就是没落地，不要继续调残血；"整队 0 开火"必须先归因再动手。
**来源**：`docs/design/foe-faction-a-numbers-20260911.md:262-268`、`:318-323`、`:329-335`

### 4.3 射程带的"近界"不是设计出来的盲区

**现象**：为让敌舰"落在我方射程盲区边界附近"，新增开场距离修正后，几乎所有旧卡的开场距离被压到 200~400 m（贴脸），一次改红 5 个既有用例（ammo-volley / t8 / target-lock / battle-fx-dmg / drone-loss）。
**根因**：旧路径卡的"近界"只是**射程带下界**，不是设计出来的盲区——合成卡（威胁 8/20/30）近界只有 350/377/404 m、上限 4,600~5,300 m，占比 ≈ 8%。
**解法·规避**：判据加"真近程盲区"门槛：`射程带近界 ÷ 射程上限 ≥ 15%` 才算；修正量 = `max(距离下限, 最远盲区边界 − 200m)` 再钳在 `[下限, 原开战距离]` 内；没有盲区 / 够不着 ⇒ 返回 0 逐字走原口径。
**复发检查点**：`rg -n "battleOpenBlindSpotM|FOE_BLIND_SPOT_MIN_SHARE" packages/core/src`；改开场距离后必须复跑上述 5 个用例，并单独确认"R 族五档 `rangeMinM` 全是 1 ⇒ 本族开场距离一分不动"。
**来源**：`docs/design/weekend-faction-corona-20261001.md:670-684`、`:695-701`

### 4.4 C 族全族 +1000 射程 ⇒ 大虫子"冲锋没效果"

**现象**：船长反馈「大虫子的冲锋似乎没有效果」，把冲锋倍率 ×2 提到 ×4 也测不出来。
**根因**：冲锋触发条件是"距离 > 冲锋者自己射程"，而同一批刚给虫子 +1000 射程（噬口从 2,713 m 变 3,713 m）⇒ 平时的 543~1,400 m 交距下它**永远不冲**；×4 也改变不了这件事实。
**解法·规避**：先讲清机制再改数（倍率只加在"接近速度"上、只乘冲锋者自己、不外溢僚机）；最终按船长选的"乙方案"加 `foeChargeTriggerMarginM`，触发扩为"够不着 **或** 距离 > 期望交距 + 1,000"。
**连带教训**：改射程带会同时改**命中折减基准**（同距离折减变高）、**期望交距**（若靠带内插值推导）、**开战距离**（`battleOpenM` = 双方最远武器 × 系数 ＋ 缓冲）、**冲锋门槛**四件事；"目标距离不变"必须靠已有 `desireRangeM` 覆写逐个条目钉住，多波卡末波 `foes[0]` 会换人所以每个条目都要钉。本批最终整条回滚：撤掉钉子后由插值重新推出**同样的数**，所以回滚只动射程与开战距离、交距逐字不动。
**复发检查点**：校准 A/B 必须看"同向"而不是单格——每格 5 个种子、时机一变 RNG 链重排，单格反方向抖动是噪声；回滚不是单向"变简单"（近距装配因开场距离缩短反而更疼：裂谷/星髓 A3 从 100% 掉到 80%、时长 23s→58s）。
**来源**：`docs/design/foe-c-range-20260914.md:23-33`、`:99-111`、`:117-121`、`:128-147`、`:154-176`

## 5. 大编队、存档与界面

### 5.1 只换开战函数、不改收尾 ⇒ 僚舰承伤/沉船/返航全漏账

**现象**：12 舰统一指挥预算改造里最容易想到的是"换开战入口"，但普通远征的胜负、撤退、战损和返航当时仍多处围绕 `state.shipId` 处理。
**根因**：单船时代把"玩家 = `state.shipId`"写进了结算各处；只换开战函数会让僚舰的承伤、沉船、货仓、返航、补给全部漏账。遭遇收尾当时已有逐舰辅助可作参照，但据此不能认为普通远征已完成多舰闭环。
**解法·规避**：按"出勤名单 → 逐舰收尾"重做——参战实例在战斗与返航期间锁定，不静默缩编/替船/临时从基地召僚舰；逐舰核算弹药与修理组件、无人机损失、装甲/结构写回、沉船/残骸、主控更换、存活舰返航卸货；目标奖金/声望/首胜每场一次、不乘舰数。
**复发检查点**：`rg -n "state\.shipId" packages/core/src/{expedition,encounters,ai}.ts` 逐处判"这里该不该是逐舰"；专项必须覆盖"返航锁舰"与"主舰沉没后战利品归属"。
**来源**：`docs/design/combat-command-budget-20261030.md:24`；`docs/design/combat-command-implementation-20261030.md:36-40`、`:84`

### 5.2 12 舰布局沿用旧几何 ⇒ 越界；Node 毫秒数 ≠ 窗口不卡顿

**现象**：放开编队上限到 12 舰后，现有布局函数按 12 巡洋计算，1600×900 有 8 艘我舰越界、1280×720 有 9 艘、390×844 有 11 艘我舰和 6 艘敌舰越界。
**根因**：编队数量是玩法层改动，战场布局是按旧舰数写死的几何；"敌我各最多 12 艘"必须同时改布局与敌舰同时上限（初始波、增援、复活、召唤都要服从 12 舰在场上限，超出的进待入场队列，不直接裁掉敌人/火力/奖励/波次，敌无人机不计舰体数量）。
**连带教训**：Node 引擎读到的每步 0.53~0.78 ms 不含 React、DOM、布局、绘制、GPU 与真实 IPC，**不能**拿来宣称窗口不卡顿；验收必须在生产构建的独立隐藏 Electron 窗口测帧耗时分布、长任务、内存、节点/特效数量、进退场与最小化重开。
**复发检查点**：改舰数/阵形后三档视口量越界（桌面/窄桌面/模拟手机）；基线脚本要显式带桌面 `env.d.ts` 声明，首次不带产生的宿主类型缺失不是靠改生产声明"修好"的。
**来源**：`docs/design/combat-command-implementation-20261030.md:53-60`、`:86`、`:127-130`

### 5.3 随档字段必须同时进 `state.ts` 与 `save.ts` 清洗器

**现象**：入侵旗舰的 `foeGalaxyId`、`bossHp/bossHpMax`、`bossShipId`、`bossHpLayers/bossMaxLayers` 写进了 `state.ts` 却漏了 `save.ts` 清洗器 ⇒ 读档丢值。
**根因**：本仓存档是**白名单重建**而不是整体透传，所以"类型里加了字段"与"存档会保留它"是两件事；这类漏项不会在类型检查里报错。
**解法·规避**：随档字段一次性两处落笔，并一起维护规范化白名单与往返测试；旧在途记录不能与新字段混算，损坏的新记录走明确停运/安全收口，不静默补 0。
**复发检查点**：`rg -n "<新字段名>" packages/core/src/{state,save}.ts` 必须两处都命中；跑 `save:roundtrip-audit`（可读 / 预期拒读 / 意外失败 / 往返变形四项分开报，不合并成一个"全绿"）。
**来源**：`docs/design/weekend-invasion.md:301`；`docs/design/industrial-fleet-ambush-20261101.md:372`

### 5.4 期望距离记忆：传 `undefined` 会掉回"按卡星系读"

**现象**：玩家反馈入侵和旗舰战"并不会记忆玩家选择的期望距离"。
**根因**：写入端一直是好的，漏的是开战时的读取——远征/入侵那条传 `undefined` 恰好能靠引擎回落拿到同源值（反而**不该**再显式补一次，否则变成两处读同一份）；但旗舰战传 `undefined` 会掉回"按卡自带星系读"，而旗舰卡是隐藏卡、母港是 `galaxy-hub` ⇒ 读到母港那份不相干的悬赏偏好。
**解法·规避**：显式传 `desirePrefOf(state, state.weekendEvent?.coreId)`，并且**传 `null` 而不是 `undefined`**（未命中时它本就返回 `null`）；用例钉住"只写 `galaxy-hub` 不许影响旗舰战"与"远征那条的引擎回落照旧"（防止日后有人再补一次）。
**复发检查点**：新增战斗宿主时列出"这个宿主开战读哪一份距离偏好"；`rg -n "desirePrefOf" packages/core/src` 核每个调用点第二参是 `null` 还是 `undefined`。
**来源**：`docs/design/settlement-contract-desire-drone-20260928.md:29-48`；`docs/design/battle-card-range-memory-20261021.md:10-14`

## 6. 弹药与旗舰收尾

> 历史背景：船体维修装置的预载/退还与"只把消耗组件数量显示到战后总结"的日志口径，见 `docs/archive/retired-docs-20261029/hull-repair-module-20260909.md`（**历史档案**）`:46-52`、`:88-102`；其中数值已被多批改动覆盖，不得当现行值引用。
### 6.1 弹药档位用"武器 slot→弹族"硬映射 ⇒ 爆炸炮台显示动能弹

**现象**：玩家反应掠袭破片炮消耗的是动能弹药，装配内显示的也是动能。
**根因**：武器真值、预载、战斗逐发扣弹都按模块的 `damageType` 走（破片炮是 `explosive`，只有副伤害是 `kinetic`），但 `FitPage` 的 `AMMO_SLOT_TYPES` 固定把 `turret` 映射到 `kinetic`、`AmmoTierSection` 又用高槽件的 slot 筛显示行 ⇒ 即使 `ammoLoadTotals` 已算出 explosive 预载，档位区也只渲染动能行。
**解法·规避**：去掉 slot→弹族映射，直接按**真实预载正需求**显示弹族（纯破片炮只显示爆破、混装动能/爆破两族同时显示、不耗弹的基础炮不出现假档位）；保留既有档位选择、库存取数、预载与战斗扣弹规则，不动伤害/弹药数值。
**复发检查点**：`rg -n "AMMO_SLOT_TYPES" apps/desktop` 应为 0；同类检查——凡"从武器槽位猜属性"的地方都要改成"读武器真值/预载单点"。
**来源**：`docs/design/raider-fragment-ammo-audit-20261009.md:13-14`、`:34`、`:44`

### 6.2 旗舰共享血池的小数取整 ⇒ 打死了还剩 1 HP、要再打一场

**现象**：玩家报障「继承旗舰后，旗舰战并没有结束，会剩余 1HP，需要再进入打一次」。
**根因**：章鱼在线削血保留小数，旧入场 HP 用四舍五入、战斗伤害台账也取整：共享池还剩 100.25、实战只生成 100 HP，打空后账本只扣 100，原始池剩 0.25，界面保底显示 1 HP，于是允许再开一场。
**解法·规避**：新开战把共享池入场 HP **向上取整**，台账与最终伤害走本批单点，不再生成小于池余额的战斗总 HP；旧已开战兼容只在"同时确认旗舰身份、本场只出现一艘旗舰、`bossDownAtMs`、敌舰 HP 已归零"时才补最多 1 HP 尾差，其余一律不清池；反向守卫——新场 101 HP 旗舰尚余 0.1 时，伤害向上取整不能自行认领击沉。
**复发检查点**：`weekendFlagshipHpRemaining` 是可入场血量读数、**保留最小 1 的旧返回约定**，结局成功不能拿它返回 0 当标准，要用"活动已结束 ＋ 归属 player ＋ 黑匣只发一次 ＋ 再次开战被拒绝"判断。
**来源**：`docs/design/gravekeeper-flagship-finish-20261018.md:14-19`、`:23-26`

## 校验回归清单

- [ ] 超时/撤退/沉船/全灭四种结束态，逐个确认"哪个宿主、哪条结算路径、哪条用例"覆盖（对照 `sunkShipIdsOfBattle` 的调用点）。
- [ ] 槽位/格数/容量类改动，`rg -n "shipSlotsOf|shipSlotsWithPlugsOf|wantedBaysOf|ensureRackBays"` 全仓判"船型还是实例"，并补一条存档往返端到端用例。
- [ ] 新增装备/模块族，跑 `npm run typecheck` ＋ `npm run content:check`，逐条收下它们抓出的漏项（字段→家族契约、取值域、图标 SHAPES/TONES、短效说明、市场行）。
- [ ] 新增随档字段，`state.ts` 与 `save.ts` 两处同时落笔，跑 `save:roundtrip-audit` 四项分开看。
- [ ] 改敌舰射程/火力/编成后跑 `npm run battle:calibrate`，核对 A0~A3 是否同向、有无 `600s` 触顶、敌方头目开火次数是否为 0。
- [ ] 改无人机/点防/回收，跑 `npm run battle:pd-tune` 看战损机型与"占奖励比"，并确认成本轮没有把"平衡读数"当成用例断言。
- [ ] 改战场布局或舰数后，三档视口量越界，并在生产构建的隐藏 Electron 窗口测帧耗时与长任务；不拿 Node 读数当结论。
- [ ] 新写源码级契约要做"故意改坏 ⇒ 闸门变红"的反向验证；修 BUG 的用例先证明"修前红、修后绿"，再把旧口径临时改回去复现一次报障。
- [ ] 报障涉及"体感无变化/无损失"时，先排除"结算立刻按出发编制补满"这类观感来源，再怀疑机制。
