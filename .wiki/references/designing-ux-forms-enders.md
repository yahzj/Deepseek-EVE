> 知识地图参考页：本指南基于信息设计与人机交互领域表单经典专著《Designing UX: Forms》（杰西卡·恩德斯 Jessica Enders 著，SitePoint 全本），系统梳理全书理论体系、认知模型与交互工程准则，并深度映射至《大鲸鱼-深空放置》中舰船装配、星系贸易、数值输入、离线策略及数据编辑器等复杂表单的工程实践。

## 结论先行

- **表单的本质是人际对话而非数据采集**：表单不是冷冰冰的数据库字段搬运工，而是系统与用户建立信任、展开交流的结构化对话。每一次糟糕的提问、冷漠的报错和突兀的必填，都是对用户信任关系的暴力摧残。
- **回答问题的四阶段认知阻力**：用户面对每一个输入项，都在大脑中经历**理解（Comprehension）→ 检索（Retrieval）→ 裁量（Judgement）→ 录入（Answering）**四重认知负荷。设计者的天职是在每一个阶段主动分担用户的脑力，而非让用户在「满意度折衷（Satisficing）」中胡乱应付。
- **单列垂直流（Single Vertical Path）是表单布局的金科玉律**：除极少数紧密绑定的微字段外，坚决杜绝多列横向平铺；严禁使用占位符（Placeholder）替代标签（Label）；以格式塔亲密性定义间距；让输入框物理宽度直接映射预期输入的长度。
- **下拉菜单（Dropdown / Select）是界面交互的阿喀琉斯之踵**：下拉菜单因其隐藏选项、打断视线、移动端操作繁琐及无法横向比对，成为表单可用性杀手。少于 5 项用单选框组（Radio Group）或分段控件（Segmented Control），海量选项用自动补全输入框（Autocomplete）。
- **《大鲸鱼-深空放置》的核心映射准则**：
  1. **配置流前馈化**：舰船配装、技能规划与科研排期杜绝「提交后才弹红报错」，依托失焦/防抖行内校验与前馈计算，让槽位与 CPU/PG 预算动态就地消化。
  2. **数值输入三元联动**：市场交易、物资转移与批量生产摒弃纯滑块或裸输入框，实行「步进器 + 动态滑块 + 数字输入框 + 快捷百分比」三元联动，双向计算总价与余量，杜绝手滑破产与爆仓溢出。
  3. **数据编辑器 QxQ 契约化**：在 `tools/data-content-editing` 工具链中，为海量游戏数据建立严密的逐题（QxQ）契约，定义类型约束、智能默认值与实时合理性审计（Sensibility Check）。
  4. **挂机策略防呆与容错**：离线巡航与战术策略表单杜绝死循环配置（如回港阈值高于巡航阈值），提供基于舰船定位的智能推荐预设与宽容格式输入。

## 二、表单体验工程核心章节深度精要

### 1. 表单的三维模型（Three Dimensions of Forms）

杰西卡·恩德斯指出，设计者常犯的严重错误是将表单仅视为「界面外观（Appearance）」的美化，从而忽略了更底层的另外两个维度：

```
           [ 关系维度 Relationship ]  ─── 品牌认同、隐私信任、交互意图、互惠心理
                     │
           [ 对话维度 Conversation ]  ─── 语言风格、提问次序、逻辑闭环、情绪安抚
                     │
           [ 外观维度 Appearance ]    ─── 布局排版、控件选型、视觉动线、间距色彩
```

- **关系（Relationship）**：
  - 表单是组织与用户之间关系的载体。用户在填写表单时，本质是在出让隐私、时间与精力，以换取某种价值。
  - **侵入性失衡**：过早或强制索取敏感信息（如非交易必须的手机号、身份证、家庭住址），会直接摧毁初期建立的脆弱信任，引发高跳出率或虚假数据输入。
  - **互惠原则**：表单设计必须让用户感知到「我提供这项数据，能获得即时的对应价值」（例如：输入星系坐标，系统即刻呈现安全评级与矿产分布）。
- **对话（Conversation）**：
  - 表单是一场异步的结构化对话。人类正常对话是有礼貌、轮流发问、不反复盘问已知信息的。
  - 如果现实中一个人突然在聊天中打断你、问非所问、或要求你重复三次同样的事情（如重复输入密码），你一定会认为对方极其失礼。糟糕的表单正如这种无礼的交谈者。
- **外观（Appearance）**：
  - 视觉层是承载对话的物理界面。优秀的视觉设计不是为了「花哨」，而是为了让对话尽可能顺畅、轻盈、无障碍。视觉上的混乱会直接投射为对话上的断裂。

### 2. 回答问题的四阶段认知心理模型（Four-Stage Model for Question Answering）

恩德斯将认知心理学家 Tourangeau & Rasinski 的四阶段问答模型完整迁移至表单工程，揭示了用户在每个输入项前的心理历程：

```
    [用户看到问题]
          │
          ▼
   1. 理解阶段 (Comprehension)  ────► 读懂字面单词与背后的真实意图？
          │
          ▼
   2. 检索阶段 (Retrieval)       ────► 能从记忆或外部资料中快速提取事实？
          │
          ▼
   3. 裁量阶段 (Judgement)       ────► 答案是否符合格式？说实话安全吗？选项能代表我吗？
          │
          ▼
   4. 录入阶段 (Answering)       ────► 映射到界面的控件（点击/打字）上？
          │
          ▼
    [完成当前问题]
```

- **阶段 1：Comprehension（题意理解）**
  - **痛点**：行业黑话、缩写、官僚术语、模糊不清的代词。
  - **完整问句 vs 短提示语（Full Sentence vs Brief Prompt）**：
    - 简单、通用概念采用短提示（如 `邮箱`、`指挥官姓名`）；
    - 带有前置条件、法律约束或复杂场景的提问，必须使用完整的问句（如 `过去30天内，该舰船是否曾参与过低安星系交火？`），切忌将长问句压缩成令人费解的短语。
- **阶段 2：Retrieval（记忆与资料检索）与「满意度折衷（Satisficing）」**
  - **痛点**：问题要求用户回忆精确但难以记住的数值（如 `3个月前累计消耗的三钛合金总量`）或查阅隐藏证件。
  - **赫伯特·西蒙的「满意度折衷」定律**：人类在面对高认知阻力时，不会追求最优解，而是追求「满意可用解/能交差就行」。当表单检索成本过高时，用户会开始胡乱填报虚假数值，导致系统底层数据质量雪崩。
  - **解法**：就地提供外部知识检索提示（如「在星图右上角查看星系编号」），支持近似范围估算，或由系统自动拉取玩家历史日志自动预填。
- **阶段 3：Judgement（答案裁量与心理校验）**
  - **痛点**：用户检索到了事实，但在决定是否提交时产生纠结：「系统要这个干什么？」、「如果没有完全匹配我的选项怎么办？」。
  - **解法**：在提问旁直接提供微观上下文解释（Contextual Help）；在单选题中确保选项穷尽且互斥，必要时提供「其他/不适用」逃生通道。
- **阶段 4：Answering（物理录入）**
  - **痛点**：想填的内容与界面控件形态冲突（如控件强迫分为三个框、或者格式限制不给输入特殊符号）。
  - **解法**：降低物理操作摩擦，保证控件对齐直觉，支持多种格式输入由后台自动解析。

### 3. 文本与语言工程（Words Matter Most）

恩德斯强调：**在表单中，文案的影响力超越一切花哨的动效**。

- **题干与标签设计原则**：
  - **简明（Plain Language）**：用最普通人的词汇取代开发者的内部字段名（如用 `每秒伤害输出 (DPS)` 取代内部字段 `f_turret_dmg_rate_calc`）。
  - **标签末尾标点**：严格**不加冒号（No colon at the end of labels）**。在现代 Web 与移动端，冒号是机械打字机时代的无意义残留，只会制造视觉边缘杂点。
- **行动按钮文案动宾法则（Action-Object Principle）**：
  - **严禁无脑词汇**：坚决废弃模糊、冷漠的 `提交 (Submit)`、`确定 (OK)`、`下一步 (Next)`。
  - **动宾结构清晰明确**：使用具体的 `[动词 + 宾语]`，如 `创建指挥官角色`、`确认装配方案`、`发起星系跳跃`、`导出配置清单`。
  - 动宾文案让用户在不读上下文的情况下，单看按钮就能准确预判物理动作的后果。
- **人称代词策略（Yours or Mine?）**：
  - **默认准则：尽量不用人称代词**。写 `电子邮箱` 而不是 `您的电子邮箱`，写 `收货地址` 而不是 `我的收货地址`。省略代词让界面最干净利落。
  - **需要区分主体时的统一定位**：
    - 提问属于系统向用户发问，使用第二人称：`Your Ship (你的旗舰)`；
    - 按钮属于用户向系统下达意志，使用第一人称：`Claim My Bounty (领取我的赏金)`。
    - 绝对禁止在同一个屏幕上混淆使用「您」、「我」导致指代主体混乱。
- **建设性错误文案三原则（Constructive Error Messages）**：
  任何只提示「输入错误」或「格式不合法」的报错文案都是合格设计的耻辱。优秀报错必须满足三要素：
  1. **发生何事（What happened）**：客观、非指责性陈述事实（例：`跳跃能量不足`，而非 `你未充能`）；
  2. **为何发生（Why it happened）**：解释触发约束的原因（例：`跃迁至该星区需要至少 450 GJ 电容，当前仅余 210 GJ`）；
  3. **如何解决（How to fix）**：给出确定性的下一步行动指南（例：`请等待电容回充 35 秒，或装配辅助电容电池`）。

### 4. 物理布局与视觉平衡（Single Vertical Path & Layout）

#### 单一垂直完成路径（Single Vertical Path to Completion）
- **核心法则**：全表单呈单列从上向下延伸。
- **多列布局的毒害**：横向并排多个问题会导致用户的视线呈 Z 字形反复折返，不仅大幅增加眼球运动与认知负荷，而且在屏幕自适应缩放或移动端换行时极易造成意想不到的字段错位与漏填。
- **唯一的并排例外**：仅在语义上**极度绑定且简短**的微字段组合时才允许横排（例如：`[城市] [邮编]`，或 `[最小射程] - [最大射程]`）。

```
  【错误：多列横排导致视线折返】             【正确：单列纵向路径流】
  [问题 1] ──────► [问题 2]                [问题 1]
     │                                        │
     └────────┐                               ▼
              ▼                               [问题 2]
  [问题 3] ──────► [问题 4]                   │
                                              ▼
  (视线不断横向拉扯，极易漏填)                 [问题 3]
                                              (一气呵成，单向平滑向下)
```

#### 标签位置（Label Placement）与视线沟壑
- **顶部标签（Top-aligned Labels）为王**：
  - 标签置于输入框正上方，符合自上而下的自然阅读眼动（Saccade）。视线从标签到输入框几乎无横向偏转，完成速度最快，且天然自适应多语言翻译文本长度膨胀。
- **左对齐与右对齐标签的局限**：
  - **左对齐（Left-aligned）**：导致标签与右侧输入框之间形成巨大的「空白水沟（The Gutter）」，视线左右反复横跳，阅读极其吃力，仅适合需要极慢核对的超复杂合同表单。
  - **右对齐（Right-aligned）**：虽然缩短了与输入框的距离，但左侧边缘参差不齐，用户极难自上而下快速扫视题目。
- **严禁使用 Placeholder 代替 Label**：
  - **四大罪状**：
    1. 键入第一个字符后标签彻底消失，用户无法回头复核自己填的是什么；
    2. 低对比度灰字容易被用户误认为是「系统已经预填好的内容」而直接跳过；
    3. 长文案在小屏幕输入框内直接被截断；
    4. 对辅助技术与屏幕阅读器极度不友好。
  - **浮动标签（Float Labels）的妥协性**：虽然解决了消失问题，但动效占用空间、字体缩微后辨识度差，依然不能代替稳固的顶部标签。

#### 格式塔亲密性（Proximity）与输入框尺寸
- **间距亲密性**：
  - 标签与所属输入框的间距（`margin-bottom: 6px`）必须**显著小于**该输入框与下一个问题标签的间距（`margin-bottom: 24px`），维持至少 1:3 到 1:4 的比例差距。相等间距会导致用户无法判断标签是管上面还是管下面。
- **输入框物理宽度的示能（Affordance of Box Width）**：
  - 输入框的长度必须向用户传达预期的输入长度。
  - 严禁对所有字段机械地套用 `width: 100%`。一个 4 位的安全码（PIN）框必须只有 4-6 个字符宽；全宽的超大框会让用户产生「我是不是应该输入一篇长文」的判断焦虑。

### 5. 控件精选与下拉菜单反模式（Dropdowns & Component Selection）

#### 下拉菜单（Dropdowns / Select）的七大弊病
杰西卡·恩德斯在书中对下拉菜单提出了严厉批评，将其列为现代 UI 中滥用最严重的反模式：
1. **隐藏信息**：在点击前，用户完全看不见有哪些选项，丧失可发现性；
2. **操作繁复**：至少需要点击打开、移动滚动定位、再次点击选中三次物理动作；
3. **无法横向比对**：长下拉列表一次只能看到当前滚到的局部选项，打断记忆对比；
4. **小选项的荒谬**：只有 2~3 个选项（如性别、是否、支付模式）还用下拉菜单，纯属人为制造阻碍；
5. **大选项的灾难**：几十上百个选项在移动端触发原生滚轮，滑过头与误触频发；
6. **容易意外关闭**：光标轻微滑出下拉区域即可能导致浮层关闭，辛苦选择瞬间丢失；
7. **文字截断**：固定宽度的下拉框无法完整展示具有层级或较长描述的选项。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      恩德斯控件选型决策矩阵 (Field Selection)               │
├───────────────┬─────────────────────────────┬───────────────────────────────┤
│ 选项数量与特征 │ 推荐采用控件                 │ 绝对禁止控件                  │
├───────────────┼─────────────────────────────┼───────────────────────────────┤
│ 2 ~ 4 个互斥项│ 单选框组 (Radio Buttons) 或 │ 下拉菜单 (Select)、           │
│               │ 分段控件 (Segmented Control)│ 多选框 (Checkbox) 用于单选    │
├───────────────┼─────────────────────────────┼───────────────────────────────┤
│ 5 ~ 10 个互斥项│ 垂直排列单选框组            │ 水平折行单选框、下拉菜单       │
├───────────────┼─────────────────────────────┼───────────────────────────────┤
│ > 10 个海量项 │ 自动补全输入框 (Autocomplete│ 纯下拉菜单、纯无提示文本框    │
│ (星系/物品名) │ with Type-ahead Suggestion) │                               │
├───────────────┼─────────────────────────────┼───────────────────────────────┤
│ 连续范围/精细值│ 滑块 + 数字输入框联动       │ 纯滑块 (无法输入精确值)       │
│               │ (Slider + Number Stepper)   │ 纯步进器 (大范围调整极慢)     │
└───────────────┴─────────────────────────────┴───────────────────────────────┘
```

#### 滑块（Slider）与步进器（Stepper）的使用边界
- **纯滑块的缺陷**：滑块只适用于「探索性、对精确绝对值不敏感」的定性场景（如音量、背景模糊度）。一旦任务涉及精确数值（如生产配额、交易价格），手指或鼠标在滑块上精准选定单个数字极其痛苦。
- **三元黄金组合**：`滑块 (快速拖动大范围) + 步进器/输入框 (直接输入或微调 ±1) + 快捷预设按钮 (25%, 50%, MAX)`。

---

### 6. 流程架构与屏幕编排（Flow, Screens & Gateways）

- **问题排序心理学四法则**：
  1. **贴合心智（Follow How the User Thinks）**：按用户的生活逻辑或心智顺序提问，而非按后台数据库表的字段顺序排布。
  2. **核心先于补充（Core Before Supplementary）**：先解决主要诉求，再收集边角辅助信息。
  3. **由易入难（Easy Before Difficult）**：先问无争议、容易回答的基础问题，利用沉没成本（Foot-in-the-Door 登门槛效应）让用户建立完成动力，再呈现复杂权衡题。
  4. **亲密成组（Related Together）**：语义相关的问题通过分段标题（Section Heading）明确归类，段落间留白分明。
- **单步 vs 多步拆分决策树**：
  - **少于 10-12 个字段**：坚决保持在单屏内完成，避免用户因反复页面切换产生中断感。
  - **长表单分步（Wizard）**：按任务概念清晰切分屏幕（如 `[第一步：选择舰体] → [第二步：配置武器] → [第三步：确认能源预算]`）。
  - **进度指示器（Progress Indicators）真实性**：严禁伪造步数！若存在动态跳题逻辑，步数会增减，切勿显示固定的 `第 2 步 / 共 5 步`，改用带有阶段名称的面包屑或列表状态。
- **前后关键屏的心理保护**：
  - **网关屏（Gateway Screen）**：在复杂装配或高额交易前，设立前置说明屏：明确告知所需准备（如「需要准备：4级巡洋舰驾驶执照、至少 5,000,000 ISK，耗时约 2 分钟」），杜绝中途卡壳。
  - **检查屏（Review Screen）**：不可逆提交前提供只读汇总面板，且支持在当前屏**原地编辑（In-place Edit）**，而不是点编辑后跳回第一步重新一步一步点过来。
  - **完成确认屏（Confirmation Screen）**：给出唯一事务凭证编号、执行摘要及下一步明确指引。

### 7. 容错、校验与减负技术（Validation, Errors & Workload Reduction）

#### 遗漏差错（Omission） vs 动作差错（Commission）
- **遗漏差错**：用户漏填了必填字段。
- **动作差错**：用户填了，但超出边界、字符不合法或逻辑冲突。

#### 禁用主行动按钮（Disabling Primary Action Button）的反模式批判
- 前端界面的常见坏毛病：表单未填完整前，将「提交」按钮置灰（`disabled`）。
- **恩德斯的犀利批判**：置灰按钮是「静默的暴政」。用户填完全部内容，看着灰色的按钮陷入绝望，完全不知道系统到底嫌弃哪个字段没填对。
- **正确做法**：**保持主按钮始终可点击**！用户点击时，如果校验失败：
  1. 页面平滑滚动并将焦点聚焦在**第一个错误字段**；
  2. 该字段下方弹出清晰明确的红字建设性指引；
  3. 主按钮旁展示微型提示：`还有 2 项配置需要修正才能保存`。

#### 行内即时校验（Inline Validation）的触发时机
- **严禁提前校验（Premature Validation）**：用户刚打入第一个字母就疯狂弹红报错「格式不正确」，会引发强烈的被冒犯感与焦虑。
- **失焦校验（Validate on Blur）**：当用户输入完毕、将光标移出输入框时，再触发格式校验。
- **防抖延时（Debounced Check）**：对于必须实时联想的场景（如指挥官昵称重复检测），必须设置至少 400~600ms 的防抖，等用户停笔后再进行异步校验。
- **成功绿标克制使用**：只在复杂的格式限制项（如满足特定密码复杂度规则）成功时给予安静的绿色前馈，日常普通输入无需到处打满绿勾制造视觉干扰。

#### 宽容格式（Forgiving Format）与智能默认值
- **宽容输入**：电话、编号、代号输入框无论用户带不带空格、横线、括号，前端自动清洗去除杂质，绝不让用户为了适配系统的格式而重新打字。
- **智能预填（Pre-population）**：利用玩家历史行为、当前所处星系、默认主力舰船自动填入初始数据，玩家只需做增量确认。

### 8. 表单工程文档化：QxQ（Question-by-Question Documentation）

在专业复杂系统的工程开发中，表单绝不能仅靠设计师的原型稿随意口传。杰西卡·恩德斯提倡将 **QxQ（逐题契约表）** 作为跨职能交付的标准契约：

```markdown
| 字段属性 (Property) | 规范要求与示例 |
|:---|:---|
| **Question ID** | `mkt_order_quantity` (全局唯一业务键) |
| **Label Text** | `挂单采购数量` (中文正式文案，严禁末尾冒号) |
| **Field Component**| `NumberStepperInput` (步进器与数字输入框) |
| **Data Type** | `uint32` (非负整数，最小 `1`，最大 `999,999`) |
| **Required** | `true` (必填字段) |
| **Default Value** | `1` (或上次挂单历史记忆) |
| **Conditional Rule**| 仅在 `mkt_order_type === 'BUY'` 时激活 |
| **Inline Validation**| 失焦校验：`value > 0` 且 `value <= player.storage_free_capacity` |
| **Sensibility Check**| 若单次输入超过全星区日均流通量 300%，触发确认警告 |
| **Error Message** | `购买数量超出货舱剩余容积（当前可用容积：{cap} m³）` |
| **Help Text** | `挂单成功后，成交物资将自动转入当前空间站机库` |
```

- **QxQ 的工程价值**：
  1. **前后端接口对齐**：前端验证逻辑与后端 API 校验规则 100% 同构；
  2. **QA 确定性用例源头**：测试人员直接依据 QxQ 生成边界值、空值、非法格式自动化测试套件；
  3. **变更审计追踪**：当数值策划修改字段边界或文案时，QxQ 作为唯一的单点真理（Single Source of Truth）。

## 三、《大鲸鱼-深空放置》复杂表单与数值输入工程落地映射

将杰西卡·恩德斯的表单工程理论与《大鲸鱼-深空放置》项目深度融合，全面重塑以下四大高频交互场景：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                 《大鲸鱼-深空放置》 表单与数值交互工程落地架构              │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. 舰船装配/技能科研配置流 ──► 单列垂直对齐，就地预算前馈，失焦即时微观校验  │
│ 2. 市场交易与仓储物资转移 ──► 步进器+滑块+输入框三元联动，双向总价/结余防爆 │
│ 3. 数据编辑器 (Data Editing) ─► 严密 QxQ 契约，自动补全替换下拉，禁置灰按钮  │
│ 4. 离线挂机策略与自动化脚本 ──► 逻辑死循环合理性检查，智能安全预设推荐      │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1. 舰船装配/技能规划/科研队列等配置界面的表单流重构
- **现状痛点**：
  - 舰船配装涉及武器槽位、改装件、计算力（CPU）、动力栅格（PG）、校准值消耗等海量配置。旧界面常采用左右两列混杂折叠面板，玩家装上模块后，只有在点击最底部的「保存配置」时才弹出刺眼的红字拦截「CPU 超限 12 MW」，迫使玩家重新逐个排查是哪件装备超额。
- **恩德斯表单落地规范**：
  - **单列垂直动线与模块化卡片**：
    - 配装流程按 `[高槽火力] → [中槽推进/防御] → [低槽装甲/辅助] → [改装件/无人机]` 严格自上而下单向排布；
    - 废弃多层级折叠抽屉嵌套，槽位状态与已装载模块一目了然。
  - **即时行内前馈（Inline Feedforward）**：
    - 装备悬停或被拖选的毫秒级瞬间，在页面侧栏或顶部**直接模拟高亮能源预算变化**：`CPU: 320/350 (+45 ⚠️ 超限)`，让用户在物理点击前就完成认知决策（Judgement）；
    - 若前置技能等级不足，在装备选择列表的题干旁就地显示建设性文字：`需要 [中型能量炮台操作理论 III]（还差 4小时12分）`，不让用户装上后再承受报错挫败。

---

### 2. 市场交易、仓储转移与批量生产的数值输入
- **现状痛点**：
  - 在星系市场挂单、向旗舰转运矿石、或军工制造厂批量建造护卫舰时，数值经常在数百到数千万之间跨度极大。很多界面仅提供纯滑块，鼠标轻微晃动就会在 1,000 与 100,000 间剧烈漂移；或者只提供裸文本框，玩家手滑多打一个零导致倾家荡产买下天价物资。
- **恩德斯表单落地规范**：
  - **三元联动组件（Stepper-Slider-Input Trio）**：
    - **数值微调步进器（Stepper）**：提供 `[-10] [-1] [数值框] [+1] [+10]`，支持小规模精确微调；
    - **非线性对数滑块（Logarithmic Slider）**：在大范围变动时，滑块刻度采用对数分布，前半程细腻微调，后半程迅速推进至最大值；
    - **快捷百分比分段胶囊**：`[25%] [50%] [75%] [最大 (MAX)]`，一键满足玩家最常见的心智模型。
  - **双向联动结算计算器（Bi-directional Real-time Feedback）**：
    - 输入数量，右侧实时显示：`总计花费: 4,500,000 ISK`、`交易税: 45,000 ISK`、`账户结余: 12,300,500 ISK (剩余 73%)`；
    - 输入预期投资金额，反向自动算出可采购的精确最大物资数量；
    - 当采购量超出当前驻留空间站机库体积（`Storage Limit`）时，输入框即时呈现琥珀色警告（而非红字打断），并在下方提示：`物资将分流至临时租用货柜（每日租金 2,000 ISK）`。

---

### 3. 数据编辑器（`tools/data-content-editing`）中海量装备/物品条目的配置表单防错
- **现状痛点**：
  - 游戏数据内容编辑是高频且极度枯燥的工程任务。旧配置界面经常出现长达数百行的超长原生下拉菜单（Select）让策划挑选前置技能 ID，稍微手抖就选错；且保存按钮常年在校验不通过时置灰，策划常常抓狂：「为什么保存按钮还是灰的？到底哪个字段格式错了？」。
- **恩德斯表单落地规范**：
  - **全面剿灭原生下拉菜单**：
    - 凡是选项超过 5 个的字段（如 `item_id`、`required_skills`、`hull_type`），彻底废除 `<select>`，全面改用**带防抖索引与拼音/英文检索的自动补全组件（Type-ahead Autocomplete）**；
    - 选项输入框支持模糊查询与分类标签高亮（如打入 `巡洋` 自动联想出所有巡洋舰级舰体）。
  - **拒绝置灰保存按钮，实行智能聚焦滚动**：
    - 保存按钮保持始终激活；
    - 点击若未通过校验，编辑器平滑滚动并将焦点（Focus）置于第一个非法字段，弹出红框与具体修复建议（如：`校准值消耗 (Calibration) 不能超过该舰体上限 400 点`）；
    - 顶部信息条展示错误清单统计：`存在 2 处配置错误，点击可直接跳转定位`。
  - **全面落地 QxQ 架构**：
    - 在 `packages/data/` 与编辑器之间建立共享的 schema 验证定义，确保前端编辑界面与游戏运行时引擎共享单一校验规则。

---

### 4. 离线挂机策略与自动化脚本设置表单的容错
- **现状痛点**：
  - 放置类游戏允许玩家配置复杂的离线循环策略（如自动采矿航线、护盾过低撤退阈值、无人机索敌模式）。玩家由于理解偏差，经常配置出自相矛盾的死循环脚本（例如：将「回港维修护盾阈值」设为 95%，而「脱战重新出击阈值」设为 90%，导致舰船刚飞出星港就立刻折返，挂机一整晚毫无产出）。
- **恩德斯表单落地规范**：
  - **合理性检查（Sensibility Checks）与逻辑互锁**：
    - 表单字段之间建立交叉依赖关系校验。当 `回港阈值 >= 出击阈值` 时，不等待保存，直接在两字段间以黄色连线呈现逻辑警示：`警告：回港护盾阈值 (95%) 不得高于出击阈值 (90%)，否则将导致战舰无限折返`；
    - 自动提供一键「修复并使用推荐差值（回港 30% / 出击 100%）」快捷修正按钮。
  - **场景化智能预设（Smart Defaults）**：
    - 表单顶部提供三大经典模式一键切换：`[稳健采矿模式] [极限掠夺模式] [逃生防爆模式]`；
    - 玩家选择预设后，下方具体参数自动填入经过数学验证的最佳平衡值，玩家只需针对微小偏好做个性化微调。

## 四、表单体验与防错设计审查清单（Form UX Checklist）

在交付任何涉及玩家输入、配装配置或后台数据录入的表单时，严格按照以下 20 条黄金审查清单逐项验收：

| 维度 | 审查项目 | 合格标准 | 状态 |
|:---|:---|:---|:---:|
| **关系** | 1. 必填字段克制性 | 绝不索取与当前交互目标无关的冗余数据 | [ ] |
| **关系** | 2. 隐私与后果前馈 | 敏感操作或涉及资产消耗时，提前明确告知扣除明细 | [ ] |
| **对话** | 3. 语言通俗性 | 消除内部系统代码与生硬黑话，完全采用玩家视角专业词汇 | [ ] |
| **对话** | 4. 动宾行动按钮 | 按钮文案采用具体动宾结构（如 `保存装配`），废除 `确定`、`Submit` | [ ] |
| **对话** | 5. 无人称代词泛滥 | 标签尽量剔除「你的/我的」修饰，保持界面清爽 | [ ] |
| **对话** | 6. 建设性报错 | 错误提示必须包含「发生何事 + 为何发生 + 如何解决」三要素 | [ ] |
| **外观** | 7. 单列垂直路径 | 全流程单列自上而下对齐，杜绝无意义的多列视线折返 | [ ] |
| **外观** | 8. 顶部标签排布 | 标签统一部署在输入框正上方，末尾严禁添加冒号 `:` | [ ] |
| **外观** | 9. 坚决不用 Placeholder 替代 Label | 输入框外必须保留永久可见的真实标签文本 | [ ] |
| **外观** | 10. 间距格式塔亲密性 | 标签与所属输入框间距显著小于到下一题的距离（至少 1:3） | [ ] |
| **外观** | 11. 输入框尺寸暗示 | 输入框宽度与预期输入的字符长度保持物理直觉一致 | [ ] |
| **外观** | 12. 彻底移除 Reset 按钮 | 绝不在界面放置容易手滑清空全屏的「重置/清空」按钮 | [ ] |
| **控件** | 13. 下拉菜单禁令 | 选项 ≤ 4 个必须使用单选框组或分段控件，禁止使用下拉菜单 | [ ] |
| **控件** | 14. 海量数据自动补全 | 选项 > 10 个（如物品/星系列表）必须提供带防抖的搜索自动补全 | [ ] |
| **控件** | 15. 数值输入三元联动 | 精确数值调整必须同时提供输入框、微调步进器与快捷比例 | [ ] |
| **流程** | 16. 由易入难与逻辑成组 | 核心与易答问题排在前面，相关题目使用分区标题归类 | [ ] |
| **流程** | 17. 拒绝置灰主按钮 | 校验不通过时主按钮不置灰，点击后平滑滚动并聚焦首个错误项 | [ ] |
| **校验** | 18. 行内校验时机合适 | 严禁提早弹红报错，统一采用失焦（Blur）校验或延时防抖校验 | [ ] |
| **校验** | 19. 宽容格式清洗 | 系统自动过滤用户输入的空格、破折号及多余字符，不报错刁难 | [ ] |
| **契约** | 20. 核心表单具备 QxQ | 复杂业务表单（交易/配装/数据编辑）在代码中具备完备的 Schema 契约 | [ ] |
