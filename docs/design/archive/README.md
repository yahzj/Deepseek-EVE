# 归档区说明（docs/design/archive/）

> 本目录存放**已结案的公告待审稿**与**历史交接卡**。它们仍属 `docs/` 权威的一部分，可随时回查；
> 只是不再需要在一线目录里与在办设计稿混排。**本目录内的文件请勿再按"待办"对待。**

## 一、为什么在这里

`docs/design/` 直接子级一度累积 **154 份** markdown，其中相当一部分是"使命已完成、不再有后续动作"
的待审稿与交接卡。2026-09-12 船长指示「清理多余的备注和文档信息」，裁定口径：

- **构建产物**：直接删除（本就可重建）；
- **多余文档**：**移入本归档目录，不删除**（保留 git 历史与可回查性）；
- **源码注释**：不动（注释记录的是"为什么这么取值"的设计依据，且不在玩家可见范围）。

## 二、归档判据（两条任一命中即归档）

1. **公告待审稿**：顶部已有船长显式批复（已写入公告数据 / 船长明判"不发" / 整体作废）⇒ 使命已完成。
   > **例外**：`announcement-draft-20260912-*.md` 两份虽已作废，但属**当日终局裁定**（船长
   > 「清理剩余待审稿，不发」），近期还可能与"要不要重发"挂钩 ⇒ **留在 `docs/design/` 一线**。
   > 另**在一线目录没有"生效待审稿"这一说**——公告的唯一权威是 `packages/data/src/announcements.ts`。
2. **交接卡**：仅保留**最新一份**（一号与二号各一）；被它取代的历史交接卡一律归档。


## 五、要取回某一份怎么办

```powershell
# 取回一线（恢复为在办状态）
git mv docs/design/archive/<文件名> docs/design/<文件名>
git commit -m "chore(docs): 取回归档件 <文件名>"
```

归档只是移动，**git 历史完整保留**：`git log --follow docs/design/archive/<文件名>` 可查到改名前后的全部提交。
