## 追加定位：ui.MapPage.006 原样泄漏

船长进一步记忆：「是ui.mappage.006好像」。现场核对实际id为 `ui.MapPage.006`，词条存在，中英为「长途运输」/ `Long-haul transport`；没有发现这个入口用错大小写。

- **已复现**：长途运输 active，调用真实 `gateMainActivity(state, 'mining')` 得到首击确认警告；把真实判据字段按现有命令结构交给真实 `cmdText`，中文输出为 `ui.MapPage.006进行中：切换会中断它——本段报酬拿不到（报酬到站才结）。再点一次即确认：自动停止并开始新活动。`；英文也原样保留 `ui.MapPage.006 is running: ...`。
- **根因**：activityGate 的 `ACTIVITY_LABEL_ID.hauling` 合法复用 `ui.MapPage.006`；`messageParams.p1Id` 带着这个id。`resolveParamIds` 使用 `paramText`，而 `paramText` 只判断 `startsWith('core.')`，把 ui 域id当作普通文字并覆盖原本完整的 `p1` 活动名。
- **接线**：GameEngine `withActivitySwitch` 首击返回同一错误/警告；MapPage 等入口通过 `onToast(cmdText(r))` 输出。日志使用另一套 `composeParts` 的查表步骤，既有日志夹具通过并不能覆盖该操作提示缺口。
- **同族**：`ACTIVITY_LABEL_ID` 另有 mining/salvaging/wormholeScan 复用 ui 域词条，应检查所有活动的命令提示与参数，不只硬修运输字符串。部分活动会直接自动停，不一定产生首击确认警告，不能冒称所有这些id都在相同场景漏出。
- **建议修法**：显式 `p{n}Id` 指向的词条按唯一表取词，不用 `core.` 前缀猜是否为合法id；保持原始文本参数和不存在词条的现行兜底，不把任意普通文本当id翻译。增加真实活动确认/拒绝→cmdText的中英测试，保留运输两次确认、处罚/报酬、停机和存档规则。
