## 一、结论：这条 bug 有**两半**，缺一半都还会犯

| # | 位置 | 病根 | 修法 |
|---|---|---|---|
| ① | `core/wormholeSalvage.ts` `wormholeSyncMatterTurns` | 夹紧是**单边**的：上限变大一律 `turnsLeft += delta`，上限变小时却只在"剩余 > 新上限"时才夹 ⇒ **一趟"出仓再回仓"净赚 +10**，来回拖就能把花掉的回合整段刷回来（弱化成"每次花完都能刷满"） | 一律按「**已花费 = 上限 − 剩余**」反推新剩余 ⇒ 同一趟局面无论怎么走到这儿结果都一样（真正幂等） |
| ② | `core/save.ts` 洞内趟的清洗器 | 它是**逐字段重建**的，`turnsBase` / `turnsTechBonus` **没登记** ⇒ **每读一次档就丢一次回合账本锚**；丢了之后同步器只能在"第一次同步那一刻"现推基础预算——那一刻装置若正好被拖在临时空间（不在货仓），推出来的基础预算就**凭空多 10 回合**，回到货仓再按"上限变大"补一次 | 两个字段按"是不是有限数"登记进重建表（**0 也合法**，不用 `> 0` 判） |

**为什么②是主因**：只要读一次档（进游戏 / 刷新 / 读档）账本锚就没了 ⇒ **任何人**都能复现，
不必是老档；而且它把①的漏洞从"每次花完刷一次"变成"**拖出去再拖回来就 +10**"——正是船长看到的「来回拖会重复加回合」。
（这与同文件 `attending` 那条注释记的是同一类事故：手抄白名单漏登记 = 字段静默丢失。）

## 二、复现（先红后绿）

  然后"货仓 → 临时空间 → 货仓"各 3 个来回，逐趟断言上限与剩余都回到起始那一对值。
  - 修前：`expected 52 to be 47` —— 第 1 趟就把花掉的 5 回合整段刷了回来（再花再刷 = 无限回合）。
  - 修后：✅ 全绿。
- **⑤c `turnsBase / turnsTechBonus 随档往返`**（新）：同步一次让账本落地，`serializeSaveFile` → `loadSaveFile`，
  断言两个字段还在、值不漂、再同步一次上限与剩余一字不动。
  - 修前：`expected undefined to be 42` —— **读档把账本锚丢了**。
  - 修后：✅ 全绿。

### 2.2 真界面探针（`npm run wh:turn`，真档 `test-save-wh-all-20260914-122105.json`）

装档 → 出港 → 扫描虫洞 → 返回虫洞 → 货仓页 → 点选 + 落格（与拖拽同一条 `dropAt → wormholeBoardTransfer`），
把「时序核心」在货仓 ↔ 临时空间之间来回搬 3 趟，每趟读**界面回合行**与 **localStorage 存档**两处：

| | 修前（只剩①未修时的现象见单测；②未修时） | **修后（实测）** |
|---|---|---|
| 起始 | 回合 39/39 | 回合 39/39 |
| 出仓（货仓 → 临时空间） | 39/39（没掉） | **29/29**（上限与剩余各 −10） |
| 回仓（临时空间 → 货仓） | 49/49（**+10**） | **39/39**（净零） |
| 重复 3 趟 | 每趟回仓都 +10 | **3 趟全部净零（相对起始 +0）** |

⇒ 修后行为：**装置离开货仓，本趟上限与剩余一起 −10；放回来，一起 +10；来回多少趟都回到原值。**

## 三、⚠ 与既有裁定的一处出入（请船长确认）

`wormholeSyncMatterTurns` 里 2026-09-13 那版注释写的是「上限**变小**（丢掉了装置）⇒ 剩余**夹到新上限**、
**永不为负**；**不追缴**已经花掉的回合」。本次把"变小只夹紧、剩余原样不动"收严成"**已花费守恒**"：

- 不变的三条：上限变大 ⇒ 剩余同样多给这么多（捡到就真能多走几步）✔；变小后永不为负 ✔；撤离不看回合、不会软锁 ✔。
- 收严的一条：变小之后剩余**跟着减**（而不是"只要没超过新上限就不动"）。
- **为什么非收不可**：「来回拖不刷回合」与「变小不追缴（剩余原样不动）」**二者不可兼得**——
  上限掉下去时剩余不动、涨回来时又加一遍，那个差额就是白刷出来的回合。
