## 2. 船长的工作方式（今天新增的经验）

**四步闸门**（触发：新大功能/系统级/存档结构、涉及设计取舍或数值体系、需求模糊）：
集中提问（一次问完 + 给选项与推荐）→ **中文设计总结**（结尾写「请确认」）→ **等显式确认**（「可以/没问题/确认」才算）
→ 确认后实现并把决策落进 `docs/design/…`。

**今天的实战经验（都真实发生）**
1. **他会用选项标签作答**（「甲」「乙」「丙」「按推荐来」）——所以提问时要**把选项写成可执行的具体方案**（含数值与影响面），
   他一句话就能定；**给了示例数值不等于他确认了具体数值**，落码前把最终值在汇报里单独列出。
2. **他会连续改口**：今天对同两件事先说「归档」、随后更正「**说错了，2 和 3 消档**」。
   ⇒ **以最新一句为准**，并把前一次动作**撤回**（未推送的本地提交可直接 `git reset --hard HEAD~1` 后重做）。
3. **「归档」≠「消档」**：归档 = 留档并标注不作；**消档 = 从台账里删掉、不再出现**。用词要问清或按最新口径执行。
4. **玩家反馈是最高优先级的输入**：今天 4 条玩家反馈全部查出真问题（2 条是我们自己引入的回归）。
   ⇒ 接到反馈先**在真引擎里取证**（读数 + 复现），再给方案；他会追问数。
5. **他会让你"先不退/先不推"**：推送是独立闸门，**只有他说推才推**。
6. **数值他给的就是结论**（如「单发提高，因为射程更短威力应该更高」）——按此定标，不要自行打折。

## 10. 已知坑与教训（今天全部真实踩过）

1. **`edit` 工具会吞掉文件 BOM**：改完 `apps/desktop/src/renderer/src/game/engine.ts` 后 diff 首行出现 BOM 变更
   ⇒ 用 node 按字节补回（`Buffer.concat([BOM, buf])`）并复查 diff。**改 UTF-8 文件后必查 BOM/行尾**。
2. **PowerShell 改源码会把文件毁掉**：`(Get-Content …) -replace … | Set-Content -NoNewline` 把整个 `.ts` 挤成**一行**，
   `tsx` 直接语法报错。⇒ **改文件一律用写/编辑工具或 node 脚本**，中文盘写入用 .NET 显式 UTF-8。
3. **roadmap 插入必须按"行锚点"**：用 `text.indexOf('## 变更记录（本文件）')` 会撞到**文内出现的同名字符串**，
   今天的推送回执就被插到了第 87 行（中段）。⇒ 先 `split(/\r?\n/)` 再 `findIndex(l => l.startsWith(...))`。
4. **文档批量写入三自检**（约定 §三）：BOM/行尾与改前一致 · 全仓往返解码**乱码 0** · 父提交有的行还在。
   今天每次写文档都跑了自检，**有两次因为"行数增量写错"而中止**——脚本里把预期增量写准（或按实际改动数传参）。
5. **写完必自查玩家可见文案**：`content:check` 的「产物说明契约」会核对说明里的数值声明——
   今天改近防炮伤害时，三档说明文同批改写（旧文「威力远不如主炮」已不成立）。
6. **旧条款冲突要走 §5.2**：改数值前先找文档里的旧口径（今天命中 `foe-drone-system-20260911.md` §六 的
   「单发 = 同档主炮的 ~40%」），实现时**就地标注作废 + 追加新口径小节 + 词典登记**。
7. **既有用例会因数值改动失效**：今天 `foe-drone.test.ts` 的「必须有存活补位机」断言在近防炮变强后失效
   ⇒ 按新口径改写断言（**去掉与数值绑定的隐含前提，机制断言不放松**），并在注释里写清原因。
8. **探针纪律**：临时探针 `_` 前缀、收尾删除（今天建了 10+ 个，全部在提交前删净）；
   有复用价值的转正式工具并挂 npm script。
9. **别用错字段名**：今天一度读 `b.outcome` 得到"未决"，其实引擎写的是 **`b.ended`**（`'me' | 'foe' | null`）
   ⇒ 读数前先确认字段名，别把探针 bug 当成引擎 bug 上报。
