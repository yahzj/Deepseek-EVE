> 「**检查游戏之前有多少旧存档迁移的机制**」⇒ 盘点后指示：「**删除过旧的版本迁移，仅保留虫洞之后的。
> 假如之后玩家的存档版本过旧，则提示玩家新开一个存档。**」

| 问 | 裁定 |

| 老档 fixture 与体检工具 | 清 `docs/test-saves/` 里 v<24 的档，**留 1 份最老的做"应被拒"反证**；`save:migrate` 口径同步 |
| 类型阶梯 | **保留 `GameStateV1..V23`**（当前类型的基座，只删迁移函数） |
| 旧迁移用例 | 删旧断言，**改留两条钉子**（v24 可读 / v23 拒载入） |

## 二、盘点结论（动手前）

- 迁移链原来 **28 级**（`MIGRATIONS` key `0..27`）：`v0→v1` … `v27→v28`；类型阶梯 `GameStateV1..V28`（V17 缺号）。
- 配套机制另有五类：**零迁移兼容字段**（core 内 153 处标注）· **运行态登记表**（18 条 `kind: runtime`）·
  **归一化/清洗助手**（18 个）· **改名/折算映射表**（3 张）· **一次性老档判定**（1 处：v26）。
- **拒载入的通道早已存在**：`save.ts` 取不到迁移脚本时抛 `SaveError('VERSION')`，
  `engine.start()` catch 后开新档并写日志（旧档文件原样保留、不覆盖）。
- 校验侧有 `npm run save:migrate`（`tools/save-migrate-check.ts`）扫 `docs/test-saves/` **全部各代真档**。

## 四、边界与影响面

- **v23 及更早的真实老档从此读不进来**：表现 = 启动开新档 ＋ 一条日志；**旧档文件原样留在盘上、不覆盖**。
- **历史备份/导出档**若为 v23 及更早 ⇒ 恢复备份会失败。
- **零玩法/数值改动**；当前档（v28）不受影响。
- 保留四级一次性老档折算：v24→v25（虫洞状态）· v25→v26（「第一次」判定）· v26→v27（市场链）· v27→v28（残骸并组）。
