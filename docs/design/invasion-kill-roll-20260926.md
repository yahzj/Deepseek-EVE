## 二、玩家真正的损失：**没有抢到最后一下**那一档

船长 2026-09-25 定的爆率表（`weekendBlackBoxChanceOf`）：

| 情形 | 爆率 |
| --- | --- |
| 抢到最后一下 ＋ p > 50% | **100%** |
| 抢到最后一下 ＋ p ≤ 50% | 100% → 10% 线性 |
| **没抢到最后一下** | **25% × p** |

该玩家 p = 97.75% ⇒ 爆率 = **24.438%**。**按同一条确定性子流重算，那一掷是 0.015648 < 24.438% ⇒ 本该命中**
（本该拿到 1 个黑匣）。

## 三、真根因：**这一掷根本没有发生**（我们的 bug）

`weekendRollBlackBox` 只在**公开收口** `weekendEvent.weekendTick` 的"章鱼得手"分支里被调用；
而**引擎每拍走的是另一个收口** `weekendTickBoss`（`engine.advanceGame` → `weekendTickBoss`，
2026-09-26「章鱼人冷却 60 秒」那批新加的第 4 参闸就在它里面）。那个分支里**没有掷骰**：

```
if (weekendOctopusTick(state, ev, dt, inBattle)) {
  ev.flagshipDown = 'octopus'
  endWeekendEvent(state, nowWallMs)   // ← 原先这里漏了 weekendRollBlackBox
  return { down: 'octopus' }
}
```

一旦它在这里结束本场，随后公开收口 `weekendTick` 就因"本场已结束"直接返回 ⇒ **那一掷永远不发生**
⇒ `flagshipBlackBox` 缺省 ⇒ 结算补发判据 `ev.flagshipBlackBox === true` 为假 ⇒ **玩家一个黑匣都拿不到**。

**这不是个例**：引擎心跳里"章鱼把血条削空"这一类**全部**走本收口 ⇒ 所有"母舰被章鱼收走"的场次
都丢了这一掷（玩家按规则该得的黑匣被吞）。报障玩家只是其中一例，而且他的那一掷**本该命中**。

## 四、已修（本次落码）

`weekendEvent.weekendTickBoss` 的"章鱼得手"分支补上 `weekendRollBlackBox(state, ev, false)`（与公开收口
逐字同款，掷骰本身幂等、走同一条确定性子流）⇒ 掷中时结算会照旧补发黑匣（`boxAtSettle` 那条路）。

**新增用例 2 条**（`octopus-hold-20260926.test.ts`）：⑧ 章鱼得手必须留下掷骰结果；⑧b 与公开收口同源、

## 六、另一个可选项（机制，不动为默认）

本场玩家 97.75% vs 章鱼 2.25%，最后 1 点血被章鱼收走 ⇒ 体验上"打了 97% 却算章鱼击沉"。
若船长认为该改，可选：
- **甲**：章鱼只有削掉 ≥ 总血量的某个比例（如 50%）才允许认领击沉，否则血条清空仍记玩家击沉；
- **乙**：保持归属，但"没抢到最后一下"那条爆率在 p 很高时抬起来（如 p ≥ 90% 必爆）；
- **丙**：延长停工时间（60 秒 → N 分钟）或只在玩家离线/长时间不接战时允许章鱼收尾；
- **丁**：不改机制，只补提示（界面写明"章鱼将在 X 秒后恢复削血"——当时那批船长明令"不做界面/倒计时改动"）。
