## 五、技能树排布：多前置合流的裁决与落实（船长选「乙」）

### 原始冲突（读数）

```
✗ b-warship 没挂住：装甲舰操作 的子（护卫舰操作、驱逐舰操作、巡洋舰操作、战列操作）没有一个在它正下方
✗ b-warship 往回长：护卫舰操作（x=84）跑到了前置 装甲舰操作（x=548）左边
✗ b-warship 往回长：驱逐舰操作（x=200）…
✗ b-warship 往回长：巡洋舰操作（x=316）…
✗ b-warship 往回长：战列操作（x=432）…
```

### 根因（结构上不可能同时满足，不是排布参数没调好）

这四条技能是**全仓第一批「同一本书内两条前置」的节点**。体检的两条口径（`tools/skilltree-layout-check.ts` ③）是：**3a 挂得住**（每个有子的节点至少有一个子落在它正下方）＋ **3b 不回头**（子不许跑到父的左边）。

设两个父列 `pA`（武装舰操作）< `pB`（装甲舰操作）。共享子要"挂得住"给 `pA` ⇒ 必须有一个子在 `pA` 列；但 3b 要求**每个子** `x ≥ pB` ⇒ `pA ≥ pB`，矛盾（对 `pB` 同理）。**一列只能承一个父 ⇒ 两条边不可能同时满足 3a＋3b。**

### 三案与裁决

| 方案 | 做法 | 结果 |
| --- | --- | --- |
| 甲 | 算法「共享子轮流承父列」＋体检只判"承父边" | 未采纳 |
| **乙（船长选）** | **数据与排布算法都不动，只给体检加多前置豁免** | ✅ 已落实 |
| 丙 | 前置只留一条 | 未采纳（须推翻「两条都要 Lv1」的原裁定） |

### 落实内容（`tools/skilltree-layout-check.ts` ③ 段）

- **共享子** = 本图内有 **≥2 个更浅前置**的节点（本批四条）；
- **一个父的子若全是共享子 ⇒ 不判它 3a、也不判这些边的 3b**（此刻这些边是"汇流线"，子承的是另一个父的列）；
- **但整族不能都不落地**：若这一族共享子没有一条"向下生长"的边（存在某父与某共享子同列），仍报「没挂住」；
- **独占子（本图内只有一个父）照旧严格判** ⇒ 单前置的书与改动前**逐字一致**。

## 六、已知取舍

- **乙 的代价**：子全是共享子的父不再判"挂得住"（该父的落位正确性由"整族至少一条边向下生长"兜底）⇒ 这一族的排布信号比单前置的族弱一档。
- 舰种操作在 `createPlayerSpec` 内取 `ship.tier` ⇒ **只影响主控在驾的那艘**；副船 / 无人机不吃（与船长裁定一致）。
- `tierResistLv = max(巡洋舰操作, 战列操作)`：一艘船只有一个舰种，两者至多一条非零，取 `max` 与"逐层判断"等价。
- 炉温精调学的钳制与炉心熔炼学不同：前者 `max(0, …)`（不会被自身的下限截断），后者保留既有 `max(0.6, …)` 口径 —— 两条叠乘后周期下限仍由既有代码兜住。
