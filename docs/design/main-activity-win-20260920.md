## 关键技术口径

- **窗口内 `vw` 问题**：战斗屏内层有 `clamp(420px, 52vw, 780px)`（标尺 / 底栏）与 `padding: 6px 4vw`——全屏时 `vw` 即窗口宽，窗口化后必须改为按窗口算。**只覆盖这四处**，且在 `.app-winbox` 作用域内，不动全局规则。
- **窄窗横滑**：战斗屏的手机段口径（`@media (max-width: 640px)`）改为**按容器**生效（`.app-winbox` 窄时舞台横滑、底栏适配宽度），因为窗口宽度与视口宽度无关。
- **z 序**：窗口 110（低于详情窗 120 / 140 与悬浮说明 1000，高于浮动还原标 90 与公告 88）。
- **弹窗与最小化**：照抄战斗窗口既有机制（`xxxOpen` state + 活动上升沿自动弹出一次 + 手动最小化后不再自动弹回）。

### 动画是否"真的在跑"的核验（2026-09-20 第二轮）

"几何对"不等于"动画跑起来了"——CSS 类名写错、`animation-name` 没接上，画面就是死的。故探针
新增三项**逐场景**诊断：演出 SVG 在不在、`app-act-*` 元件几个、每个动画类的 **computed
`animation-name`**（`none` ⇒ 没跑），以及进度条宽度。五个夹具实测：

| 场景 | 演出 SVG | 元件 | 真在跑的动画类 | 进度条 |
|---|---|---|---|---|
| 采掘中 | 有 | 14 | flame · beam · chip | 54% |
| 打捞中 | 有 | 14 | cone · beam · arc · chip | **67%**（本轮新补） |
| 长途运输中（承运） | 有 | 14 | haulbody · flame · trail | 27% |
| 长途运输 · 就位中 | 有 | 15 | haulbody · flame · trail · echo | 1% |
| 扫描虫洞中 | 有 | 14 | array · wave · echo | 6% |

**本轮据此补掉两个真缺口**：
1. **打捞原本没有进度条**（实现里写成 `progress: null`）——而船长第 3 条明确要求"进度条也显示"。
   打捞以**最短打捞器周期**为统一推进步（`salvaging.ts`：多台各自维护相位）⇒ 进度 =
   `cycleAccMs / min(salvagerCyclesOf(...))`；出航/返航段不显示循环进度（那两段是航行）。
   同时补两行读数（打捞器台数、推进步长）。
2. 采掘/承运/扫描三态的进度条与读数**当场取了真值**（54% / 27% / 6%），确认不是死值。

另附三张全窗口截图于 `tools/_ui-artifacts/shots/actwin-*.png`（**可重建、不入库**）——
**只用于船长观感审查**，不作为"已完成"的证据。

**已知取证边界（如实标注）**：
1. **战斗窗口壳量的是同构元素**（生产类名 `app-winbox is-battle` + 壳内两层），不是实弹交火——
   仓里没有 `phase==='battle'` 的档，且 `combatView` 由引擎在真交火时给出、伪造不出来。
   量的是真 CSS 尺寸与居中，但"真交火下窗口里内容是否正常"**尚未取证**。
2. **采掘夹具是现场改档造的**（`user-backup-20260920-102449` 点开采矿作业）——因为仓里的采掘档
   （`test-save-b1-*` 等）是 v1x 老档，`loadSaveFile` 判失败会回落新档，测不到"采掘中"。
3. **离线结算会把老档推进到不同状态**：夹具档距今数日 ⇒ 载入即跑一大段离线结算，窗口要等渲染完
   才出现（探针因此把等窗口上限设为 8s、并在诊断里打印游戏时钟以区分"窗口有问题"与"夹具没载进去"）。
4. **动画频率与观感未做主观判定**：本轮只核"动没动"（`animation-name ≠ none`），没有、也不该由
   我判"动得好不好看"——那是船长的观感审查。另外扫描进度以**12 小时窗口**为分母，10Hz tick 下
   每帧涨幅极小 ⇒ 进度条**肉眼几乎不动**（数字与场景动画仍在动），若船长觉得该更"有感"，
   可改为按小时分格或加环形进度，属观感取舍、等船长裁。
