## 关键技术口径

- **窗口内 `vw` 问题**：战斗屏内层有 `clamp(420px, 52vw, 780px)`（标尺 / 底栏）与 `padding: 6px 4vw`——全屏时 `vw` 即窗口宽，窗口化后必须改为按窗口算。**只覆盖这四处**，且在 `.app-winbox` 作用域内，不动全局规则。
- **窄窗横滑**：战斗屏的手机段口径（`@media (max-width: 640px)`）改为**按容器**生效（`.app-winbox` 窄时舞台横滑、底栏适配宽度），因为窗口宽度与视口宽度无关。
- **z 序**：窗口 110（低于详情窗 120 / 140 与悬浮说明 1000，高于浮动还原标 90 与公告 88）。
- **弹窗与最小化**：照抄战斗窗口既有机制（`xxxOpen` state + 活动上升沿自动弹出一次 + 手动最小化后不再自动弹回）。

### 船长实测报障（2026-09-20 · 两条）

船长原话：「我测试了，发现了几个疑点，退出战斗的按钮有2个，而且说是退出战斗其实不准去，应该是最小化
战斗窗口。其次敌人血条明显短于我方血条。」

**① 两个"退出"按钮 —— 已修（真因 = 我套壳时漏删）**
`ui/WinBox.tsx` 的顶栏本来就会渲染一枚最小化按钮，而战斗屏**自己顶栏里也有一枚**
（`.app-battle-screen-top` 最左那枚），两枚并排 ⇒ 船长看到 2 个。修法：给壳加
`showMinimizeButton`（缺省 true），战斗屏传 `false`（保留它自己那枚，因为它旁边还有"洞内不给撤退"
的同伴说明）。
**文案同时改口径**（船长："说是退出战斗其实不准确"）：`ui.BattleScreen.037` 由
「← 退出战场 / ← Leave battle」改为「← 最小化 / ← Minimize」；`ui.BattleScreen.105` 的悬停说明
也改成明确写"**不中止战斗**，它照常在后台推进"。全仓玩家可见文案里已无"退出战场/离开战场/Leave battle"。

**② 敌人血条短于我方 —— 已定案并修复**（船长回话：「是情况1」，并把交火档导出在主树
`save-20260921-201652.json`）

真因（用**真交火档**在无头浏览器里量出来的，不是纸上推演）：
- 敌舰那根条挂在 `.app-bts-unit`（`display: inline-flex`）里，而**该单位的宽度就是舰影那一百来像素**；
  内联style 给的 `width: 185px` 被 `.app-bts-hpWrap` 的 `max-width: 100%` **夹到了父单位宽**。
- 实测对照（同一战场、同一时刻）：
  | | offsetWidth（布局宽） | rectWidth（视觉宽） | css width | inline |
  |---|---|---|---|---|
  | 我方主控 | 185 | 185 | 185px | — |
  | 敌方单位 | **110** | **89** | 110px | `width: 185px` |
- 我方那根在 `.app-bts-col` 里、父宽足够 ⇒ 一直是 185；两者并排看就是"**敌方短一截**"。
  （`rectW=89` 那一截还叠了入场动画 `app-bts-foe-in` 的 `scale(.8)`，动画跑完回到 185 的布局宽。）

修法（最小改动）：`.app-bts-unit > .app-bts-hpWrap.is-unitBar { max-width: none }`——舰下那根条
**不再参与父宽夹取**。它的宽度本就由 `foeBarGeom` 按**同排间距**逐舰算好（拥挤时会收窄或整排竖排
堆叠），不需要再用父宽兜一层。

修复后实测（同一份真交火档、入场动画跑完的稳态）：
| | offsetWidth | rectWidth |
|---|---|---|
| 我方主控 | 185 | **185** |
| 敌方单位 | **185** | **185** |
⇒ 两侧等宽，报障消除。

**顺带作废的一处猜测**：先前删掉的 `.app-bts-col.is-foe .app-battle-hp:not(.is-big) { width: 280px }`
**与本案无关**（它被 `.app-bts-hpWrap` 的 185 覆盖、从未生效），CSS 里已写明删除理由。

**取证素材**：船长导出的交火档已复制进本工作树 `docs/test-saves/save-20260921-201652.json`
（主树原件未动）；探针在测量时**改副本**把交火窗口往后推（原档 `finishAtGameMs < gameMs`，
离线结算第一 tick 就会结算掉那场训练战）。

原实现拿**整窗口**当分母，而窗口基准 12 小时（还要吃技能与谜质科技的削减）、tick 是 10Hz
⇒ 每帧进度只涨 0.0002%，**条子实际上是死的**（玩家看到的是一条不动的槽）。

改为：**进度条 = 当前这一小时的完成度**（每小时扫满一次、条子扫过一遍），整窗的绝对进度由
**读数如实给出**（`本次进度：x.x h / y.y h（z%）` + `还剩约 n 小时扫满`）。
⇒ "条子在动"与"数值可信"两件事都有：条子负责动感，数字负责真相。
实测：同一份夹具的扫描条由 **6%（且不动）→ 24%（且会走）**。

这是**我在"观感"边界内做的最小动作**——没有改任何玩法数值与进度语义，只改"这条子画的是哪一段
区间"；若船长认为该显示整窗进度（哪怕几乎不动），一句话就能改回去。

1. **战斗窗口壳量的是同构元素**（生产类名 `app-winbox is-battle` + 壳内两层），不是实弹交火——

   每帧涨幅极小 ⇒ 进度条**肉眼几乎不动**（数字与场景动画仍在动），若船长觉得该更"有感"，
   可改为按小时分格或加环形进度，属观感取舍、等船长裁。

### 两层动画口径（"跟真实进度挂钩"怎么落）

- **动感层**（激光闪烁 / 碎屑回流 / 牵引锥呼吸 / 航迹拖尾 / 扫描波外掠，固定短周期）：负责"在动"，
  与进度无关，快慢只服从观感。
- **进度层**（矿脉高光 / 打捞扫描弧 / 航标进度环 / 扫描雷达环，类名带 `app-act-tick`）：
  **相位锁真实作业进度**——舞台上 `--act-cycle` = 一个作业周期的毫秒数、`--act-delay` = 已走毫秒取负
  ⇒ **周期完成那一刻正好走到峰值**（出货 / 捞上一件 / 到站 / 扫完一遍的瞬间亮一下），进度归零相位也归零。
- **节拍只夹快慢、不夹相位**：周期 <1.6s 会闪成一片、>12s 近乎静止（扫描虫洞的"小时带"是 3.6e6ms）
  ⇒ 夹到 `[1.6s, 12s]`。**相位照样按真实进度对齐，读数与进度条不受任何影响**（真相由读数负责）。

### 本轮实现自查（动手时就地修掉的两个真缺口）

① **漂浮物全挤在画布左上角**：落位要 `transform="translate(…)"`、漂移动画也要动 `transform`，
   同一个元素上两处抢一个属性 ⇒ 动画把落位覆盖掉。改为**外层 `<g>` 落位、内层 `.app-act-drift` 动画**。
② **星点全是隐形**：根 `<svg fill="none">` 是继承源，`<circle>` 没给 `fill` ⇒ 一个点都看不见。
   改为 `.app-act-stars circle { fill: #d7e7f4 }`（固定冷白，活动色留给"在作业的东西"，同小窗口径）。

### 无头读数核实（工具 `tools/activity-win-probe.ts`，⚠ **读数不是观感结论**）

首次量"光带有没有接到作业对象上"时踩了一个坑，记进工具注释：`getBBox()` 给的是**元素自己那一层的
局部坐标**（不含自身与祖先 transform），于是"舰（自带 scale/translate）"与"光带（画在画布绝对坐标）"
两边的数根本不可比（舰报 x20~238，看着像跑到画布左上角）。改为**经 `getScreenCTM()` 逆变换回画布坐标**，
并顺带给探针加了"该动却没动"白名单（星野 / 矿岩 / 航标本就是静态层，不能一律报缺陷）。

| 场景 | 元件 | 舰形 | 星点 | 进度层 | 节拍 `--act-cycle`/`--act-delay` | 进度条 |
|---|---|---|---|---|---|---|
| 采掘中 | 21 | 资产形(16 节点) | 96 | 1 | 11900ms / −6400ms | 54% |
| 打捞中 | 23 | 资产形(13 节点) | 96 | 1 | 6000ms / −4000ms | 67% |
| 长途运输中（承运） | 20 | 资产形(16 节点) | 96 | 1 | 12000ms / −3284ms | 27% |
| 长途运输 · 就位中 | 18 | 资产形(16 节点) | 96 | 1 | 12000ms / −151ms | 1% |
| 扫描虫洞中 | 22 | 资产形(16 节点) | 96 | 1 | 12000ms / −2849ms | 24% |

**相位挂钩是数值可验的**：`|--act-delay| ÷ --act-cycle` 与进度条百分比逐一吻合
（采掘 6400/11900 = 54%、打捞 4000/6000 = 67%、承运 3284/12000 = 27%、就位 151/12000 = 1%）
⇒ "动画相位 = 真实进度"这条不是口头承诺。

**画布几何（逆 CTM 回画布用户单位）**：

| 场景 | 舰 | 作业对象 | 光带 | 结论 |
|---|---|---|---|---|
| 采掘中 | x128~277 | 矿岩 x428~504 | x230~429 | 不叠（舰在左、对象在右）·光带起于舰内、抵达对象 |
| 打捞中 | x136~259 | 残骸 x426~496 | x230~506 | 同上 |

并不等于画布宽（资产 240×110 里留了边距，实测最窄的舰描边只到 ±61）⇒ 打捞舰的光带**离舰 7 单位**
（悬在舰首外）。改为固定在**锚点内侧 34 单位**（`EMITTER_X`）⇒ 对任何舰形都从舰体内射出。

### ① 漂浮物半路消失 —— 真因与修法（缺陷，按缺陷直接修）

真因不是玄学：漂移动画的**横向行程只有 290 画布单位**，而道具**落位**又在 x≈404~530
⇒ 出场点在右缘外、**消失点落在 x≈274~400**，正是画面右半到正中。左上角小窗那套
（`app-swin-drift`）是 150 → −34 一整个来回飞出左缘，所以那边看不到"半路消失"。
根子在于**落位与行程混用**：落位占掉了行程的 x 分量。

改法：**落位只管 y**（`<g transform="translate(0 y)">`），横向行程写死在 keyframes 里
`translateX(620px) → translateX(-80px)`，两端都在画框外（画布宽 560）⇒ 消失点回到画框外；
淡入淡出也一并挪到框外（5% 起亮、90% 起暗，而 12% 才进画、92% 已出画）。

**读数**（两路证据，探针 `npm run ui:actwin`）：
- **声明**（CSSOM 里读 `@keyframes`）：`app-act-drift` 与 `app-act-drift-spin` 都是
  `0%: translate(620px)/op0 → 100%: translate(-80px)/op0` ⇒ 起点 620 ≥ 画布宽 560、终点 −80 + 物宽 26 ≤ 0，
  **两端都在画框外**（这就是"不会半路消失"的判据，且淡入淡出也都落在框外）。
- **运行时采样**（6 帧）：实测横向范围 x≈1~640，与声明一致（最右到 640 ≈ 起点 620 + 物宽）。
  ⚠ **采样采不到最左端**：道具待在框外左侧只有收尾 ~8% 的时间，6 帧抓不到 ⇒ **不能拿"没采到 x<0"当缺陷**
  （首测就这么误报过一轮）。故判据取声明、采样只作"样式真的生效"的旁证。

### ② 窗口改覆盖「主内容区」（不再整屏悬浮）

- 两个窗口组件在 `App.tsx` 里**从 `.app-root` 直下挪进 `<main className="app-page-main">`**；
- `.app-page-main` 加 `position: relative`，窗口层由 `position: fixed; inset: 0`（整屏）改为
  **`position: absolute; inset: 0`**（吃主内容区）⇒ **左导航（含小窗）与顶栏永不遮挡**，
  而且不用去量导航宽 / 顶栏高（量与猜都是坑，窄屏与手机横屏尤其容易错）；

  ⇒ **窗外可点穿**（非模态）：窗口开着照样能点导航、翻页面。

  尺寸本来就是 `min(…, 100%)`，永远不会超）；`.app-root` 在手机横屏下是 `position: fixed + transform`

## 第五批：窄屏改「等比缩放」（2026-09-21）

船长原话（照抄）：

> 「窄屏窗口偏小采用等比缩放。可以合并了」

### 做法

窗口**永远按设计尺寸排版**（CSS 固定 `1180×760` / 活动窗 `860×560`，不再 `min(…, 100%)`），
装不下时由 `ui/WinBox.tsx` 量可用区（窗口层）与窗口的**布局尺寸**算出
`--win-scale = min(1, 可用宽/设计宽, 可用高/设计高)`，对整块做 `transform: scale()`
⇒ 任何屏幕都是**同一套版式**，只整体缩放；**不再出现"窄屏被压扁 ⇒ 内部转横滑/换行"的走形**。
只缩不放（`min(1, …)`）：设计尺寸就是目标尺寸，宽屏上与原样**逐像素一致**。

- 量尺寸用 `offsetWidth/Height`（**不受 transform 影响**）⇒ 缩放不会反过来改变量到的值，没有自激循环；
- `useLayoutEffect` 首帧上屏前就算好，避免"先溢出再缩回"的闪动；`ResizeObserver` 盯可用区（视口/导航/日志栏变化都重算）；
- 顺手删掉**已经不可能命中**的 `@container (max-width: 820px)` 那套窄窗横滑兜底（版式不再随窗口宽变化 ⇒ 死代码）。

**探针当场抓到一个真缺陷**：首版忘了给 `.app-winbox` 加 `flex: none`，而它的父级是 flex 容器
⇒ 默认 `flex-shrink: 1` 把窗口**压到可用宽**（实测设计尺寸读成 455×562、缩放恒为 1 = 等于没缩）。
读数暴露的（`设计=` 那几列三个视口居然不一样），看代码看不出来。

### 读数（探针，三种视口；`设计` = 布局尺寸，`缩放` = 实际生效系数）

| 视口 | 主内容区 | 活动窗口 设计→渲染 | 缩放 | 战斗窗口 设计→渲染 | 缩放 |
|---|---|---|---|---|---|
| 1440×900 | 891×834 | 862×562 → **862×562** | **1** | 1182×762 → 871×562 | 0.737 |
| 1280×800 | 731×734 | 862×562 → 711×464 | 0.825 | 1182×762 → 711×458 | 0.602 |
| 1024×768 | 475×686 | 862×562 → 455×297 | 0.528 | 1182×762 → 455×293 | 0.385 |

三视口一律：**等比=是**（渲染宽高比 = 设计宽高比）、区内居中、非全屏、**不盖导航/顶栏**、无文档溢出。
⇒ 宽屏（1440）上**活动窗口与原样逐像素一致**，只有更窄时才整体缩小。

⚠ **代价（如实标注）**：整体缩放意味着窄屏上**字号也跟着缩**——1024 宽时活动窗口的读数文字只有
设计的 53%（12.5px → 约 6.6px）。这是"版式不走形"的必然代价。若船长觉得窄屏字太小，
可加一条**缩放下限**（如不低于 0.75，再小就允许窗口越出主内容区盖住右侧日志栏）——等船长一句话。

## 第六批：窗口改「嵌入主区」＋ 四类操作自动收起（2026-09-21）

船长原话（照抄）：

> 「我的意思是取消悬浮，直接嵌入主窗口，玩家如果点击最小化或者切换导航栏之类的时候就隐藏并最小化。」

| ④ 切导航（点「舰船」） | **窗口自动收起** · 页面回来 · 角标出现 |
| ⑤ 开弹层（点顶栏「手册」，弹层出现=是） | **窗口自动收起** · 页面回来 |
| ⑥ 活动结束（点活动栏「停止采掘」） | **窗口自动收起**（跃迁计数 > 0）· 页面回来 |

### 本轮自查抓到的两个真缺陷（都在实现过程中就地修掉）

① **调试关着时主区会空白**：活动窗口有调试开关，而"上屏"判定若不算这把开关，就会出现
   "窗口不渲染、页面却已被让位" ⇒ 把 `activityWinEnabled()` 导出、并算进 `activityOnStage` 与还原入口。
② **探针量同构战斗壳只量到一半高度**（342 而非 690）：当时**真活动窗口也在场**，两个 `flex:1`
   兄弟平分高度；且"加类名让页面让位"会被 React 每 tick 刷回去 ⇒ 改用**内联 display** 同时让开两者。

## 第七批：洞内战斗内嵌进虫洞探索界面（2026-09-22）

船长原话（照抄）：

> 「虫洞内的战斗因为舰船比较多，能否改为内嵌在虫洞探索界面内？」

选择题回话：**战斗中能关面板（关了就挪回主区）**；**战斗开始时若面板没开，自动把面板叫起来**。

### 做法

- **沿革（旧裁定被本条取代）**：2026-09-13 船长报障「打捞遗迹触发战斗时，虫洞界面处于最前端遮住了战斗」
  ⇒ 当时做法是**战斗中整块不渲染虫洞面板**（战场独占屏幕）。现在换个方向：**不再藏面板，把战场嵌进面板主体**
  ——面板壳（标题/读数/关闭/撤离）与战场同屏，层级冲突从根上不存在；面板还比主区那塊更宽
  （1060 vs 887；1024 宽屏时 942 vs 471），正合"舰船比较多" ✓。
- `WormholePanel` 新增 `battleSlot` 属性，**由 `App.tsx` 把战斗节点传进来**（全仓仍只有一个战斗组件实例——
  它内部有阶段机 live→outro→report 与慢镜快照，两份实例会各跑一套）；`BattleScreen` 新增 `bare`
  （不带窗口壳，宿主的 `.app-wh-battle` 负责尺寸与背景）。
- 战斗中面板**主体整块让给战场**（CSS：`.app-wh-run.is-battle > :not(.app-wh-head):not(.app-wh-battle)`），
  只保留顶部读数条（深度/已探/回合/货舱/谜质）；地图/工作区/动作区隐掉、战斗结束原样回来。
- **收起与还原**：面板「✕ 关闭」在交火中不再禁用、也**不再等于离洞**（只收界面、`attending` 保持 true，
  战场由主区接管继续打）；`App` 侧用 `whDismissed` 记住"本场玩家已收起"，战斗结束自动复位。
- **自动开面板用「电平判据」而不是"开战上升沿"**（`whBattleLive = run.battle && attending === true`）：
  上升沿在"载入时战斗已经在打"的情形下不可靠（实测：边沿确实触发、两个 state 也都置了真，
  但页面里面板仍是关的）⇒ 电平判据直接表达"战斗在 ⇒ 面板就该在台上"，与载入顺序/重挂载/边沿丢失都无关。
  （远征战那条上升沿规则**未动**，它一直work。）文案：删死键 `ui.Wormhole.009`/`.014`，
  新增 `.378`（交火中关闭面板的悬停说明）与 `.379`（交火中的按钮文字「✕ 关闭面板」）。

### 本轮踩到并解决的两个"夹具"坑（都写进了工具注释）

① **手造的洞内战斗是无效夹具**：先把"远征战斗对象搬进 `run.battle`"——`wormholeBattleViewOf` 要按
   这一趟的编队/威胁重建视图，搬来的单位对不上 ⇒ **战斗组件一渲染就抛错、整块面板被 React 收回**
   （现象是"面板挂载即消失"，一度误以为宿主接线写坏了）。正解：**用引擎自己的 `wormholeStartBattle`
   开一局真战斗**再存档 ⇒ 新工具 `npm run save:whbattle`（顺手也成了给船长的验收测试档）。
② **放旧的夹具会被离线结算吃掉瞬时态**：几天前的档一载入就把这局战斗当场打完（行上从「交火中」
   变成「第 3 层 · 节点」）⇒ 探针加载时把存档时间戳改成"刚刚"（`patchFile` 钩子）。
