# whale-server · 1000 人在线容量评估与重构方案

> 状态：方案稿（未动手）　｜　日期：2026-11-03
> 船长口径（2026-11-03）：「撑着现在 whale-server 还不够臃肿，如果要重构的话，压力 1000 人同时在线，需要做什么」
> 前提：现有生产机 2 核 / 1.9G 内存 / 40G 盘（已用 5.8G / 32G 可用），单进程 Node + SQLite（WAL）。

---

## 结论先行

1. **1000 CCU 对这套架构不算大**：带宽、内存、WS 连接数都远没到上限；**真正会先炸的是三处**——① `node:sqlite` 同步 API 阻塞事件循环；② 云存档大 JSON 的写入与磁盘占用；③ 没有监控，出问题只能靠猜。
2. **不要先重构，先压测**：用 k6/autocannon + 1000 虚拟 WS 连接跑出现有瓶颈，再按数据改。凭感觉拆微服务是负优化。
3. **分三阶段**：A（同机优化，能撑 1000）→ B（跨进程/多实例，撑 3000~5000）→ C（分片多机，万级）。A 阶段成本最低、收益最大，B/C 按真实增长再上。
4. **交易所独立进程（Go）本身就是 A 阶段的一部分**：把撮合/AI/行情放第二核，Node 只做 IO 与资金，两者隔离。
5. **云存档必须从 SQLite BLOB 迁到文件对象存储**（或至少 gzip + 降版本数 + 配额），否则 1000 人 × 10 版 × 单档几 MB 会把 40G 盘吃穿。

---

## 一、负载模型（1000 CCU 估算）

| 流量 | 估算 | 判断 |
|---|---|---|
| WS 长连接 | 1000 条 | 单进程可承受；内存约 10~30MB |
| 行情广播 | 4 标的 × 1Hz × 1000 订阅 ≈ 4,000 帧/s | 预序列化后单核可承受；250ms 档约 1.6 万帧/s 仍可 |
| 聊天 | 峰值 ~50 条/s，广播 1000 连接 | 需 3 秒打包 + 帧大小限制（已有） |
| REST | 估 100~300 req/s（含轮询） | 单进程可承受 |
| 下单/成交 | ~30 单/s、~60 成交/s | 撮合压力极小（Go 第二核） |
| 产出上报 | 1000 人 × 1/min ≈ 17/s（带配额校验与写库） | **写库压力点** |
| 云存档上传 | 1000 人 × 2 次/日，单档 1~10MB | **最大 IO/磁盘风险点** |
| 数据库写事务 | 合计 ~100~150 事务/s | SQLite 可承受，但需 `synchronous=NORMAL` + 批量 |
| 下行带宽 | 4,000 帧/s × ~200B ≈ 0.8MB/s ≈ 6.4Mbps | 服务器 200Mbps，完全够 |

**内存**：Node ~200~300MB + Go 交易所 ~50~100MB + SQLite 缓存 + 连接缓冲，合计 < 800MB（1.9G 够）。
**磁盘**：主要风险是云存档历史（见下），其余（K线/成交/日志）每天几十 MB 级。

## 二、会先炸的点（按优先级；**已被 2026-11-03 压测修正，见第七节**）

> 压测结果：首因是 **WS 聊天广播扇出**，不是同步 SQLite。以下 P0~P5 为压测前的假设，修正后的优先级见第七节。

### P0：`node:sqlite` 同步 API 阻塞事件循环

- 现状：`DatabaseSync` 所有读写都在主线程同步执行；一次 10MB 存档的 JSON 解析 + 插入会**阻塞所有 HTTP/WS 数百毫秒**。
- 修法：
  1. `PRAGMA synchronous = NORMAL`（WAL 下安全，牺牲极端断电的最后几笔）；
  2. 大对象（存档）**移出 SQLite**：存文件 `data/saves/<account>/<version>.json.gz`，DB 只存元数据（路径/大小/哈希/时间）；
  3. 写操作经**单个写线程/写队列**批量提交（主线程只入队），避免长事务。

### P1：云存档磁盘占用

- 现状：单档上限 10MB、每账号保留 10 版 ⇒ 1000 人最坏 100GB，40G 盘必然爆。
- 修法：gzip 压缩（JSON 文本约 5~10 倍）+ **保留版本 10 → 3** + 每账号配额（如 50MB）+ 上传前客户端压缩。

### P2：WS 广播效率与慢客户端

- 修法：每个 tick **只序列化一次**行情帧，向订阅者发送同一字符串；用 `bufferedAmount` 检测慢客户端并断开；在线名单用 Map 维护 O(1)，禁止每帧遍历。

### P3：无监控/无告警

- 修法：`/metrics` 暴露事件循环延迟、WS 连接数、DB 写队列深度、事务耗时、内存、慢查询；日志轮转；2~3 条关键告警（进程挂、DB 锁等待 >1s、磁盘 >80%）。

### P4：限流是进程内滑动窗口

- 现状：重启清零、多实例不共享。单实例 1000 CCU 够用；阶段 B 换 Redis 统一限流。

### P5：无管理后台

- 封禁/回滚/补发/看玩家状态全靠手工 SQL。1000 CCU 阶段必须补一个最小后台（只读 + 少量写操作 + 审计）。

## 三、重构路线（按阶段，避免过度设计）

### 阶段 A：同机优化（目标：稳撑 1000 CCU）

| 项 | 动作 | 验收 |
|---|---|---|
| 交易所独立 | Go 服务（订单簿/撮合/行情）跑第二核；Node 只做资金与 IO | 两个进程 CPU 分别 < 60%，撮合 p99 < 50ms |
| 存档迁移 | 存档 Blob → 文件 + gzip；版本 3；账号配额 | 1000 账号模拟后磁盘增量 < 5GB |
| DB 调优 | `synchronous=NORMAL`、写队列、批量提交、索引复核 | 事务 p99 < 20ms，无锁等待告警 |
| WS 优化 | 预序列化广播、慢客户端断开、心跳与在线名单 O(1) | 1000 连接下事件循环延迟 p99 < 50ms |
| 观测 | `/metrics` + 日志轮转 + 3 条告警 | 能定位「谁在阻塞事件循环」 |
| 管理后台 | 最小只读 + 封禁/回滚 + 审计 | 运维不用再手工 SQL |

### 阶段 B：跨进程/多实例（目标：3000~5000 CCU）

- 网关层：Caddy/Nginx 前置，多 Node 实例（无状态 HTTP；WS 走粘性/网关）；
- 发布订阅：Redis（或 NATS）做行情/聊天扇出，交换所发布一次、各网关各自推送；
- 数据库：SQLite 单写扛不住多实例 ⇒ 迁 PostgreSQL（账本/钱包/订单用事务；行情 K 线可留时序/分区）；
- 会话与限流：Redis 共享；
- 存档：对象存储（腾讯云 COS）+ CDN；
- 任务队列：产出校验、存档压缩、对账等异步化。

### 阶段 C：分片多机（万级）

- 按逻辑服/星区分片；交易与账本按分片内聚；跨服只同步汇总数据；
- 撮合按标的分片到多机（一个标的只在一处撮合）；
- 全链路追踪 + 容量自动扩缩。

## 四、先做什么（建议顺序）

1. **压测基线**（1~2 天）：k6 脚本模拟 1000 WS + REST 混合流量，记录 CPU/内存/事件循环延迟/DB 等待，找出首个瓶颈；
2. **P0/P1 修复**（3~5 天）：DB 写队列 + 存档文件化 + gzip/配额/版本数 + `synchronous=NORMAL`；
3. **交易所 Go 进程**（按现有设计）；
4. **观测 + 最小后台**；
5. 压测复跑，确认 1000 CCU 达标后再谈阶段 B。

> 原则：每一步都先用数据证明瓶颈，再动手。1000 CCU 内不需要微服务；先榨干单机 + 第二核，再谈分布式。

## 五、验收指标（1000 CCU）

| 指标 | 目标 |
|---|---|
| HTTP p99 | < 150ms（普通接口）；存档上传 < 2s |
| WS 推送延迟 p99 | < 1s（1 Hz 行情） |
| 撮合延迟 p99 | < 50ms |
| 事件循环延迟 p99 | < 50ms（无长阻塞） |
| 错误率 | < 0.5% |
| 内存峰值 | < 1.2GB |
| 磁盘增量 | 1000 账号模拟一周 < 5GB |
| 备份 | 每小时成功、可恢复演练通过 |

## 七、实测基线（2026-11-03，本地压测，`whale-server` 仓 `scripts/_loadtest.ts`）

### 7.1 三档结果（每档 15~20s 窗口）

| 档位 | WS + REST | REST p50/p95/p99 | 错误率 | `/health` p99 | CPU | RSS |
|---|---|---|---|---|---|---|
| A | 200 + 200rps | 4.5 / 15.1 / 24.8ms | 0% | 21.6ms | 25.9% | 94MB |
| B | 500 + 300rps | 12.3 / 49.1 / 79.3ms | 0% | 93.2ms | 55.5% | 118MB |
| C | 1000 + 400rps | **3123 / 10755 / 13100ms** | **90.0%（全为客户端 15s 超时）** | **3660ms** | **92.5%** | 154MB |

- 空载基线：`/health` p99 1.2ms、CPU 0.4%；
- **1000 条 WS 全部建成（0 失败）**；
- 对照：**1000 空闲 WS + 400rps → p99 30.8ms、CPU 39.6%、0 错误** ⇒ 连接数本身不是问题。

### 7.2 根因：聊天广播扇出（不是 SQLite）

- 实测 `ws.send` 每帧约 **17µs**（每个接收方重新编码 + 建帧 + 写 socket）；
- 扇出 = batch/s × 在线人数：本次 20% 用户每 3s 发一包 → 65 batch/s × 1000 = **6.5 万帧/s ≈ 110% 单核**（必崩）；
- 按文档口径聊天（~50 条/s → 10~17 batch/s）→ 1.7 万帧/s ≈ **29% 单核**（能撑）；
- **行情推送 4 标的 × 1Hz × 1000 = 4000 帧/s ≈ 7% 单核**（不是问题，对交易所是好消息）。
- 对照实验：1000 WS + 聊天、关掉 HTTP → 仍崩（`/health` p99 3974ms、CPU 93.7%）⇒ 排除 HTTP/鉴权/存档读。

### 7.3 第二梯队问题（实测存在，非首因）

1. **建连路径 O(n²)**：`hello` 内嵌全量在线名单 + 每人 join 广播给所有人；1000 连接有聊天时 21.6s、无聊天 10.4s ⇒ 重连风暴要防（分页/合并 join）。
2. **鉴权写放大**：`authenticate()` 每请求 2 条 UPDATE 自动提交（WAL synchronous=2，0.45~0.6ms/次）；300rps ≈ 13% 单核。建议 `last_seen` 节流 + 批量。
3. **聊天批处理写**：每 batch 5 INSERT + 1 次全频道 DELETE（1.1ms）⇒ INSERT 批量、DELETE 交给保留任务。

### 7.4 修正后的优先级

| 优先级 | 动作 | 依据 |
|---|---|---|
| **P0** | 聊天广播降频/合并（3s→10~15s 或子频道订阅）+ 慢客户端 `bufferedAmount` 断开 | 实测首因 |
| **P0.5** | 建连路径去 O(n²)（hello 去掉全量名单、join 合并/节流） | 1000 连接 21.6s |
| **P1** | 鉴权 `last_seen` 节流、聊天 INSERT 批量、DELETE 转保留任务 | 13% 单核待省 |
| **P2** | 存档大对象外置 + gzip + 配额（本次未压 PUT /api/saves，仍是磁盘风险） | 磁盘估算 |
| **P3** | `/metrics` + 告警 + 最小管理后台 | 可观测性 |
| 降级 | SQLite 写队列/批量（原 P0，实测非首因） | 仍必做，但排后 |

### 7.5 测量局限（必须声明）

- 本机 20 核 NVMe 开发机 vs 生产 2 核机：**只迁移瓶颈排序，不迁移毫秒数**；
- Windows 回环、无 TLS/反向代理；100 个账号复用 1000 连接；未压 `PUT /api/saves`；
- C 档探针被饿死，仅约 7 个样本，p99 可视作单次观测；
- 真容量结论需在服务器低峰时段复测（需船长批准，且会占用生产资源）。
