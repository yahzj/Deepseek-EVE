# 玩家市场异步转发设计

- 状态：**机制方向已确认，数值和协议待定，未实施**。
- 日期：2026-11-04；经办：Codex；工作树：`Deepseek-EVE-verify`；分支：`verify`。
- 本轮只记录方案与待办，未改实现；目录与 roadmap 由父会话同步维护，不提交、不部署。
- 规则依据：主树 `AGENTS.md`、`docs/catalog.md`、`docs/development-conventions.md`。
- 本文记录设计约束及未来实施清单，不代表接口、参数或验收已经完成。

## 一、船长原话摘要

以下为父会话提供的船长真实原句；技术边界与协议建议另见后文，不作为船长原话引用。

> “铁人模式和在线模式的想法取消，不做这方面改动”
> “上传失败订单依旧在本地，等待下一次市场刷新时同步一下就好”
> “若订单已经被别人买/卖走，也无所谓。本地交易依旧成立。只是别的玩家收到的交易金额或者商品依旧是一份。”
> “服务器已经成功的订单在玩家本地不存在，也不会将该订单的收益发给玩家。”
> “商品资格我觉得任何商品都能交易，这点不需要限制，唯一的限制也是购买的声望条件。”

## 二、范围与不做

- 功能域为市场异步转发；本批只有设计文档，无跨域实现修改。
- 普通与铁人模式继续存在，既有模式约束、铁人账本不改，不新增强制联网模式。
- 本地导入、导出、读档和离线市场继续可用，不用取消导入规避结算问题。
- 本地 NPC 市场保持主体；服务器提供订单转发、持久去重与限额结算记录。
- 不改现有云存档、账号、聊天、证券交易所，不把云档改成服务器权威状态。
- 不做全服严格物品/信用点守恒，不承诺消除任意回档和改档造成的本地复制。
- 不新增玩家可见文案、英文覆盖或公告，不在本批注册接口、修改数据或运行部署。

## 三、挂单与刷新流程

1. 玩家按原入口挂买单或卖单，先执行本地校验、预占与撮合。
2. 本地即时成交后，仅自己的剩余有效订单进入自动上传队列，不增加上传确认。
3. 上传失败或被远端过滤，订单仍留本地，由 NPC 继续处理；下次市场刷新重试。
4. 重试沿用订单身份和未确认请求编号，上传前重读本地剩余量，不复用旧数量制造新单。
5. 市场刷新按比例或数量抽取其他玩家订单；比例、数量与刷新周期待定。
6. 抽样不按接收者当前持仓或兴趣筛选；既有界面筛选与远端抽样条件分开。
7. 外来订单进入本地后，能成交则直接成交，剩余部分按本地市场规则展示和处理。
8. 远端原单已售罄、撤销或被其他人先成交，不撤销接收者已成立的本地交易。
9. 接收者异步上报成交结果；原挂单者在服务器剩余预算内取得对应收益或商品。

- 必须保留内部来源标记，但界面不显示 NPC/玩家来源，也不增加来源切换入口。
- **外来订单绝不再次上传**，包括外来单剩余、读档恢复和混合订单簿重新序列化。
- 上传队列只枚举本存档拥有的原始挂单；不能把展示订单表直接当 owner 订单表。
- 撤单、过期、改价与并发本地成交的同步顺序需要协议确认，不能把重试当成重新挂单。

## 四、商品与购买门槛

- 所有已上线可见、具正常定义且能够存储和交付的商品，均允许进入玩家转发范围。
- 未上线、隐藏、无正常定义或无法存储交付的对象不因转发而开放。
- 不能沿用 NPC 的 `playerBuyable` / `playerSellable` 作为玩家交易禁令。
- NPC 原本不出售或不收购，只描述 NPC 行为，不能直接缩小玩家可交易商品目录。
- 保留购买累计声望门槛，不能因转发、自动撮合或原 NPC 不售而绕过。
- `bmStanding` 与普通购买累计声望如何合并、比较或分渠道校验，具体口径待核。
- 同一购买门槛须覆盖展示、手动成交、自动撮合与转发收货；最终校验职责待协议落实。

## 五、稀缺商品卖单溢价

- 对象仅为：**按规则 NPC 不出售**的商品；暂时售罄、慢补货耗尽不属于此类。
- 仅玩家卖单转发适用；原挂单者按原挂价结算，不获得转发溢价。
- 买家成交前看到最终单价、数量和总支付额，不允许成交后隐形追加扣款。
- 溢价差额由系统回收；既有正常成交税单独计算，保持原适用侧，不重复征收。
- 建议公式：`P展示 = ceil(max(P原 * M, P最低展示))`。
- `P原` 为原始卖单单价，`P最低展示` 为最低展示价；后者定义、来源和数值待定。
- `M` 候选为 5-10，**不是已确定参数**；取整单位、总价与税费计算次序待定。
- 正常 NPC 可售商品的转发不套此项稀缺溢价；不借此修改 NPC 本身的售卖规则。
- 报价保留原始单价、最终价、规则版本和固定快照；刷新、重试、读档不以展示价再乘。
- 同一订单、报价及回执不可连乘；外来单禁止再上传也不能替代报价层的幂等校验。

### 买单路径的未决边界

- 初版买单路径维持原价，不能擅自把上述卖单公式扩展到所有买单。
- 稀缺商品若直接卖给对等远端买单，可能使买方绕过稀缺负担，属于必须处理的旁路。
- 待确认方案：设计同等买方负担，或初版暂不自动走该成交路径。
- 两项均为待确认选项，本文不擅自禁止远端买单，也不授权无负担旁路上线。

## 六、两本结算账

### 接收者的本地账

- 本地成交按已展示报价扣款、交货或收货；成交结果不等待远端原单仍然可用。
- 接收者买入外来卖单：本地支付最终价并收货；原卖家只按原价获得限额内收入。
- 接收者卖给外来买单：本地交货并收款；原买家只在限额内获得对应商品。
- 远端预算耗尽或本地与远端成交重叠，系统补足接收者本地交易，不追扣、不回收。
- 本地预占、退款、仓储交付与正常成交税须完整闭合，不能把“系统补足”写成免校验。

### 原挂单者的限额账

- 每张原始订单只有一份数量预算；本地已消费数量与远端已结算数量共同占用该预算。
- 概念式：`R = max(0, Q原始 - Q本地已消费 - Q远端已结算)`。
- 每次新增远端结算：`Q本次 = min(Q请求, R)`；超出部分不再给原挂单者收益。
- 原卖单按 `Q本次 * P原` 结算并按既有规则处理正常税；原买单交付至多 `Q本次`。
- 原买单的信用点预占及原卖单的物品预占都要按同一数量账核销，不能只限制到账金额。
- 本地继续成交与远端回执竞争同一剩余量，先在单点合并预算，再计算可领取部分。
- 服务器持久保存已消费数量、结算编号和幂等记录；同一订单读档不能重置结算上限。
- 本地完整有效 owner 快照中订单不存在，不按历史成交补发，不重建订单发放收益。
- “最多一份”是原单预算约束，不是对任意本地回档的端到端绝对一次到账保证。

## 七、完整快照与身份隔离

- owner 快照指原挂单者自身订单的完整有效快照，不是当前页面、筛选结果或导入展示行。
- **不能仅删除当前 UI 中的导入行，就判定原订单不存在**；外来展示行不代表 owner 状态。
- 须明确快照完整标志、协议版本、存档格式版本、账户、存档身份与快照序号。
- 分页未收齐、局部补丁、版本不兼容、校验失败或身份不匹配均不能作为“订单不存在”依据。
- 快照完整性及新旧顺序须可校验，不能仅凭客户端自称完整就覆盖已确认状态。
- 完整 owner 快照确认订单不存在时，停止该单后续补发；失联或无快照不是订单已删除。
- 订单身份与账户、存档身份绑定；不同账户和存档不能误领、覆盖或借旧单重置预算。
- 服务器已消费数量、结算编号、领取记录属于服务器持久字段，上传快照不得覆盖或回退。
- 本地可上报消费增量和订单状态，合并规则必须去重；较旧快照不得恢复可结算数量。
- 导入副本、另存新档、同档多设备、账户切换及跨存档领取的身份与继承规则仍未决。
- 不把本地文件路径或当前云档槽位直接当作可靠存档身份，也不改现有云档行为。

## 八、隔离协议与领取取舍

- 已有 server market/wallet 是严格共享交易与账本模型，与本方案允许本地独立成交不相容。
- **不能直接接现有 market/wallet API**，也不把 relay 补足记成既有共享市场成交。
- 建议新增隔离 relay 接口、记录与结算域；可复用基础鉴权，不复用严格守恒交易语义。
- 接口职责建议分为：自有剩余单同步、外来订单抽样、成交上报、回执查询与领取确认。
- 路由、字段、数据库事务、认证边界及版本协商均待定，本文不是可直接实施的协议规范。
- 原单数量预算、消费合并、报价派生、税费与去重必须各有单点，不在客户端和服务端多处另算。
- `quoteID` 绑定原单、原价、最终价、数量边界和报价规则版本；固定快照报价防止连乘。
- `receipt` 绑定成交编号、原单、可结算量、领取结果与身份；同编号只能得到同一结果。
- 未确认交易必须自动重试且**不能换 id**；重复请求只返回原回执，不产生新预算或新发放。
- 服务端并发消费与回执写入需在服务端自身事务内闭合；这不等于与客户端存盘原子提交。

### 领取、落盘与回档

- 服务器标记已领取与本地保存无法天然原子，**不承诺完全 exactly-once**。
- 必须定义领取意图、本地持久待办、服务端回执、本地应用及确认各自的顺序和恢复行为。
- 先服务端标记领取再本地落盘：落盘失败或恢复旧档可能少领，不能换编号再次补发。
- 先本地应用并保存再向服务端确认：确认丢失可重试，但回档丢失本地去重账后可能再次应用。
- 最终选择哪种确认顺序、服务端已领回执是否可重放及恢复窗口，留待协议确认。
- 至少防止网络超时、断线、重复请求及确认丢失引发服务端多次发放；不以换 id 解决不确定态。
- 本地待办与已应用回执须随保存事务落盘、往返保留；仅内存标志不能承担去重。
- 恢复后可能少领或本地复制属于接受风险，不能据此删除导入导出或改动铁人规则。
- 原单已不在完整 owner 快照时，不得借回执恢复流程另行补发；在途确认的终态仍须协议明确。
- 任意旧档可丢失已到账资产或恢复已消费资产，不能把服务器预算不回退表述成全面防回档。

## 九、异常过滤与 NPC 兜底

- 服务器可过滤明显异常价格、数量或非法商品；过滤只影响转发，不删除本地订单。
- “基础价 1000 倍”为讨论例子，不是已确定阈值；基础价来源及无参考价商品处理待定。
- NPC 低价兜底方向已确认，包含原先无买盘商品；兜底价格、数量、周期及触发条件待定。
- 技术建议：为兜底设置价量边界，具体价量待定，并非船长已定限制；方向确认不自动授权无限兜底，也不因阈值未定缩小已确认的商品覆盖范围。

## 十、UI 体验约束

- 沿用现有市场入口、挂单和成交体验，本地与外来订单混排，不显示来源身份。
- 不增加上传确认；联网失败不阻断本地挂单、NPC 撮合或已有订单展示。
- 买方预先看见最终价、总支付及正常税费；卖方按原挂价查看自身结算，不暗示获得溢价。
- 剩余量、已成交和撤单结果从统一市场视图取数，不把远端预算耗尽显示成本地成交失败。
- 本节仅记录已确认体验，不设计新页面、提示文本、英文或公告。

## 十二、核心测试清单与未决项

以下仅为未来测试清单，**本批未运行测试**。

- 本地先成交再上传余量；上传失败/过滤保留本地订单，下次刷新以同 id 自动重试。
- 按比例/数量抽样不依赖持仓；外来单即时成交、剩余展示、存档恢复后均不再次上传。
- 已上线合法商品可转发，不误用 NPC 禁售禁收标记；购买声望各路径一致，含 `bmStanding`。
- 规则禁售与暂时缺货区分；最终价预见、卖家原价、差额回收、正常税独立且溢价不连乘。
- 远端买单稀缺费旁路按最终裁定验证；方案未确认前不能宣称此风险已解决。
- 本地与远端超量只按 `min` 结算原单；远端售罄仍完成接收者本地交易并由系统补足。
- 并发回执、网络重试及同订单读档不重置预算；旧快照不能覆盖消费数量和结算编号。
- 完整 owner 快照缺单不补发；UI 删除、筛选、分页、坏版本和错误身份不能误判缺单。
- 领取/确认/落盘各断点与回档恢复覆盖；验证不换 id、防网络多发，并显式记录少领/复制风险。
- 保存往返保留待办、身份及回执；普通/铁人、导入导出、云档、聊天和证券行为保持不变。
