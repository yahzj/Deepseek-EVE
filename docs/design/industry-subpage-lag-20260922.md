## 〇、一句话结论

**卡顿 = 切过去的那个子页要从零把卡片 DOM 造一遍，代价 ∝ 卡片数 × 单卡节点数。**
组装机 **151 张 × 55 节点 = 8298 个节点**，四个子页里最重；把 CPU 降速到 1/6（代理"配置差的机器"）后，
切一次组装机要 **1.56 秒**、造船厂要 **1.66 秒** —— 这就是玩家说的「数秒的卡顿」。

⚠ **推翻一稿结论**：一稿写的「重建不是主因，每 tick 整树重算才是」**是错的**。一稿只有船长那份
**开着监测**的快照（监测路径会把渲染改成 `flushSync` 同步，提交耗时被放大），本稿四个子页逐个实测后，
**冷启动重建正是主因**，「每 tick 整树重渲染」是叠加在它上面的放大器（第二节）。

## 一、复现方法与读数

工具 `npm run industry:lag`（正式入库，可复跑）：

1. 构建网页版 → 本地托管 → 无头 Chrome（**非默认调试端口**）；
2. CDP 发**真实鼠标点击**（不是 JS `.click()`，才会带上输入排队），按三段计时：
   `输入排队`（事件处理器开跑 − 浏览器给这次输入打的时间戳）＋ `提交`（新面板进 DOM − 处理器开跑）＝ `端到端`；
3. `Performance.getMetrics` 增量量主线程去向（任务／脚本／布局／样式）、`PerformanceObserver('longtask')` + rAF 采样量长任务与掉帧；
4. `Emulation.setCPUThrottlingRate` **降速倍率 N** 代理弱机（对比优化前后必须用同一个 N）；
5. **活值探针**：同一子页静置 5 秒，比面板全文行差 ⇒ 用来判"这块界面还活着吗"（防 `memo` 冻住实时数）。

存档：`docs/test-saves/save-20260920-164600.json.json`（后期档 466 KB · 组装机 151 张卡）。

### 1.1 一次切换要多久（端到端 = 玩家感受到的"点了到换过去"）

| 目标子页 | 面板节点 | 1× CPU | **6× CPU（弱机代理）** |
|---|---|---|---|
| ♨ 精炼炉 | 1,404 | 0.6 ms | 26 ms |
| ⚒ 组装机 | **8,298** | **154 ms** | **1,563 ms** |
| ⚓ 造船厂 | 3,367 | 79 ms | **1,660 ms** |
| ▦ 蓝图书架 | 148 | 11 ms | 166 ms |

连点 8 次的序列：1× 中位 **75 ms** / 最大 138 ms；**6× 中位 797 ms / 最大 1399 ms，最长长任务 1389 ms**。
逐次明细（1×）**高度可复现**：→ 精炼炉 21.5 与 25.3 ms · → 组装机 **138.2 与 133.2 ms** · → 造船厂 75.4 与 75.3 ms · → 蓝图书架 11.4 与 11.1 ms。

⇒ 两点结论：
- **同一张卡点两次（138.2 → 133.2 ms）几乎一样** ⇒ 每次都是**全量重建**，没有任何复用；
- 耗时几乎是节点数的线性函数：**≈16 µs/节点（1×）· 每张卡 ≈0.9 ms**。

### 1.2 挂机（不点任何东西）主线程被吃掉多少

| 当前子页 | 节点 | 1× 占用 | 6× 占用 | 活值变化行数（5 秒） |
|---|---|---|---|---|
| ▦ 蓝图书架 | 148 | 7.5% | 58% | 0（本就静态） |
| ♨ 精炼炉 | 1,404 | 27% | 102% | 21 |
| ⚓ 造船厂 | 3,367 | 22% | 110% | 105 |
| ⚒ 组装机 | 8,298 | 35% | 102% | **155** |
| 对照组：技能页（无重面板） | 1,471 | 15% | 97% | 1 |

- 提交次数实测 **1–2 次/秒**，与引擎 1 Hz 心跳对得上；每次提交 = **整棵 App 树重渲染**（`App.tsx` 的 `force()`）。
- 6× 下**整机被吃到 ~100%**：此时点任何东西都要排队（实测输入排队中位 22 ms、最大 54 ms），
  与"切换本身"叠起来就是秒级无响应 —— 与报障描述吻合，也解释了"32 核的船长只觉得轻微一顿"。

### 1.3 已排除的两条

- **引擎计算**：`npm run industry:perf` 全项 < 0.1 ms（上一稿已证），与"数秒"差 4~5 个数量级。
- **背景动画（星野/星云/氛围光）**：把背景层 `visibility:hidden` 做 **A/B/A/B 四窗交叉对照** ⇒
  主线程占用 13.7% → 9.2% → 9.3% → 11.2%，**方向不一致、不成立**（第一窗偏高是切页余温）。**不是它**。

## 二、根因（三条，均有读数）

1. **切换 = 冷启动重建**：`pages/IndustryPage.tsx:685~713` 是三元链，同一时刻**只挂载一个**子页 ⇒ 旧面板整棵卸载、新面板从零造。
2. **单卡很贵**：组装机 **55 节点/卡**（151 张）、造船厂 53 节点/卡（57 张）；大头是**每行材料**的
   「×N（原 ×M，折扣后）（仓库 K）⚒ 去精炼」——同一段里好几个 `span`，一行材料 ≈3~4 个节点。
3. **每秒 1~2 次整树重渲染**：卡片上写着**实时仓库数量**（组装机 5 秒内 155 行文本在变、造船厂 105 行），
   ⇒ 这些数**不能靠 `memo` 冻住**（冻住就变成"数字不再更新"的 BUG）。

## 三、改法（按性价比排序；第 1 步已在浏览器里**先试后报**）

### 第 1 步（一行 CSS · 已实测省一半）

在页面里**临时注入**这条 CSS 后重跑同一序列（不改产品代码）：

```css
.app-belt-card.is-assembler { content-visibility: auto; contain-intrinsic-size: auto 547px; }
```

| 目标子页 | 未注入 | 已注入 | 变化 |
|---|---|---|---|
| ⚒ 组装机 | 94.2 ms | **39.6 ms** | −58% |
| ⚓ 造船厂 | 50.4 ms | **30.3 ms** | −40% |
| 序列中位 | 50.2 ms | **30.0 ms** | −40% |

（6× 下同样有效：组装机 1111 → 503 ms、造船厂 629 → 330 ms、中位 612 → 313 ms。）

原理：屏外卡片**跳过布局与绘制**；但脚本仍要把节点造出来 ⇒ 只能省掉一半，实测正好一半。
⚠ **两处要船长定夺**：
- **观感归船长**（约定 §6）：这是样式改动，"滚动条跳不跳、卡片看不看得舒服"只有船长能判。
- **占位高度必须贴近真实卡高**：卡片是 4 列网格，行高随材料条数变化（实测行高 547 / 473 / 398 …，中位 473）。
  用 `auto 300px` 会把总高从 20455 压到 **13360**（−35%，滚动条会明显缩水）；
  用 `auto 547px` 是 **21397**（+4.6%）。且 `auto` 关键字会在卡片渲染过一次后记住真实高度 ⇒
  理论上是"越滚越准"，但**滚动过程中滚动条会有小幅变化**，这条必须船长看了才能定。

### 第 2 步（结构 · 治"每次切换都重建"）：子页**首次进入后保活**，切换只切显隐

- 效果：组装机第 2 次起切换 ≈ 一帧；**首次进入仍要 154 ms / 1.5 s**（除非同时减卡，见第 4 步）。
- 必须与第 3 步同做：四个面板同时挂在树上，若仍每 tick 全树重渲染，代价会 **×4**（一稿判断，仍然成立）。
- 行为变化（要船长点头）：面板内部的筛选／搜索／滚动位置**不再因切换而复位**；工业页常驻约 1.3 万节点。

### 第 3 步（结构 · 治"每秒整树重渲染"）：把**实时数**从卡片里拆出来

卡片格子整体 `memo`（props 先稳定化：`App.tsx` 的 `pageProps` / 内联 `onGotoMarket` 等箭头 / 卡片收到的
`productNode` 现为每次新建 ⇒ 必然击穿 `memo`），把「（仓库 K）」这类实时数字改成**自己订阅引擎的小叶子组件**
⇒ 每 tick 只更新几百个文本节点，而不是重建 8298 个元素。

- 收益（估）：组装机挂机占用 35% → 个位数；6× 下从"整机吃满"回到有余量。
- 风险：拆漏一处 ⇒ 那处数字不刷新。**本工具已带活值探针**（基线：21 / 155 / 105 / 0 行）⇒
  改完必须复跑并逐页对齐，**不许为 0**（蓝图书架除外）。

### 第 4 步（可选 · 治"首次进入"）：减卡内节点数

把一行材料的多个 `span` 合并（相同观感、更少节点）。这是**根上的减法**（151 × 55 → 目标 151 × 30 上下），
但**每一处都要过船长的眼**，建议单独排一期，不要与前三步混在一起。

### 不做 / 已否决

- **虚拟列表 / 分页**：视觉与交互都会变，且与"一级页内容完整装下、不许硬裁"的既有规矩摩擦（要做请船长另议）。
- **靠 `memo` 直接把卡片冻住**：会把实时仓库数量冻住（第二节第 3 条）。
- **"切换只隐藏不重渲染"单做**：每 tick 代价 ×4。
- **提高心跳间隔**（船长上次说的「先按A来」）：**实测无效**——挂机分支本来就 `pendingMs >= 1000` 才 `notify()`，
  已经是 1 Hz（实测提交 1–2 次/秒）。⚠ **请船长撤销这条**。
