# 工业页子页切换卡顿 · 定位与改法（2026-09-22 · 待实施）

> 状态：**定位完成 · 改法待船长拍板后实施**（未改产品代码）
> 起因（船长转玩家报障）：「点击工业内的的不同子页面，会出现数秒的卡顿后才会切换页面。」
> 船长补充（关键）：「**我开着快照的**」「**报障玩家的配置不清楚**」「**确实我自己切换组装机也会有一定的卡顿延迟**」

## 一、已排除：不是引擎计算

`npm run industry:perf`（后期档：物品 132 · 制造配方 151 · 舰船蓝图 57）：

| 计算 | 耗时 |
|---|---|
| `visibleItemDefs(ctx)`（渲染每帧调用） | 0.01 ms |
| 可见矿石过滤（精炼页 `oreDefs` 同式） | 0.01 ms |
| `oreAvailable` × 全部残骸/货柜（`boxDefs` 同式） | 0.01 ms |
| `refineRunViews(state, ctx)` | 0.01 ms |
| 组装机：全配方 `findBuildable` + `ownsBlueprint` | 0.02~0.04 ms |

**引擎侧合计 < 0.1 ms**。船长性能快照亦印证：`adv` 47 次共 **19 ms**（max 2 ms）。
⇒ **与"数秒"差 4~5 个数量级，core 计算不是原因。**

## 二、船长快照读到的真信号

| 指标 | 值 | 解读 |
|---|---|---|
| `adv` | 47 次 / 19 ms | 引擎推进极快 |
| `notify` | 66 次 / 362.9 ms（max **39.2**） | 同步通知链 ≈5.5 ms/次 |
| `commit` | 66 次 / 362.2 ms（max **39.2**） | 与 notify **几乎等值** ⇒ 时间花在**同步提交整棵 React 树** |
| `long` | **9 次 / 866 ms · max 171 ms** | 确有 171 ms 长任务 |
| `fps` | avg 58.7 · **min 5.75** | 平均流畅，有掉到 5.7 fps 的瞬间 |

⚠ **读数需打折**：船长是**开着监测**跑的，而监测路径会把渲染改成 `flushSync` 同步
（`App.tsx` PerfListener：`recording` 时 `flushSync(force)`）⇒ 提交耗时被放大。
**生产路径是异步渲染，会比这个读数好**；但下面的结构问题与读数无关，是真的。

## 三、根因（读代码确认，三条）

1. **同一时刻只挂载一个面板**：`pages/IndustryPage.tsx:685~713` 是三元表达式链
   （`craft / shipyard / refine / shelf`）⇒ 切换 = 旧面板**整棵卸载** + 新面板**冷启动重建**。
2. **⚠ 每秒（交火中每 100 ms！）整棵 App 树被强制重渲染**：
   - `App.tsx:380` `const [, force] = useReducer(...)`；
   - `App.tsx:275-289` `PerfListener` 在 `engine.subscribe` 里调 `force()`；
   - `engine.ts:790` `notify()` → **遍历全部 listeners**；心跳间隔 **挂机 500 ms / 交火 100 ms**。
   ⇒ **所有页面组件都没有 `memo`** ⇒ 工业页那个 151 行面板**每隔 100~500 ms 被全量重算一次**，
   与"玩家点没点它"无关。
3. **面板自建的派生模型很重**：`ManufacturingPanel` 每次渲染重建 **151 行**
   （每行跑 `canStartNow` / `bookPriceOf` / `productBaseOf` / `countModule`，并**当场造 ReactNode**）。

⇒ 合起来：**切换时承受"冷启动重建"，之后还持续承受"每 tick 全量重算 + 提交"**。
这也解释"您 32 核只是轻微一顿、弱机变成数秒"：同一份同步提交在弱机上被成倍放大，
**所以在强机上复现不出来**（报障玩家配置拿不到，正是这个原因）。

## 四、⚠ 船长提的两个解法，方向会**变坏**（已核代码）

| 设想 | 判断 |
|---|---|
| 「异步渲染各子页 + 进度条先暂停」 | 只改善**首次进入**的一次性卡顿；**每 tick 的全量重算照旧** ⇒ 根因不动。且预渲染 4 个面板会把每 tick 的重算量**放大 4 倍**。 |
| 「切换只隐藏、不重新渲染」 | **会明确变糟**：4 个面板同时挂在树上 ⇒ 每次 `force()` **4 个一起重算**（现在是 1 个）。隐藏解决"重建"，代价是"每 tick 重算 ×4"。 |

⇒ **"重建"不是主因，"每 tick 整树重算与提交"才是**。先治后者。

## 五、正解与实施顺序（船长已选「先按推荐的来」= 1+3）

1. **加 `memo` 边界 + 稳定 props**（治"每 tick 全树重算"）：
   - 把 App 里内联的 `onGotoMarket` / `onGotoWormhole` / `pageProps`（`App.tsx:800` 每次渲染新建对象）
     等**稳定化**（`useCallback` / `useMemo`）—— 否则 `memo` 会被**新引用击穿**；
   - 给 `ManufacturingPanel` / `ShipyardPanel` / `BlueprintShelfPanel` 加 `memo`。
   ⚠ **风险点（必须同时处理，否则会"冻结"实时读数）**：这些面板读的是**可变的 `engine.state`**
   （不是 React state），现在靠父级 force 才刷新 ⇒ 单纯 `memo` 会让进度条/库存**停止更新**。
   **正解 = 把"实时数"与"静态列表"拆开**：列表 memo，进度/倒计时另挂订阅或按 tick 单独更新。
2. **`ManufacturingPanel` 的 151 行模型 `useMemo` 化**（依赖 = 相关 state 切片），
   并让 `BlueprintCard` 的 props **不含每次新建的 ReactNode**（`productNode` 现为当场新建 ⇒ 必然击穿 memo），
   改为传数据、在卡片内部渲染。
3. （后续大改，可选）**把"全树 force"改成"分域订阅"**：顶栏/活动栏订 tick，当前页面按需订阅。

## 六、⚠ 实施前的诚实说明（这是我没有直接动刀的原因）

- **我无法在浏览器里验收**：§6 规定观感/交互类改动不许我自己起无头浏览器截图当依据；
  而这类改动**恰恰只能靠"点几次子页、看还卡不卡"来验收**。
- **我能验证的只有**：`typecheck` ×4 · core 测试不受影响（改的是渲染层）· `ui:rot-check` / `content:check` / `l10n:check`。
- **最危险的失败模式**：`memo` 边界加错 ⇒ **界面停止刷新**（进度条不动、库存不更新）。
  这种失败**静态检查发现不了**，而我不能开浏览器 ⇒ 一旦上线就是"卡顿没修好、反而多了个冻结 BUG"。
- ⇒ 因此建议：**改完后必须由船长在本地实测点几次子页**（关掉监测跑，避免 `flushSync` 污染对比）确认，
  再决定合入/推送。这条不是客套 —— 是本改动的**唯一可行验收手段**。
