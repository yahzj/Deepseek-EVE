# 证券交易所 · 并行化架构决策（交易所计算线独立）

> 状态：实施中　｜　日期：2026-11-03
> 船长口径（2026-11-03）：「这个架构不好的，不能多线程，我起码服务器的2核的呀，交易系统分离出来做并行」「把股市这条线单独并行运行把」
> 关联：`stock-exchange-backend-b0-20261103.md`（B0-1 已交付）、`stock-exchange-backend-spec-20261103.md`（契约）

---

## 结论先行

1. **现状确认**：whale-server 是单进程单事件循环，2 核机器上确实只吃 1 核；交易所的撮合、价格引擎、后续 AI 人格都会挤在这个循环里。
2. **并行手段选择**：Node 的真并行只有两种——`worker_thread`（同进程多线程）与 `child_process`（独立进程）。本批选 **worker_thread**：真吃第二核、资金零跨进程风险、部署与客户端零改动。
3. **职责划分（本批）**：**主线程** = HTTP/WS、鉴权、账本/钱包/落库/审计（**唯一写库者**）；**worker 线程** = 内存订单簿 + 撮合 + 序号分配（后续价格引擎/AI 也放这里）。
4. **资金不变量不动**：worker **不碰 SQLite**；所有资产变动仍由主线程单写、单事务，因此**不存在跨线程分布式事务**。
5. **阶段 2（规模化后）**：把 worker 提升为独立进程/服务，主服务反向代理 + 内部 localhost RPC + 幂等资金接口。设计已备，本批不做。

## 一、为什么不是现在就拆独立进程

| 维度 | worker_thread（本批） | 独立进程（阶段 2） |
|---|---|---|
| 并行收益 | ✅ 撮合/AI 用第二核 | ✅ 同样，还能独立扩容 |
| 资金一致性 | ✅ 主线程唯一写库，零分布式事务 | ❌ 需要内部 RPC + 幂等 + 对账 + 失败补偿 |
| 鉴权/会话 | ✅ 直接复用主线程内存 | ❌ 需要共享会话或内部鉴权 |
| 部署/客户端 | ✅ 同 systemd、同端口，客户端无感 | ❌ 新端口/代理/健康检查/两处日志 |
| 故障恢复 | 主线程重启 worker，从 DB 重建订单簿 | 需进程守护 + 主服务降级策略 |
| 适用时机 | **现在** | 交易所 CPU 成瓶颈、或需独立伸缩时 |

> 结论：先拿 worker 把「第二条核心」用起来；等实测不够用，再把同一模块边界升级为独立进程（届时只改传输层）。

## 二、本批架构（Stage 1：worker_thread）

```
┌─────────────────────────── whale-server 进程（2 核机器）───────────────────────────┐
│                                                                                   │
│  ┌────────────── 主线程（core #1）──────────────┐   ┌──── worker（core #2）────┐   │
│  │ HTTP REST / WebSocket                        │   │ 内存订单簿（4 标的）      │   │
│  │ 鉴权（sessions）                             │   │ 撮合（价格/时间优先）     │   │
│  │ 钱包 / 账本（唯一写库者）                     │◀─▶│ 序号分配（seq）          │   │
│  │ SQLite（WAL，全部写操作）                     │   │ 后续：价格引擎 / AI 人格  │   │
│  │ 交易所 API 门面（async）                      │   │ 不碰 DB、不碰文件         │   │
│  └──────────────────────────────────────────────┘   └──────────────────────────┘   │
│                              postMessage 命令/回执（下单→撮合→成交回传）              │
└───────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 命令与回执

| 命令 | 方向 | 内容 |
|---|---|---|
| `place` | 主 → worker | 已校验/已冻结资金的订单（含 maker 所需信息） |
| `cancel` | 主 → worker | 撤单（worker 返回是否已成交/剩余量） |
| `snapshot` | 主 → worker | 五档盘口/我的委托（查询用） |
| `restore` | 主 → worker | 启动时用 DB 里的未成交挂单重建簿子 |
| `fills` | worker → 主 | 本拍成交批次（主线程据此记账、写库、广播） |
| `tick` | worker → 主 | 状态变更通知（供 WS 增量推送，B0-2） |

### 2.2 资金不变量（不许破）

1. worker **不连 SQLite**、不写任何文件、不发网络请求；
2. 挂单冻结、成交划转、手续费、入金/出金全部由主线程在单事务内完成；
3. worker 崩溃/无响应 ⇒ 主线程拒绝新单并重建 worker，从 DB 恢复未成交挂单；
4. 同一订单的 `clientOrderId` 幂等仍由主线程保证。

### 2.3 启动与恢复

1. 主线程打开 DB → 读出所有 `open/partial` 挂单 → 发送 `restore` 给 worker；
2. worker 重建订单簿并校验 seq 单调（从 DB `max(seq)+1` 继续）；
3. 重建完成前交易所 API 返回 503 `exchange_starting`（短暂）。

## 三、阶段 2（独立进程）预留设计

- 部署：`whale-server`（8787，客户端入口，做反向代理）+ `whale-exchange`（8788，仅 localhost）。
- 鉴权：主服务校验 Bearer 后注入 `x-whale-account` + 内部共享密钥，exchange 只信任来自本机代理的请求。
- 资金：exchange 不直接改钱包；成交后调用主服务 `/internal/settle`（幂等 batchId），主服务写账本/钱包后回执。
- 数据：exchange 独立 SQLite 文件（订单/成交/审计），主服务的 `exchange_*` 表停写；迁移用一次性导出。
- 触发条件（达到任一即启动阶段 2）：撮合延迟 p99 > 50ms、exchange CPU 持续 > 30% 单核、需要独立扩缩容。

---

## 四、不做（本批）

- 不做独立进程/新端口/代理（阶段 2）
- 不做多 worker 池（4 标的用不上；AI 人格上量后再评估）
- 不引入 Redis/消息队列（单机 2 核，杀鸡用牛刀）

---

## 五、验收

1. `npm run typecheck` 零错误；`npm test` 全绿（基线 111 + 交易所用例）；
2. 行为不变：入金→挂单→撮合→成交→账本、自成交拦截、撤单退款、重启恢复全部保留；
3. **并行证据**：撮合/引擎在 worker 线程执行（日志打印 threadId 与主线程不同）；
4. **隔离证据**：人为让 worker 跑重计算时，主线程 `/health` 延迟不显著恶化（记录 p99）；
5. worker 强制崩溃后：主线程能重建 worker、恢复未成交挂单、拒绝新单期间返回明确错误码。
