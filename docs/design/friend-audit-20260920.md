### 五之一、MK2 弹药的"供应量 / 收购"实测（临时探针，用完已删）

**实测口径**：`buildSimContext()` + 真档 + 跑 **24 游戏小时**；① 挂一张高价买单 5,000 件看能买到多少；
② 挂一张贴买盘价的卖单 5,000 件看能卖掉多少；③ 记录 24h 后簿面；④ 记录池量。

| 商品 | ① 24h 能买到 | ② 24h 能卖掉 | ③ 24h 后簿面（NPC 供货 / 收购） | ④ 池量 |
|---|---|---|---|---|
| 动能弹药 MK2 | **67 件** | 5,000 件（贴买盘价 23） | 0 张 / 0 件 · 2 张 / 4 件 | 518,400 |
| 爆破弹药 MK2 | **81 件** | 4,998 件（贴买盘价 35） | 2 张 / 3 件 · 1 张 / 2 件 | 518,400 |
| 能量弹药 MK2 | **61 件** | 4,996 件（贴买盘价 50） | 3 张 / 7 件 · 1 张 / 2 件 | 518,400 |

**消耗侧**（`combat.ammoLoadTotals`：预载 = ⌈4 分钟 ÷ 装填 × 1.5⌉ 轮 × 每轮门数）：以 5 门动能炮（装填 2,380ms）
的巡洋舰算，**单舰单场预载 ≈755 发 · 4 舰编队 ≈3,000 发/场**（打完才扣、余弹退还）。

**⇒ 结论：一天能买到 61~81 发，一场战斗就要 ~3,000 发 —— 差 50~100 倍。**

**根因**：这三件**今天早些时候**被改判进「稀有订单」渠道（`marketCatalog.ts:181-188` 的注释记着这次改判）。
那条渠道是为"一件一件的稀罕货"设计的：每 10 分钟抽 `8%~15% × 已解锁稀罕货件数`（当前 rare 目录 **167 件**
⇒ 每轮 13~25 张单），**每张单只有 1~3 件**，还要在 167 件里加权分 ⇒ 单看一系弹药 ≈ 每 1~2 小时一张单、1~3 件。

**顺带发现两处口径残留**（无论选哪个方案都该一起理顺）：
① 卡片上的 `poolTarget: 518_400` / `supplyFlow: 4_320` 还在，而 `absorbBaseQtyOf` 仍按"池商品"读它
   ⇒ **站内吸收还是池级的**（贴买盘价挂 5,000 件当天全被吃掉）——买不到、却卖得掉，两头不对称；
② 那个 518,400 发的池**已经买不出来**（rare 不走常驻供货阶梯）⇒ 记着库存却拿不到货。

**三个方案（等你点头；数值都按上面读数标定）**

| | 甲案：回到常驻池 | 乙案：留在稀有订单 + 消耗品批量档 | 丙案：混合 |
|---|---|---|---|
| 做法 | 三件改回 `rarity: 'common'`，用卡片上现成的 `poolTarget 518,400 / supplyFlow 4,320` | 新增两个卡片字段：`rareQtyMul`（单张件数 ×N，例 **200** ⇒ 一张单 200~600 发）＋ `rareWeightMul`（抽取/收购权重 ×N，例 **20**） | 供货走池（甲）＋ 价格按稀有档（乙的半条） |
| 供货量 | 4,320 件/20 分钟 ≈ **31 万发/天**（够 ~100 场） | ≈ **4,000~24,000 发/天/系**（够几场~十几场） | 同甲 |
| 收购 | 同额吸收 ＋ 常驻收购单（看得见在收） | 收购单概率/件数同乘 ⇒ 每天几千件可见 ＋ 吸收保持 | 同甲 |
| 与今天那条裁定的关系 | **撤回**「弹药 MK2 移动到稀有订单」（§5.2 ⇒ 需你确认） | 保留裁定，只给消耗品破一个例 | 半撤回 |
| 改动面 | 3 行数据（改 rarity）＋1 处吸收口径 | 卡片字段 2 个 ＋ 抽取/刷单/收购 3 处接线 ＋ 契约 ＋ 用例 | 最大 |
| 我的建议 | **首选**：量级自动对齐既有标定，与"修理组件常驻可买可卖"同款 | 若你要保住"弹药 MK2 是稀罕货"的质感 ⇒ 选它 | 不推荐（改动最大、收益与甲接近） |

### 五之二、第 4 条详解（`tools/` 纳入 `npm run typecheck`）

- **现状**：`typecheck` 只跑 4 个 workspace（core / data / ui / desktop），`tools/` 在仓库根部、不属于任何 workspace
  ⇒ **一行都没被类型检查**。实证代价：`flow-newgame.ts` 的 `good.id`（字段不存在）就这么溜进仓库，
  直到朋友审计才发现（`tools/flow-newgame.ts:190`，已修）。
- **三条可行做法**：
  - **(a) 全纳入**：新增 `tools/tsconfig.json`（`extends` 根配置 + `jsx: react-jsx` + `include: tools/**/*.ts`），
    挂 `typecheck:tools` 并进 `npm run typecheck` 链。**前提是先清一轮存量错误**（历史经验：单独 tsc 过
    `content-check.ts` 就报过若干，多为 `--jsx` 未开、重复标识符、旧字段名）。工作量未知，得先出清单。
  - **(b) 白名单纳入**：只纳入常跑的那十几个（flow-newgame / make-test-save / liquidity-audit / wormhole-econ /
    content-check / skill-id-audit …），其余老工具留待逐个清理。马上能跑，代价是白名单要维护。
  - **(c) 不纳入 tsc，改运行期护栏**：像刚立的 `skill:audit` 那样，给"工具引用的关键 id/字段"各写一条体检。
    覆盖窄、成本高，只适合个别高频错点。
- **我的建议**：先让我跑一次 (a) 的**只读清单**（临时加一份 tsconfig、跑 tsc、把错误按"真错/无害/风格"分档，
  报告后删掉那份 tsconfig，不提交）⇒ 你拿清单决定是"全纳入"还是"白名单纳入"。**要不要现在出这份清单？**

### 五之三、第 5 条详解（`wormhole-econ` 政策补"清临时空间"）

- **现象**：`wormhole-econ --runs=20` 里 **2/20 趟记 `未结束`**，停止原因是引擎那句
  「临时空间里有 N 件没处理：先到「货仓」页放回货仓或丢弃，再继续」。原因不是游戏 bug，而是**工具政策缺一步**：
  洞内拿到装不进背包的大件会先落进"临时空间"，`wormholeTempBlockReason` 会拦下后续**扫描/前往**，而政策没有
  "处理临时空间"这个动作 ⇒ 那趟就停在那儿，收集物也不计入到手。
- **为什么现在才暴露**：改技能 id 之前编队"0 技能裸奔"，往往第一层就全损 ⇒ 根本活不到捡到大件那一刻。
- **影响面**：**只影响这个工具的读数**（游戏本体没问题，玩家在界面上会被明确提示去货仓页处理）。
- **两种修法**：① **照抄 `mt-harvest.ts` 的 `clearTempSpace(state, ctx)`**（把临时空间的件搬回货仓、
  放不下就丢 —— 与玩家在界面上的两条选择完全一致）⇒ 推荐，口径已被另一个工具验证过；
  ② 让政策"不捡装不下的大件" ⇒ 与玩家行为不一致，且要重写拾取判据，不推荐。
- **工作量/风险**：约 20~30 行（工具内）+ 重跑 20 趟读数（几分钟）；**只动工具、不动游戏**，风险低。
- **要不要现在做？**（做完我把 20 趟的干净读数给你，那份读数才对平衡判断有意义。）
