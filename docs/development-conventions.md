# 开发约定（Development Conventions）

> 本文件是仓库级"协作铁律"，与代码同等重要。**每一轮会话开工前，先读本文件。**
> 所有与用户（船长）的沟通、思考过程呈现、总结、文档、代码注释、日志一律使用中文。

---

## 一、确认流程（最高优先级，用户明确要求）

用户原话（语义记录）：

> "当你有疑问提问完后进行总结时，应该等我确认你的总结文档没有问题后再开始进行工作流程。"

### 适用场景（满足其一就必须走流程）
- 新的大功能 / 系统级改动（如：市场、战斗、舰队重构这类）；
- 涉及设计取舍、数值体系、存档结构（version 迁移）的改动；
- 用户需求模糊、有多个可选方案、或我判断需要拍板的地方；
- 用户没有明确说"开始做"的实现请求（先确认范围再动手）。

### 标准步骤（四步闸门）
1. **集中提问**：有疑问先一次性问完（不要边做边问）；
2. **中文设计总结**：给出完整总结（方案 + 关键取舍 + 涉及模块/数值 + 边界情况），
   并在结尾明确写"**以上总结请你确认，确认后我再开始实现**"；
3. **等待确认**：停手。**"用户没有反对" ≠ 确认**，必须得到明确的"可以 / 没问题 / 确认"；
4. **确认后实现**：开工，并把已确认的决策落进对应设计文档
   （`docs/design/…`，顶部标注"状态：已确认"）。

### 例外与回补
- **完全基于已确认设计的"执行落地"**（如 V9 市场系统：此前多轮确认过 V1→V5 总结，
  含"砸盘叠加上限不做限制"）可以继续实现；但每完成一个段落要主动向用户说明
  "这轮做了 X，基于你此前确认的 Y"，并给出复核入口（总结/文档）。
- 若实现中发现需要**推翻已确认设计**的重大问题：停下来重新提问 + 总结 + 等确认，
  不允许擅自替换方案。

### 红线
- 未确认不动工（设计未定的部分）；
- 不把"随便 / 你看着办 / 都行"当正式确认（需再追问一句明确范围）；
- 不在总结里藏私货：修改了什么、删了什么、新增了什么，必须列清楚，等用户看见。

## 二、思考与工作过程约定

### 动脑前先动手读
- 接手任何任务先读：本文件 → `docs/architecture.md` → 相关 `docs/design/` 文档 → 代码现状；
- 不凭记忆/猜测写代码：改结构前先查全部引用（界面、测试、工具脚本）再动手；
- 项目内已有"验证闭环"和"文档纪律"，新代码必须沿用，不要另起炉灶。

### 实施节奏
1. 大任务先列任务清单（分步、可见进度）；
2. 一次只推进一组相关改动，改完立即自检，避免长距离无验证的"连写"；
3. 每步自检闭环（见下），出现失败先查明原因再继续，不绕路；
4. 有疑问但用户不在场：记录下来进总结，不猜着做。

### 验证闭环（项目固定动作）
- `npm run typecheck`（core / data / ui / desktop 四包全绿）；
- `npm run test -w @whale/core`（vitest；改行为必须同步改/加测试，断言确定性优先）；
- `npm run build`（electron-vite）；结构改动后跑 Electron 冒烟 + 真实存档迁移检查
  （`%APPDATA%\whale-idle\save.json`，动它之前先备份）；
- 数值/经济改动跑 `npm run balance`（tools/balance-check.ts，三策略 24h 对比）；
- 临时调试文件（`tools/_*.ts`、`tests/_dbg.test.ts` 之类）用后即删。

### 汇报与文档纪律
- 每完成一段功能：中文汇报——**改了哪些文件 + 行为变化 + 验证结果 + 已知取舍**；
- 功能/方案设计 → `docs/design/`（标注确认状态）；结构/版本 → `docs/architecture.md`；
- 新约定、教训、决策 → 追加/更新本文件；
- 会话结束时若 Hindsight 记忆可用，把约定与已确认决策同步进记忆库；不可用则本文件即记忆。

## 三、多 agent 并行协作（大鲸鱼二号 / 其它会话）

> 背景：同一工作区可能有多条工作线并行（如"大鲸鱼二号"负责战斗系统与物品导入）。
> **本会话与二号没有直接通信通道**——用户是唯一协调桥梁；本会话通过共享文件系统观察对方。

### 疑似检测信号（命中任意即进入"疑似"状态）
- 一批文件在短时间内被批量改写（几分钟内十几个文件、mtime 密集变化）；
- 结构版本号/类型定义跳变（如 CURRENT_STATE_VERSION 突然 +1、新增 XXX.ts 基础设施文件）；
- 出现他人风格的大范围重构痕迹（新常量文件、类型字段扩充：ModuleSlot 增加槽位、ShipDef 增加字段等）；
- typecheck/测试突然大面积红且报错指向"我最近没碰过的文件"。

### 发现疑似时的行为（先停手，再报告）
1. **立即停止写入**疑似重叠区域：不覆盖、不回滚、不替对方"修复"中间态；
2. **核对自己的改动是否存活**（grep 关键函数/常量），并确认对方改动是否基于我的代码之上；
3. **第一时间向用户报告**，格式固定：
   - 证据（文件清单 + 时间窗 + 内容推断）；
   - 影响面（红测试/编译阻塞清单；波及哪些我的成果）；
   - 我的判断（中间态 or 已完成；与分工的重叠点）；
   - 交接建议与"完成信号"（如 typecheck 全绿 = 可以接手的明确信号）；
4. 用户协调明确前，对相关区域保持**只读观察**；收到指示后再继续（等对方合入 / 我接管 / 分区并行）。

### 协作红线
- 同一文件双方都需要改 → 默认让用户协调错峰，不抢先覆盖；
- 不做"预防性重构"去适配对方未完成的设计；
- 对方完成后要求我适配（如 UI 跟随新类型）时，先确认其"完成信号"再动手。

## 五、检索纪律（用户 2026-09-04 定）

> 查找某个物品/条目/字段并定位其文本时，**尽量不靠上下文，而是依靠 id/唯一键快速检索**。

- 本仓库全部内容与状态对象都以 **id / key 为主键**（item/anomaly/belt/galaxy/skill/module/ship 的 `id`、
  市场 `good.key`、类型字段名、存档字段名），可做到快速精确检索：
  1. **首选 grep 唯一锚点**：如 `id: 'ore-glowstone'`、`good.key: 'gas-neon'`、字段名 `standingReq`；
  2. **改条目文本/数值**：先以该条 id 定位所属块，再在该块内作小范围修改，**禁止用整段长文本
     近似匹配去做改写**（易与另一条相似文本误匹配、也易受文案改版影响）；
  3. **文案重写**：按 id 索引定位 `description:` 所在行，整行替换（不必先猜旧文案全文）；
  4. 需跨表核对时可用一次性 node/tsx 脚本读取 data 目录做结构化查询（如安全等级/距离矩阵），
     用后即删（`tools/_*.cjs|ts`）；
  5. 无 id 的纯文案场合（日志/提示语）才回退到"少量上下文 + 唯一化判断"。
- 好处：检索与替换稳定、不误伤、对内容演进的改动（改名/改文案）免疫。

## 六、会话续接与压缩纪律（用户 2026-09-04 定）

> 目标：把"上下文压缩导致细节丢失"的影响降到最低，让长会话/跨会话工作流稳定续接。

事实与机制（对船长透明）：
- 模型**无法读取剩余上下文配额，也无法主动触发压缩**——压缩由运行环境在轮次边界自动进行
  （本仓库会话已验证：自动压缩后同一工作线无缝续接，磁盘上的代码/存档/文档不受影响）；
- 压缩的真正风险只在"尚未落进文件的口头约束 / 进行中任务的精确下一步"这类对话内细节。

纪律（我方承诺执行）：
1. **里程碑即固化**：每个已确认功能完成 → 落 `docs/design/`、`architecture.md`、本文件（文档即记忆）；
2. **新系统级大工程开工前，主动提醒船长"此处是良好压缩点"**，并先产出「续接卡」：
   下一步、涉及文件、验证状态、待确认项——再开始动手；
3. 每轮汇报末尾保留"下一步"要点（便于 checkpoint 提取与船长跟进）；
3b. **批量需求纪律（船长整批下发 roadmap 置顶单时）**：默认逐条走四步闸门；归类"可直接执行"须先说明归类理由；**任何含糊表述一律先问清，禁止以合理猜测替代**——对确认流程红线的强化；
4. 船长可随时要求"整理续接卡"或"先固化状态"——我方立即把当前会话状态写入文档/列表再继续；
5. 开启全新会话接力时：先读 本文件 → 相关 design 文档 → 续接卡/变更记录，再动代码。

## 七、沟通与语言
- 一律中文：面向用户的叙述、推理过程呈现、总结、文档、代码注释、游戏内文案、日志；
- 汇报不刷屏：结论先行（做了什么 / 能否用 / 有什么坑），细节附录或展开待问；
- 用户给出新约束时：先复述确认（一句话），再落进本文件/设计文档，形成闭环；
- 船长询问"下一步 / 新工作流 / 继续做什么"时，**先读 `docs/roadmap.md`（后续工作流备忘）再讨论**；roadmap 状态随采纳/完成情况同步更新。

## 八、测试门槛存档约定（船长 2026-09-04 定）

> 目的：大功能交付后船长能立刻实测，不需要手工改存档凑测试条件。

- **适用判定**：批次 B（大系统/结构级/规则数值）与新玩法数值的首次交付；批次 A 小修不配。
- **交付物（双份）**：
  1. 仓库内可复现脚本 `tools/make-test-save.ts`（按功能注入门槛）；
  2. 交付时运行脚本生成的存档文件 + 说明，落 `docs/test-saves/`（README 记录加载方法）。
- **注入基础**：**基于船长当前真档复制注入**（保留其现有进度；运行前自动把真档备份到输出目录旁，绝不写坏原档）。
- **加载方法**（交付说明内固定写明）：游戏内先「存档管理 → 备份」→ 退出游戏 → 用生成的存档文件替换
  `%APPDATA%\whale-idle\save.json` → 启动即测；测完可用游戏内恢复备份回原档。
- **注入原则**：只补"难达成的门槛"（资金/声望/星系点亮/舰船/核心/装配弹药等），
  可达成的操作（跑一段航程、点一个按钮）不代做；注入前后各写一条 system 日志说明；
  走 loadSaveFile/serializeSaveFile 保证字段合法与版本兼容。
- **功能门槛注入以 case 注册制扩展**：每个功能一个 case（b1 = 低安遭遇…），列表维护在脚本头注释。

## 九、UI 风格一致性（船长 2026-09-04 定）

> 做任何界面调整 / 新增界面元素前，**先查看同级的其它相似界面是否已有规范风格**，
> 复用既有类名与结构，不另起炉灶、不自造一套"看起来差不多"的新样式。

- 页面级「功能标签页」规范 = 星图页的 `.app-subtabs / .app-subtab`（胶囊按钮 + 图标 +
  label，激活青色高亮，`role="tablist"/"tab"` + `aria-selected`）——示例：物品页
  「仓库/货仓」子标签已按此统一；
- 行级列表/卡片规范 = `.app-inv-list/.app-inv-row`、`.app-shipchip`、`.app-btn`
  家族、`.app-subtab` 等既有样式；新增页面先 grep 同级页面与 styles.css 是否已有
  同类实现再动手；
- 命名沿用 `app-` 前缀与状态后缀（`is-active`/`is-warn`…）；CSS 尽量只补缺口，
  不重定义既有组件样式。
