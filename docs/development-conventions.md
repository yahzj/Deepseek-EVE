# 开发约定（Development Conventions）

> 本文件是仓库级"协作铁律"，与代码同等重要。**开工先读仓库根 `AGENTS.md`**（可执行精简版 + 按任务类型的
> 「文档目录」），再按目录**只读本次任务需要的那几份**；本文件作为权威正文详读的场合 = 首次接手 / 大工程开工 /
> 压缩续接后（见 `AGENTS.md` §0）。所有与用户（船长）的沟通、思考过程呈现、总结、文档、代码注释、日志一律使用中文。
>
> **章节编号说明**：正文为 **一 / 二 / 三 / 五 ~ 十五** 章——**第四章自本文件建立时即为缺号**（历史遗留），
> **编号不回收、不重排**，以免破坏全仓按号引用（如"§八 测试档""§九 UI""§十一 术语""§十四 表现层"）。

## 一、确认流程（最高优先级，用户明确要求）

用户原话（语义记录）：

> "当你有疑问提问完后进行总结时，应该等我确认你的总结文档没有问题后再开始进行工作流程。"

### 适用场景（满足其一就必须走流程）
- 新的大功能 / 系统级改动（如：市场、战斗、舰队重构这类）；
- 涉及设计取舍、数值体系、存档结构（version 迁移）的改动；
- 用户需求模糊、有多个可选方案、或我判断需要拍板的地方；
- 用户没有明确说"开始做"的实现请求（先确认范围再动手）。

### 标准步骤（四步闸门）
1. **集中提问**：有疑问先一次性问完（不要边做边问）；
2. **中文设计总结**：给出完整总结（方案 + 关键取舍 + 涉及模块/数值 + 边界情况），
   并在结尾明确写"**以上总结请你确认，确认后我再开始实现**"；
3. **等待确认**：停手。**"用户没有反对" ≠ 确认**，必须得到明确的"可以 / 没问题 / 确认"；
4. **确认后实现**：开工，并把已确认的决策落进对应设计文档
   （`docs/design/…`，顶部标注"状态：已确认"）。

### 例外与回补
- **完全基于已确认设计的"执行落地"**（如 V9 市场系统：此前多轮确认过 V1→V5 总结，
  含"砸盘叠加上限不做限制"）可以继续实现；但每完成一个段落要主动向用户说明
  "这轮做了 X，基于你此前确认的 Y"，并给出复核入口（总结/文档）。
- 若实现中发现需要**推翻已确认设计**的重大问题：停下来重新提问 + 总结 + 等确认，
  不允许擅自替换方案。

### 红线
- 未确认不动工（设计未定的部分）；
- 不把"随便 / 你看着办 / 都行"当正式确认（需再追问一句明确范围）；
- 不在总结里藏私货：修改了什么、删了什么、新增了什么，必须列清楚，等用户看见。

## 二、思考与工作过程约定

### 动脑前先动手读
- 接手任何任务先读：**仓库根 `AGENTS.md`**（2026-09-06 建立：可执行精简版约定，随会话自动注入上下文；**压缩/续接后若上下文中未见其内容，先重读它**）→ 按其 §0.1 指引读 **`docs/catalog.md`**（文档目录），**只读本次任务需要的那几份**（本文件、`docs/architecture.md`、相关 `docs/design/` 文档）→ 代码现状；
- 不凭记忆/猜测写代码：改结构前先查全部引用（界面、测试、工具脚本）再动手；
- 项目内已有"验证闭环"和"文档纪律"，新代码必须沿用，不要另起炉灶。

### 报障处理：**玩家反馈的问题不在本地存档**（船长 2026-09-18 定）
- **原话（照抄）**：「**并不是本地存档。但是同意将UI改成按批制作。建议加入提示，所有玩家反馈的问题，并不在本地存档。**」
- **口径**：玩家报障说的是**他们自己那份线上档**上的现象 —— **本地（船长）存档与此无关，也绝不允许拿它去"复现/验证/覆写"**
  （真档只读纪律见 §四）。⇒ 处理报障的**唯一正道 = 从代码与真引擎复现**：写一次性探针（`tools/_*.ts` 或
  `packages/core/tests/_probe-*.test.ts`，用完即删）或加确定性用例，把"玩家看到的那句话"还原成引擎里的数与文案。
- **为什么单列一条**：本地档看不见玩家的库存/进度/技能组合，**按本地档猜原因必然跑偏**（典型如"玩家的目标数
  与引擎计数单位不一致"这类口径问题，本地档里根本看不出来）。
- **收尾要求**：报障结论要写清 **①复现路径 ②根因（代码位置） ③玩家可见现象为什么长这样 ④改法与影响面**；
  若结论是"设计如此"（如材料耗尽自动停线），要把**提示是否够醒目**一并给船长裁。

### 实施节奏
1. 大任务先列任务清单（分步、可见进度）；
2. 一次只推进一组相关改动，改完立即自检，避免长距离无验证的"连写"；
3. 每步自检闭环（见下），出现失败先查明原因再继续，不绕路；
4. 有疑问但用户不在场：记录下来进总结，不猜着做。

### 验证闭环（项目固定动作）
- `npm run typecheck`（core / data / ui / desktop 四包全绿）；
- `npm run test -w @whale/core`（vitest；改行为必须同步改/加测试，断言确定性优先）；
- `npm run content:check`（内容契约体检）与 **`npm run ui:rot-check`**（**旋转口径体检 · 2026-09-14 起为第五道闸门**，
  船长定：手机竖屏自动横屏是"逻辑空间 1200 × `--mob-h`"，凡用 `vw`/`vh` 定尺寸的覆盖层必须按逻辑空间同轴覆盖、
  窄窗媒体查询在旋转下不许误触发、侧栏让位只许收内边距；只读 `styles.css`、不用浏览器）；
- `npm run build`（electron-vite）；结构改动后跑 Electron 冒烟 + 真实存档迁移检查
  （`%APPDATA%\whale-idle\save.json`，动它之前先备份）；
- 数值/经济改动跑 `npm run balance`（tools/balance-check.ts，三策略 24h 对比）；
- **任务/次数链/市场收入/技能训练 的"要多久"读数**跑 `npm run balance:chains`（`tools/chain-balance.ts`，
  2026-09-18 立：船长审「全部级别完成要多久」时把四个临时探针合并入库）——四段 `tasks`（13 条「第一次」
  任务各自耗时，能跑引擎的实跑）· `chain`（13 条次数链顶档 ＋ 逐级累计，读 `CHAIN_TIERS`，改表后重跑即得新读数）·
  `market`（交易收入链：各矿种满产卖出的 ISK/小时 ＋ 市场吸纳上限对照）· `skills`（训练时长与满级总级数）；
  可只跑一段：`npm run balance:chains -- chain`；
- 临时调试文件（`tools/_*.ts`、`tests/_dbg.test.ts` 之类）**不一律"用后即删"**：按工具纪律
  （第十章）收尾二选一——有复用价值转正式入库，确属一次性才删除。

### 汇报与文档纪律
- 每完成一段功能：中文汇报——**改了哪些文件 + 行为变化 + 验证结果 + 已知取舍**；
- 功能/方案设计 → `docs/design/`（标注确认状态）；结构/版本 → `docs/architecture.md`；
- 新约定、教训、决策 → 追加/更新本文件；
- 会话结束时若记忆工具可用（DSH 的 memory），把约定与已确认决策同步进记忆库；不可用则本文件即记忆。

## 三、多 agent 并行协作（一号 / 二号 d2 / 三号 verify / 其它会话）

> 背景：同一工作区可能有多条工作线并行（如"大鲸鱼二号"负责战斗系统与物品导入）。
> **本会话与二号没有直接通信通道**——用户是唯一协调桥梁；本会话通过共享文件系统观察对方。

### 疑似检测信号（命中任意即进入"疑似"状态）
- 一批文件在短时间内被批量改写（几分钟内十几个文件、mtime 密集变化）；
- 结构版本号/类型定义跳变（如 CURRENT_STATE_VERSION 突然 +1、新增 XXX.ts 基础设施文件）；
- 出现他人风格的大范围重构痕迹（新常量文件、类型字段扩充：ModuleSlot 增加槽位、ShipDef 增加字段等）；
- typecheck/测试突然大面积红且报错指向"我最近没碰过的文件"。

### 发现疑似时的行为（先停手，再报告）
1. **立即停止写入**疑似重叠区域：不覆盖、不回滚、不替对方"修复"中间态；
2. **核对自己的改动是否存活**（grep 关键函数/常量），并确认对方改动是否基于我的代码之上；
3. **第一时间向用户报告**，格式固定：
   - 证据（文件清单 + 时间窗 + 内容推断）；
   - 影响面（红测试/编译阻塞清单；波及哪些我的成果）；
   - 我的判断（中间态 or 已完成；与分工的重叠点）；
   - 交接建议与"完成信号"（如 typecheck 全绿 = 可以接手的明确信号）；
4. 用户协调明确前，对相关区域保持**只读观察**；收到指示后再继续（等对方合入 / 我接管 / 分区并行）。

### 协作红线
- 同一文件双方都需要改 → 默认让用户协调错峰，不抢先覆盖；
- 不做"预防性重构"去适配对方未完成的设计；
- 对方完成后要求我适配（如 UI 跟随新类型）时，先确认其"完成信号"再动手。

> 船长拍板：既然用了 git，两个 agent 的工作区相互独立。

- **物理隔离**：主工作树 `H:\大鲸鱼\Deepseek-EVE`（分支 main，一号/船长独占）；二号工作树
  `H:\大鲸鱼\Deepseek-EVE-d2`（同仓 `git worktree`，分支 `d2/*`，2026-09-05 建立）；三号工作树
  `H:\大鲸鱼\Deepseek-EVE-verify`（同仓 `git worktree`，分支 `verify`，2026-09-09 建立 —— 核验与收尾，
  **分支名叫 verify、不叫 d3**，勿混）。
  二号/三号**永不直接写主树文件**，一切改动在各自工作树完成并提交。
- **基线同步**：各自开工前 `git fetch . main`（同仓）确认基线；主树有一号未提交 WIP 时视基线
  未定型，等稳定 commit 再动手/合入。
- **完成即合入（船长原话："每完成一次安排的工作后就进行合并"）**：完成一件安排的工作、

  `git fetch . main` + rebase/merge 解冲突，确认主树干净（无未提交改动）后在主树执行 merge；
  合完自己工作树追平 main 并清理临时分支。三号的舞步同此（verify 提交 → `merge main` 解冲突 → 主树 ff）。
- **推送闸门（船长 2026-09-08 定，与公告发布同批）**：**开发/推进过程中只做本地 commit，不推送
  `origin`**；只有在该工作**确实完成**（自测全绿 + 船长验收口径满足，含大更时公告稿已通过

  未完成批次即使已本地提交也留在本地，标注"待验收/待发布"；
  需要远程同步的临时理由（如二号合并需要主树基线推送）先问船长。

  （不写持久 git 配置；若日后代理端口变化，以系统代理设置/监听端口为准）。
- **文档同步（船长 2026-09-05 定）**：docs 目录留在主树仓库内，是**唯一权威**；二号 d2 工作树

- **真档与实测**：涉及 %APPDATA% 真档的操作只读或走副本备份，绝不覆写一号正在玩的档。

### 合入与批量文档写入的编码纪律（船长 2026-09-12 定）
> 背景：2026-09-12 二号在 d2 解两次合并冲突时，`docs/roadmap.md` 被写成「UTF-8 文本按 GBK 解码后又存回 UTF-8」
> 的**转码产物**（449 / 548 行乱码、10,460 字），并**丢掉 19 行正文**（含 `## C./D./E.` 三个分节标题、一条待办）；
> 而 typecheck / core 测试 / `content:check` **全绿都发现不了**（纯文档，无任何自动门禁覆盖）。船长裁定：**新增本条纪律**。

- **首选：让 git 自己物化文件**——取任一历史/对方版本一律用 `git checkout <rev> -- <path>`（或
  `git restore --source=<rev> <path>`）直接落到工作树，**不要**「读进变量再写回」这条中转路径。
- **必须经变量时，编码显式**（本机 `pwsh` 工具实为 **Windows PowerShell 5.1**，不是 PowerShell 7）：
  ① 收外部命令输出用 .NET 显式编码（`ProcessStartInfo.StandardOutputEncoding = [Text.Encoding]::UTF8`）；
  ② 写回用 `[System.IO.File]::WriteAllText($p, $t, [Text.UTF8Encoding]::new($true))`；
  ③ **禁止** `Set-Content` / `Out-File` / `>` 不带 `-Encoding` 落中文盘；
  ④ `_` 前缀探针脚本若含中文，**先加 UTF-8 BOM 再交给 `powershell -File` 跑**（5.1 按 ANSI 读无 BOM 脚本会破坏中文）。
- **⚠ .NET 文件 API 必须用绝对路径（2026-09-12 事故，二号）**：`[System.IO.File]::ReadAllText('相对路径')` 是按
  **.NET 进程的当前目录**解析的，**不等于** PowerShell 的 `Get-Location`——实测脚本已 `Set-Location` 到 d2，
  相对路径却落到了**会话工作区根**（`H:\大鲸鱼`）⇒ 读失败后**代码仍继续执行写入**，把 `docs/roadmap.md`
  **写成 0 字节**。纪律：① .NET 文件 API 一律传**绝对路径**；② **写前先校验读到的内容**（行数 / 关键锚点行文本），
  不符预期就 `exit`，**绝不带着空数据往下写**；③ 写前把预期结果算出来比一比（如「新行数 = 旧行数 − 3」），不符即中止。
- **⚠ 递给原生命令的参数里禁带双引号（2026-09-19 立 · 二号 · 船长点名「提前规避」）**：本机 `pwsh` 是
  **Windows PowerShell 5.1**，它把参数递给原生进程（git / node / tsx …）时**自己拼一条命令行**，参数内的
  `"` **既不被转义也不被保留**——实测 `$s = 'a "b" c'` 经 `node -e … $s` 到达时变成 `a b c`（引号凭空消失）；
  长文本还会被**按空格/换行切成多个参数**（`git commit -m $msg` 于是把提交消息切成一堆 pathspec 报
  `did not match any file(s) known to git`，**消息越正式越容易中招**）。**纪律四条**：
  ① **多行文本或含引号的文本，一律走"写文件 + `-F`"**——**首选现成工具 `npm run commit:msg`**
  （`tools/commit-msg.ts`：消息从 **stdin** 进来、自带编码自检与预览，内部就是写 `$TEMP` 临时文件 + `git commit -F`，
  用完即删）；⚠ **要给 git 传参数（如 `--amend`）时，分隔符必须写成 `'--'`**——PowerShell 会把**裸 `--`**
  当自己的"参数结束"标记吃掉，`npm run commit:msg -- --amend` 到不了脚本（实测参数被当 npm 配置丢掉）；
  也可直连 `npx tsx tools/commit-msg.ts --amend`。手工做法同理：`git commit -F <临时文件>`，
  消息文件写 `$env:TEMP`、不在仓库留垃圾，写盘仍按上条用 .NET 显式 UTF-8；
  ② 短消息**宁可避开 `"`**：中文引号一律用「」；
  ③ 单引号 here-string `@'…'@` **只保证 PowerShell 自己不解析内容**，**不保证原生侧收到原样**
  ⇒ 别把 `-m $msg` 当安全路径（已两次踩：提交消息被吞引号 + 被切碎）；
  ④ 同族坑（同一台 5.1）：**没有 `??`**（直接语法错）· **双引号串里反引号是转义符**（`` `r`n `` 才是换行，
  单引号串里反引号是普通字符）· 单引号串里要写字面单引号得写成 `''`。
- **写坏了怎么救**：合并冲突中把某文件写坏，用 **`git checkout -m -- <path>`** 可就地**重建该文件的冲突态**
  （两侧版本都在库里，**内容零损失**），再用正确写法重做——**不要**凭记忆重写，也不要急着 `git merge --abort`
  （那会连已解好的其它文件一起丢掉）。
- **合入或批量写文档后必做三条自检（读数写进汇报）**：
  ① **BOM 与行尾**与改动前一致（本仓库 .md 普遍带 BOM）；
  ② **乱码自检**：逐行做**往返解码**测试——`UTF8.GetString(GBK.GetBytes(行))` 若能还原出「的 / 了 / 是 / 在」这类
  常用字，该行就是转码产物（**全仓文本文件应 0 命中**；只查某个特征字会漏检，2026-09-12 实测踩过）；
  ③ **覆盖自检**：与合并的**两侧父提交**逐行比对——**父提交里有的行，结果里必须还在**
  （「两侧都有、结果却没有」＝**丢行事故**）。

## 九、UI 风格一致性（船长 2026-09-04 定）

> **底层规则（船长 2026-09-06 升格）**：任何位置**新增内容**——新卡片/新行/新弹层/新标签页/
> 新页面/新图标/新增文案位——样式一律**优先参考"同级下的其它相似项"**：同列表或卡片组内的
> 相似项 > 同页面其它区块 > 同功能模块其它页面 > 全仓 `app-*` 家族（styles.css）。先复刻既有
> 结构与类名、再按需做最小差异，禁止另起炉灶自造"看起来差不多"的新样式——避免风格割裂。
> （做任何界面调整同理：先对照同级是否已有规范风格。）

- **先复刻后差异**：新内容落地前先找同级相似实现（同款卡片/行/按钮/弹层），复制其
  结构 + 类名再改差异部分；不确定"同级相似项"是谁时，对照最接近的既有界面或先问船长；
- 页面级「功能标签页」规范 = 星图页的 `.app-subtabs / .app-subtab`（胶囊按钮 + 图标 +
  label，激活青色高亮，`role="tablist"/"tab"` + `aria-selected`）——示例：物品页
  「仓库/货仓」子标签已按此统一；
- 行级列表/卡片规范 = `.app-inv-list/.app-inv-row`、`.app-shipchip`、`.app-btn`
  家族、`.app-subtab` 等既有样式；新增页面先 grep 同级页面与 styles.css 是否已有
  同类实现再动手；
- 命名沿用 `app-` 前缀与状态后缀（`is-active`/`is-warn`…）；CSS 尽量只补缺口，
  不重定义既有组件样式。
- **尺寸稳定性规范**（船长 2026-09-05 定）：窗口/容器/卡片/格子尽量用固定尺寸
  （固定 height / min-height / grid 等宽列），**不允许随内容物变大变小**——装备入槽、
  文案换行等状态变化不得引起界面跳动；设计时按最大情况预留空间（长名
  `text-overflow: ellipsis` 单行截断、图标行固定行高、状态后缀元素计入高度）；
  空态与满态共用同一盒模型（含 `box-sizing: border-box`），只换内容不换尺寸。
  实证：装配页槽位格在装入装备后高度变化，已修（`.app-fit-slot-icon` 固定 76px）。
- **一级页不滚 / 滚动只进二级窗口**（船长 2026-09-08 定）：
  ①一级页 = 导航栏直系页（星图/舰船/装配/物品/市场/工业/技能）：**整页无页面滚动条**，
  页面高度 = 主窗口内容区高度（导航/活动栏固定），溢出滚动一律放进**二级窗口**
  （页面内标签页/功能窗的列表、卡网格、表格等内部滚动条）；
  ②**前提红线：一级不滚仅在其内容能被窗口完整装下时成立**——不得为了去掉滚动条
  而硬裁/隐藏任何应有内容；内容确实放不下、又无法拆分进二级窗口的页面，
  **单独提出与船长讨论修改方案**，不擅自强行落地；
  ③二级窗口滚动统一走既有内滚样式族（`.app-*` 列表/网格 + `overflow-y:auto;
  min-height:0`），滚动条不新造样式。

- **整页内容有最大宽度 `--app-max-w`**（船长 2026-09-13 定，起因「有玩家反应，当屏幕偏长时，
  游戏界面过宽」）：顶栏 `.app-header` 与工作区 `.app-workspace` 各自
  **`width:100%` + `box-sizing:border-box` + `max-width:var(--app-max-w)` + 左右 `auto`**
  ——窗口比 `--app-max-w`（当前 1760px）宽时内容整块**居中**、两侧露出宇宙底图
  （= 天然"填充空白"，不另画占位）；**没超过时逐像素不变**。
  两个已踩过的坑：①**只写 `max-width` + `margin:auto` 不行**——纵向 flex 交叉轴的 auto 外边距
  会取消 stretch，顶栏缩成内容宽；②**`width:100%` 必须带 `box-sizing:border-box`**，否则内边距
  算在宽度之外（"100% + 32px"）⇒ 普通窗口被挤出横向滚动条。
  实测读数：1600 窗口 `x=0 · w=1600`（与改前一致）· 2560 `x=400 · w=1760` · 3440 `x=840 · w=1760`，
  三档**页面滚动条 0 / 横向滚动 0**。**不套这层**：全屏覆盖层（战斗画面 = 按窗口铺开的场景；
  弹层/详情自带宽度上限并居中）。新增一级页/顶栏元素时**不要**自己写死宽度绕过这一层。

- **视觉物件一律 SVG 线稿**（船长 2026-09-10 定）：游戏内新增/改绘的**图形物件**
  （舰船/敌舰等大形资产、以及小视觉件 = 状态小窗的飘浮物、开火闪光、弹道点、
  场景点缀等一切"看得见的形状"）一律用 **SVG 绘制**——线稿语言与既有舰船资产
  同源（细描边轮廓 `currentColor` 可配色、面板/点缀件用类控制、`viewBox`
  本地坐标）；**禁止用 CSS 拼形状**（`clip-path` 多边形、伪元素画的形、CSS
  渐变裁出的轮廓、`border-radius` 拼图等）——背景氛围光效（渐变/光带/光晕）
  不属于"物件"，可用 CSS；浮动物件动画（平移/自转/闪烁）作用于 SVG 元素即可。
  实证：导航舰船状态窗的采矿小行星/残骸碎片/信号点/炮口火光由 CSS 形状重绘为
  SVG 线稿（ShipStatusWin.tsx）。

- **悬停提示一律走自绘接管层**（2026-09-13 一号固化，源自船长报障的"实时 `title` 旧提示"BUG）：
  玩家可见的悬停说明**只写 `title` 属性**，由 `ui/Tooltip.tsx` 的单例层统一接管
  （限宽 300px · 多行 `pre-line` · 悬停 200ms 才弹 · 跟随鼠标 · 边缘翻转）——
  **不许**另起悬停/浮层机制，也不许为"想多行好看"把它改写成 `data-*` 或自绘气泡。
  **实时读数的 `title`（内容每拍在变，如活动栏「工业 ×N」徽标）不需要任何特殊处理**：
  展示期间该层挂了**只盯 `title` 属性**的 `MutationObserver`，React 把新 `title` 写回来就**再摘一次**
  并把提示内容刷成新值（否则写回来的 `title` 会让浏览器**原生提示**与自绘提示同时显示）；
  新增这类 `title` 时照常只写 `title`，**不要**在展示期间直接操作提示层 DOM。
  实证：2026-09-13 修「悬停工业 AI 徽标久了冒旧 title」（读数：修后 `title` 缺席 5/5 采样，
  反向对照 4/5 被写回）。
  - **2026-09-14 修订（船长报障「部分情况仍会出现系统默认的鼠标悬浮 title 窗口」后 · 船长裁定"甲"）**：
    ①**SVG 元素用 `data-tip`**——`title` 属性在 React 的 SVG 类型里**不接受**（这正是历史上两处写成
    SVG `<title>` 子元素的原因），故 SVG 里的悬停说明一律写 `data-tip="…"`，**仍然进同一个接管层**
    （作者属性、无需摘除，本层按 `title` > `data-tip` > 暂存的优先级识别）；
    ②**禁止 SVG `<title>` 子元素**：它不是属性、接管层看不见 ⇒ 浏览器按 SVG 标准弹**系统默认**提示
    （实证：`closest('[title]')` 命中不到、`<title>` 子元素仍在）。机制层已兜底（命中就**清空该
    `<title>` 文本**、离开放回；只清文本不摘元素，避免 React 卸载时 `removeChild` 抛错），
    体检另加「悬停提示契约」静态守卫（渲染层出现 `<title` 即红）；
    ③**进入事件按"外层→内层"顺序派发**：接管层记录"指针所在元素"时**不能**因"新目标是旧目标的
    子元素"就早退，否则 `hovered` 停在最外层容器、内层永远轮不到接管（2026-09-14 真产物端到端
    实测到该回归并已修）；同属一个提示归属元素时延迟不重启，跨归属才重开一轮。
    实测读数（真产物 `web/dist` + 无头 Chromium 真鼠标）：HTML 按钮悬停 ⇒ `.app-tip` 弹出、
    `title` 摘走 / 离开恢复；SVG `data-tip` 夹具悬停 ⇒ 自绘提示、作者属性保留；SVG `<title>` 子元素
    夹具悬停 ⇒ 自绘提示且 `<title>` 文本被清空、离开原样恢复。
  - **2026-09-15 修订（船长报障「鼠标悬浮按钮的提示会和上一级的悬浮提示相互冲突。且悬浮的反应时间太快。
    建议所有 UI 统一下」· 已落码）**——三条：
    ①**延迟统一为 `TIP_DELAY_MS = 500`**（`ui/Tooltip.tsx` 导出的**唯一**常量；2026-09-13 定的 200ms
    **作废**，船长反馈"太快"）。**三条路径全部共用它**：`title`/`data-tip` 全局接管层 ·
    **富内容提示 `hoverTipProps(content)`**（`ShipHover` / `InfoHover` 等，此前是**即时弹**）·
    `HoverTip` 组件（此前也是即时弹）⇒ 现在任何悬停说明都是"停够 500ms 才弹、移开即收"。
    ⚠ **新写富内容悬停一律用 `hoverTipProps`**（或 `HoverTip`），**不要**再手写
    `onMouseEnter={showTip}` 那三件套（低层 API 仍导出，但组件层一律走工厂）。
    ②**"内层优先"判据（冲突根治点）**：`hoverTipProps` 在 `mouseenter` 时从指针目标往上走到自身，
    若中途出现**更深的提示归属**（`title` / `data-tip` / 另一个 `hoverTipProps`）⇒ 本次**不接**
    （让给内层）；接管层对带 `data-tip-hover` 的元素**不再重复接管**。⇒ 悬浮按钮时，外层卡片/行
    的提示不再抢着弹。
    ③**原生提示必须被"整条祖先链"压住**：接管时把被接管元素的 `title` 写成**空串**（不再
    `removeAttribute`——摘掉后浏览器会顺着祖先链找到上一级卡片那条 title 弹**系统默认**提示，
    这正是"相互冲突"的第二种成因），并**把祖先链上所有 title 一并置空**（记原值，离开时逐个还原；
    React 若已写新值则以新值为准）。`srcOf` 把 `title=""` 视为"没有 title"，继续从暂存里取真文本。
    ④**新守卫**：「悬停提示契约」新增一条——**同一 JSX 元素不许同时带 `title` 与 `hoverTipProps` 展开**
    （一个元素只能有一个提示归属）。

- **🔴 表现的观感审查权在船长（船长 2026-09-13 定）**：UI / 观感类改动，
  **实现 + 五闸门（typecheck / 测试 / content:check / 旋转口径 / 构建）跑完就直接交船长审查**——
  **不许自己起无头浏览器截图、然后拿截图当"已经改好了"的判断依据**。
  为什么：① 好不好看、像不像、够不够醒目**只有船长能判**，截图只能判"有没有渲出来"，判不了观感；
  ② 截图/探针要起无头浏览器 + 本地服务，占机器、抢端口；
  ③ 同一件事在交班件里已有先例——`docs/design/archive/handoff-20260913-wormhole-4ship-stage.md` 记着
  「UI 改动给无头 Chrome + CDP 的实测读数 + 截图」这句被船长删除。
  **例外（只此两类，且能少则少）**：a) **读数型问题**——溢出不溢出、有没有滚动条、
  跨窗口尺寸几何、性能帧数这类"**光看代码判不了**"的事实；b) **船长明确要求**取证时。
  即便如此也要：先看代码能不能判、能判就**不跑探针**；要跑就**挂后台任务**并在汇报里
  写清"这是读数、不是观感结论"，**观感结论一律留给船长**。

### 九之七、悬停详情的两个单点（船长 2026-09-16 两条报障后定）

1. **富卡皮肤单点 = `ui/shipInfo.tsx`**：悬停显示"这件东西的完整参数"一律走
   **`infoCardContent(标题, 参数表, 备注, 追加)`**（`InfoHover` / `ModuleHover` / `ItemHover` 与
   两个"不带包裹元素"的出口 **`moduleHoverContent(mod, hint?)`** / **`itemHoverContent(item, nameOf?, hint?)`**
   共用同一份皮肤）——后者给**容器标签不能换**的场合（如装配台槽位/候选卡是 `<button>`，要挂 `onClick`）：
   `{...hoverTipProps(moduleHoverContent(def, '行动提示'))}`。
   **新页面不许自造第二套悬停样式**；"仓库/市场/手册有的详情，装配台之类的地方也该有"——
   ⚠ 2026-09-16 那次报障的根因正是**漏接**（`shipInfo` 注释里写着"已装槽位行"，代码却停在薄 `title`）。
2. **层级规矩：`.app-tip` 必须压过全站所有浮层**（现行 `z-index: 3000`，全站最高浮层是换装浮层
   `.app-fit-overlay` 的 1100）——提示层画在 `App.tsx` 末尾的 `fixed` 单例里，**新加浮层不得超过它**。
   ⚠ 报障原文：「**装入和更换界面中，鼠标悬停的悬浮窗会被界面遮挡。**」（原值 1000 被 1100 压住）。
3. 配套纪律照旧：同一元素**禁** `title` + `hoverTipProps` 并存（两个提示路径会在同一个单例层上互顶）·
   内层优先（子元素自带提示时外层让位）· 全站同一延迟 `TIP_DELAY_MS`。

## 十、工具纪律（船长 2026-09-05 定）

> 背景：小工具/脚本"用完即删"或"不入库搁置"都浪费——正式工具入库沉淀（有版本、有文档、
> 可复跑），临时探针无版本地原地演进后往往需要从头重建（观察实证：C4 期间 `_synth-check.ts`
> → `_dbg-synth.ts` 活体迭代，git 历史中正式工具零删除）。

- **正式工具**（体检/校准/批量生成等可复跑）：`tools/xxx.ts`（不带 `_` 前缀）**入库** +
  头部注释（用途/用法/输入输出）；常用者挂 `package.json` 的 npm script
  （现例：`content:check` / `balance` / `battle:calibrate`）；改动随所属功能提交维护。
- **临时探针**（单次诊断，`tools/_*.ts`、`tests/_dbg.test.ts` 等）：允许以 `_` 前缀暂存不入库，
  但**任务收尾时二选一**，判定标准一句话——"下次平衡/体检/内容变更还会复跑它吗？"
  1. 会 → **转正式**：去 `_` 前缀、补头部注释、入库（必要时挂 npm script）；
  2. 不会 → **删除**，不留工作区垃圾。
- 探针命名一律 `_` 前缀：一眼区分 + 收尾清点入口 = `git status` 里的 `?? tools/_*.ts` 待处置清单。
- 多 agent 并行时探针归作者自处置：**不替对方删除或收编其探针**——疑似对方在用则保持只读
  并向船长报告（同第三章协作红线）。
- **🔴 底层规则：一律不许关闭浏览器进程**（船长 2026-09-13 定）：
  - **禁止**以任何形式"按名字/按命令行特征"结束浏览器进程：`Stop-Process`/`taskkill` 打在
    `chrome` / `msedge` / `firefox` / `brave` 等**任何**浏览器进程（含 `Get-Process chrome | …`、
    `Get-CimInstance … | Where-Object { $_.CommandLine -match '…' } | Stop-Process` 这类写法）**都不行**；
  - **禁止**对"不确定是不是自己起的"实例发 CDP `Browser.close`；
  - **为什么**：船长的浏览器可能**自己也带 `--remote-debugging-port`**（例如他本人在调试），
    任何按"命令行里有调试端口"的过滤都会命中**他的**实例并把他的窗口一起关掉；
  - **正确做法（三选一，按优先级）**：
    1. **把它挂在后台任务里**（`run_in_background: true` 起一个前台可见的命令），收尾用 `job_kill`
       结束该任务——进程树由 harness 管，**不碰任何别的进程**；
    2. 自己 `Start-Process` 时**留住返回的 PID**，只对**这一个 PID**收尾（必要时先核对启动时间），
       绝不再枚举同名进程；
    3. 拿不准 / PID 丢了 ⇒ **就让它跑着**，在汇报里写明"还留着一个无头实例（端口 N）"，
       由船长自行处置——**宁可留个进程，也不许误关船长的浏览器**；
  - 端口一律用**非默认端口**（本次探针用 4400/9223 这类），起之前先探占用、占用就换端口，
    避免与船长/其它会话的实例抢同一个端口（抢不到端口时自己的实例会静默失败、探针就会连到**别人的**浏览器上）。

## 十一、术语词典纪律（船长 2026-09-05 定）

> 背景：游戏自创术语多、跨里程碑复用，会话压缩后名词含义可能漂移（实证：B3 讨论中
> "低安"等既有术语被遗忘/重新发明）。为跨会话沟通一致，术语以词典为权威。

- **权威词典 = `docs/glossary.md`**（仓库级，根目录）：通用游戏术语 + 各里程碑专用术语
  一律先登记再使用；写作文档/代码注释/与船长沟通前，名词存疑先查词典，不凭印象猜；
- **新术语登记制**：新系统设计定稿词（船长拍板或总结确认后）由经办人**当天登记进词典**，
  带定义/公式/出处与状态（已定稿/待定）；
- **压缩遗忘处理**：上下文压缩导致遗忘属正常——查词典即可恢复，不必让船长重新解释
  （确有歧义或词典缺失才提问，提问时注明"词典未收录"）；
- 各 `docs/design/` 文档可保留局部细化，但与词典冲突时以词典为准并回头修订词典。

### 十一之二、本地化排队口径：**未完成的功能不计入**（船长 2026-09-20 定）

> 船长原话（照抄）：「**新增规则，未完成的功能不计入本地化工作排队。**」

- **规则**：**未完成**（在建 / 挂起 / 只有预留接口）的功能，其文案**不进本地化工作排队**——
  三号（本地化工程线）看到标了未完成记号的文案，**一律跳过**，等该功能**完成并合入 main** 后再排。
- **为什么**：未完成的文案会随实现继续变（改名、改口径、整段重写都常见）⇒ 先翻等于白翻，
  还占住本地化排队的进度读数（`l10n:check` 的「未译读数」是分母口径，被未完成项撑大就失真）。
- **识别记号（统一 · 必写）**：在**该功能的代码与文档改动处**留一行
  **`⟪未完成 YYYY-MM-DD⟫`** ＋一句状态/恢复入口（照 §十三「改过的文案要留痕」的 `⟪文案调整⟫` 同款手法，
  `⟪⟫` 为全仓保留记号）⇒ `grep -rn '⟪未完成'` 一次列全所有豁免面。
- **收口**：功能**完成并合入 main** 的那一刻，**删掉该处记号**（并补该功能文案的本地化条目）——
  记号残留 = 本地化会**永远跳过**它，属交付缺陷。
- **与 §15「工作文档 → 归档」的关系**：本记号不是替代归档，只是**排队豁免**；
  未完成项本身仍要在 `docs/roadmap.md` 的「未完成功能清单」里挂账（两条一起用）。

### 十一之三、本地化＝**id 映射制**（船长 2026-09-20 定）

> 船长原话（照抄）：「**将本地化采用id映射写入规则，以后新内容直接采用这个为其他语言本地化直接提供替换id。**」
> （先出草稿递船长过目 → 船长「可以」⇒ 本条生效。）

- **id 是唯一键，语言只是列**：玩家可见文案集中在 `packages/data/src/l10n/table.ts`，形如
  `id → { zh, en, … }`；内容数据（舰船 / 装备 / 物品 / 技能 / 异常 / 星系 / 蓝图 / 残骸 / 空间站 / 势力 /
  谜质 / 航行事件）的名称与说明走**按 def id 的英文覆盖表** `packages/data/src/l10n.ts`
  （`ship/mod/item/…` 域已在工具里预留，日后收敛进唯一表）。
- **新内容一律先取 id**：任何**新增的玩家可见文案**（界面标签 / 说明 / 悬浮、内容名称与说明、
  core 日志与错误提示）都必须走三步 —— **① 造 id ② 调用点写 `t('id')`（core 用 `textId` / `errorId`）
  ③ 在表里补 `zh` 与 `en`**；**不得内联中文字面量**。
- **id 形态**：`<域>.<短名>.<三位序号>`（域 = `ui / ship / mod / item / skill / ano / gal / bp / wreck /
  station / faction / travel / matter / core`）；**id 一经使用不复用、不改名**，只递增序号。
- **为什么这么定**：表以 id 为键 ⇒ **再加一门语言 = 给同一批 id 补一列译文**（`ja` / `ko` …），
  **实现零改动**；同时避开旧方案「以中文源串当 key」的坑（改一次中文，key 失效、既有译文全丢）。
- **例外走声明制**：确需保持原样的串（类型联合 key / 形状槽键 / 键表 label / 性能探针 / i18n 实现自身）
  在源码就地标 `l10n-keep`；**声明过就不算未译**，但新功能收口时要复核一遍。
- **合入前必跑**：`npm run l10n:check`（id 形态 · 调用点必须传 id · 表与源码一一对应 · 英文值禁残留中日韩 ·
  占位符对齐）＋ `npm run l10n:list` 看未译清单。
- **与既有条文的关系**：`AGENTS.md` §1（玩家可见文案中英双语）是**目标**，本条是**实现方式**；
  §十一之二（未完成功能不计入排队）是**排队口径**——功能完成并合入 main 时，按本条补齐 id 与译文；
  术语与专名仍以 `docs/glossary-en.md` 为权威；`content:check` 的禁用词契约按语言分叉。
- **不进存档**：语言选择仍存 localStorage；老档历史日志保持中文（`state.logs[].text` 存的是渲染好的文本）；
  开发侧文档 / 注释 / 汇报一律中文不变。

## 十二、游戏内更新公告（船长 2026-09-05 定；2026-09-08 增"发布审核"流程）

> 每个"大的系统添加或更新"完成并入主树时，**经办人必须准备一条玩家可见的更新公告**
> ——规则同时适用于一号与二号（谁完成大更谁备公告，不需要等船长/对方）。
> 公告数据 = `packages/data/src/announcements.ts`（每批在**文件最上方**新增一条）。

- **判定"大"**：新系统/新玩法上线、存档结构或大数值体系变更、界面信息架构调整、重大修复批次
  （如序章·苏醒整批）；纯文案/小修不强制，可顺手并入同批公告；
- **写法**：`id`（日期+短名）· `title`（一句话）· `date` · `tag`（系统/内容/数值/修复）·
  `bullets` 3~5 条玩家向说明（改了什么、如何体验），中文；
- **发布审核（2026-09-08 船长定）**：开发交流/设计讨论内容**不得直接写进公告数据**；
  批次发布前，经办人把公告文案（id/title/tag/bullets）**整理成待审稿递送船长审核**，
  得到明确批准后才写入 `announcements.ts` 合入——被驳回则按船长意见修改后再审；
- **人称与话术（2026-09-08 船长补定）**：①公告文案**禁用第一/第二人称代词**
  （我/我们/你/你的/我方/玩家你……），一律以**「玩家」**作第三人称表述
  （例："玩家接近敌方近身盲区时……"，不写"你可以……"）；②**开发/验收话语不进公告**——
  复测/校准/对齐口径/目标带/矩阵/参数名等"我们调过并验证"类表述一律不写，
  公告只说"世界发生了什么"（改了什么、玩家会体验到什么），不说"开发者做了什么/我们如何保证"；
- **生效方式**：公告数据随代码合入即发布——玩家下次启动若存在未读（顶栏「公告」红点）会
  自动弹一次，之后随时可从「公告」按钮回看历史；已读状态存 localStorage
  （`whale-idle:announce-seen`），不清档不重弹；
- **UI 归属**：顶栏「公告」入口在 `apps/desktop/src/renderer/src/panels/Announcements.tsx`
  （App 顶栏按钮 + 弹层），新增公告无需改 UI。

## 十三、游戏内文案纯净与设定（船长 2026-09-06 定）

> **底层规则**：玩家可见的一切文本（UI 文案、按钮/悬停提示、日志、公告、手册、教程、
> 任务/事件/卡面描述等）**必须符合游戏内世界观设定**；**开发/协作/商讨阶段的内容不得
> 进入玩家可见范围**——玩家只应看到"这个世界里的话"，不应看到"开发者的话"。

- **禁入清单（开发痕迹）**：版本号/日期/作者/经办人、「复核/待定/暂定/TODO/占位/口径/
  兼容/旧档」等工程措辞、内部代号/文件名/字段名、讨论与审批语境的表述、调试/探针信息
  ——一律不得出现在玩家可见文本；确需表达"尚未确定/后续会变"时，用符合设定的叙事措辞
  或与船长约定玩家向表述；
- **新文案默认先过"设定关"**：动笔时默认自己是游戏世界里的角色，科技/组织/地名/物品的
  表述以 `docs/glossary.md` 与既有内容表风格为准；与现实世界、开发语境、工程术语混同的
  一律改写；
- **交付前自查**：经办人对自己新增/修改的可见字符串做清单扫描（UI 卡面/日志模板/公告/
  教程/任务与事件文本/悬停提示），确认无版本日期、复核词、占位符、口径词、内部标识后
  交付；发现历史残留（旧版本遗留的开发备注、日志冒出开发文案等）按第五章检索纪律定位
  清理，并在汇报中报告；
- **改过的玩家可见文案要留痕，便于日后快速检索（2026-09-19 船长：「有过调整的文案都留个备注，
  方便之后快速查找」）**：凡**按船长报障 / 裁定调整过**的玩家可见文案（界面文字、按钮与**悬停提示**、
  日志模板、卡面说明…），必须在**改动处**留一行可检索备注——
  记号**固定**写成 **`⟪文案调整 YYYY-MM-DD⟫`** ＋一句缘由（船长原话摘要，照抄优先）；
  同时在**当批工作文档**（`docs/design/<主题>-<日期>.md`）的「**文案调整台账**」里登记一行：
  **日期 · 位置（文件/元素）· 原 → 新 · 缘由**；归档时随工作文档并入老文档（§十五）。
  **为什么要记号**：`git log -S` 只能查出"某句变过"，查不出"改过哪几句、各自为什么改"——
  `grep -rn '⟪文案调整'` 一次列全，省得后人靠猜（本记号 `⟪⟫` 全仓未占用，专供此事）。
  ⚠ 只标**调整过**的文案；**新写的**不必标（`git blame` 已足够）。
- 「公告」「教程」等带 meta 性质的界面同样适用：一律玩家向语言，不出现开发语境。
- **道具说明（装备 / 物品 / 蓝图 / 舰船的 `description`）另有四条禁写（2026-09-16 船长点名审查后立）**：
  1. **不写渠道 / 档位标签**——「（市场稀有）」「（奇货现货）」「（市场专供）」「（需高声望）」这类尾巴一律不写：
     渠道与稀有度由**市场页与图鉴的 chip** 承担，说明里重复既啰嗦又是"市场侧的话"。**"能不能造"是有用信息**，
     统一用中性句「**不可制造**」（**有蓝图的件一律不提**——组装机与图鉴本就看得见）；
  2. **不复述另一件装备的名字与数字（跨件对比）**——「比装甲增厚板 MK3 还厚四成」「（射速计算机 MK3 是 ÷1.12）」
     「单发是激光炮 MK3 的 1.8 倍」一律改写为**只讲本件**。两条理由：**阅读**（说明回答"这件是什么"，
     不是比价表）＋**维护**（他件调价/调 CPU 时那句话会静默过期）；实测一例：删掉跨件句后，靠"**跨件差值**"

## 十四、表现层实现与性能纪律（船长 2026-09-10 定；本条源自无人机战斗动画批次）

> 适用：桌面端战斗画面与其它**逐帧/事件驱动**的表现层（React + SVG 线稿 + CSS 动画）。
> 与第九章（风格一致性）同域但不同类：**第九章管"长什么样"，本章管"怎么实现才不出事故"**。
> 每条都来自实测事故，写进来是为了不再重犯。

1. **渲染体的提前 `return` 之后禁止出现任何 hook。**
   组件在"数据缺失/战斗已结束"等分支提前 `return null` 时，写在它之后的 `useEffect/useState/useMemo`
   会被跳过 → hooks 数量前后不一致 → React 卸载整棵树（表现为**整屏黑屏且无响应**）。
   实测事故：战斗结束时 `view.combat` 变 null 提前 return，落在其后的一个 `useEffect` 触发该问题。
   规矩：**所有 hook 写在任何提前 return 之前**；改动后自检"守卫之后是否还有 hook"。

2. **逐帧移动的物件，位置不得依赖 React 重渲染节奏。**
   若位置写在渲染体内、而重渲染由"某状态变化才 setState"的循环驱动，一旦该状态稳定（如敌舰到位不动），
   位置就只剩低频通知刷新（实测退化为 10fps 步进感）。
   规矩：位置用 **`requestAnimationFrame` 循环直接写 DOM `transform`**（`translate3d` 走合成层），
   并做"**值未变不写**"守卫；结构/显隐仍交给 React。

3. **组件局部的"生死/演出"登记必须能与引擎真值对齐。**
   把"谁已阵亡/谁在演出"只记在组件局部 ref 里，一旦组件卸载重挂（退出界面再进来）就清空，
   会把引擎里 hp 已归零的单位**重新当成存活渲染**（实测：重进战场已摧毁敌舰复活且血量 0）。
   规矩：这类状态**在入场时按引擎状态重建**（如按 `battle.units` 的 hp 预登记），而不是只靠增量事件累积。

4. **位移动画不要交给 CSS 关键帧的 `forwards`。**
   `animation-fill-mode: forwards` 会把**动画结束那一刻的终点值冻结**；目标（敌舰/列位）随后移动时，
   物件会停在旧坐标（实测："飞到某个固定地点就不动"）。
   规矩：跟随型位移由第 2 条的 rAF 循环逐帧求解；CSS 只做与位置无关的漂浮/呼吸等微动效。

5. **大 SVG 子树上不要用 `filter` 做状态表现，大幅 `box-shadow` 的缩放动画要走独立合成层。**
   `filter: grayscale()/brightness()/drop-shadow()` 会让整份矢量子树**重新栅格化**（实测：击毁瞬间
   一次 ~50–60ms 绘制尖峰、FPS 掉到 ~20；改法 = 尸骸灰化改为"把描边色传成灰 + 降透明度"，
   爆炸环加 `will-change: transform, opacity`、去掉内阴影并收小模糊半径 → 长任务归零）。
   规矩：状态表现优先改**数据（颜色/透明度/描边）**，不优先改滤镜。

6. **锚点几何依赖的测量值，必须随布局变化重测。**
   弹道/命中点/射程弧的锚点是由"列宽等测量值 + 布局公式"推出来的；编队数量变化会改变实际列宽，
   若不重测，锚点与 DOM 实际位置会整体错开（实测：击毁僚舰后弹道落点整体偏右，无人机瞄中心最明显）。
   规矩：测量值变化（编队增减/波次增援/窗口变化）→ **重测**；重测入口写在渲染体之外、由循环节流调用。

7. **引擎事件的展示字段是表现层差异化的地基，先做地基再谈演出。**
   表现层要区分"谁在开火"（炮台/导弹/激光/无人机/基础舰炮、机型），前提是引擎事件携带来源。
   做法：`WeaponSpec.src` + `artId` → `BattleFx.src/artId`，**旧事件缺省即回退旧口径**（兼容回归与旧档），
   表现层再据此分支。反例（本批起点）：事件只带弹种，无人机与炮台同色同形，无法差异化。

> 补充（同批经验）：**一次改动只动一条主因**——本批多次返工的根因都是"把位移交给 CSS 关键帧"、
> "位置写在渲染体内"、"测量值不重测"这类**实现层选择**，而非数值或资产问题；改表现层前先用
> `perfHub`（`localStorage['whale-idle:debug']='1'` → 顶栏「⏱ 性能」导出快照）取数，别凭猜。

## 十五、文档工作流：工作文档 → 归档（船长 2026-09-15 定）

> **船长原话（照抄）**：「**工作流没有进行收尾归档事，不允许直接修改旧文档。应该新建一个该工作的临时文档
> 记录工作相关。等到归档时，再合入旧文档。**」
> **同日补充裁定（照抄）**：「**归档后当前工作文档直接删除，只将关键内容归档。**」
>
> 背景：`docs/roadmap.md` 曾涨到 **1523 KB / 824 行**（单条平均 1.9 KB 的巨型条目）、
> `docs/glossary.md` 294 KB —— 老文档被当成"随手记"的草稿纸用了。本条把「记录」与「权威文档」分开。

1. **开工先建工作文档**：`docs/design/<主题>-<YYYYMMDD>.md`（沿用既有命名，**不是** `_` 临时探针——
   它是正式工作记录）。头部四行固定：`> **状态：进行中**（经办人 · 分支 · 日期）` · 船长原话（照抄）·
   范围/不做 · 待裁决点（要船长定的项）。
2. **工作期间只改这份工作文档**（＋代码/数据/测试）。**不许**给 `docs/roadmap.md` 追加批次条目、
   **不许**改 `docs/glossary.md` 的现行词条、**不许**改 `docs/architecture.md` 与既有设计稿——
   那些都是本条的"旧文档"。
3. **归档触发**：船长验收 ＋ 合入 main 之后，由经办人**当批归档**（一件工作一归档，不攒批）。
4. **归档动作（三步，缺一不可）**：
   ① **关键内容并入**该去的老文档——`docs/roadmap.md` 一条**精简条目**（要点 ＋ 指向代码/设计稿，
   不再堆船长原话）· 该更新的 `docs/glossary.md` 词条 · 必要时 `docs/architecture.md` / 本约定；
   ② **删除工作文档**（`git rm`）——**不留存档副本**；过程细节以 **git 历史**兜底
   （`git log -S "<关键词>"` 随时可查）⇒ **结论、数值、口径必须在第 ① 步就已并入**，
   不许只留在被删的工作文档里；
   ③ 重跑 `npm run docs:index`（索引跟随；`--check` 可验是否过期）。
5. **例外（这几份允许随时改，不受第 2 条约束）**：**根 `AGENTS.md` 仅船长明确指示时修改（2026-09-15 船长补定，不再属"随时可改"）** · 本文件 ·
   `docs/development-conventions-changelog.md`（规则类必须**当场生效**，否则约定形同虚设）·
   `docs/glossary.md` 的**新术语登记**（"新术语先登记再用"是 §十一 的硬纪律）·
   **`docs/catalog.md`（指路目录，导航变了就更新）** ·
   生成件 `docs/INDEX.md` 与 `docs/archive/` 封存卷（由工具/封存流程维护）。
6. **怎么判违规**：`git diff` 里出现"旧文档正文新增"却没有对应的工作文档 ⇒ 违规
   （自己发现就补建工作文档并说明；审查发现按 §一 走）。
7. **与既有条款的关系**：本条只**改时点**——`AGENTS.md` §8 旧话「里程碑**即**固化到文档」里的"即"
   指"归档时"；`docs/roadmap.md` 的定位同时改为「**待办活面 ＋ 最近批次滚动窗口 ＋ 封存卷索引**」
   （封存机制 = `npm run docs:seal`，规则见 `docs/archive/README.md`），它**不再**是随手追加的流水账。
