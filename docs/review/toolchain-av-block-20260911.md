# 工具链被安全软件拦截 · 记录与处置（2026-09-11）

> **用途**：记录本机「火绒安全 6.0」拦截 DSH 命令外壳一事——现象、证据、根因、放行办法，
> 以及我方为防止"静默失败"新增的护栏。供后续接手人（一号 / 二号 / 三号）与船长查阅。
> **一句话**：不是代码问题，是杀软的「隐藏执行PowerShell」通杀规则命中了 DSH 的命令外壳；
> 放行 DSH 宿主即可，**不要**整条放行 `powershell.exe`。

## 1. 现象与证据（船长提供火绒拦截记录原文）

| 字段 | 内容 |
|---|---|
| 防护项目 | **隐藏执行PowerShell** |
| 执行文件 | `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` |
| 命令行 | `powershell.exe -NoLogo -NoProfile -NonInteractive -Command "[Console]::OutputEncoding = …; <实际命令>"` |
| 操作结果 | **已阻止**（进程 ID 23996） |
| 操作进程 | `D:\Program Files\Deepseek Harness Desktop\DeepSeek Harness Desktop.exe` |
| 父进程 | `powershell.exe … -EncodedCommand …`（宿主启动链） |

- 船长反馈："你们的 powershell 申请好像因为我忘记确认被火绒拒绝了"——即该防护为**弹窗询问**式，
  **未点确认 = 拒绝**，被拒的命令拿不到输出。
- 被拦的那条**具体命令属于并行会话**（在统计 `packages/data/src/anomalies.ts` 的威胁/奖金分布），
  不是三号本批的命令；但**同一外壳是所有会话共用的**，故风险对每个会话都成立。

## 2. 根因

- DSH 执行任何命令都走固定外壳：`powershell.exe -NoLogo -NoProfile -NonInteractive -Command "<先设 UTF-8 输出编码，再跑用户命令>"`；
- 火绒 6.0 的「隐藏执行PowerShell」把"非交互、无窗口的 PowerShell"当作恶意软件常用手法做**通杀拦截** → 命中该外壳；
- 本机实际的 shell 是 **Windows PowerShell 5.1**（`C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`；
  本机**没有** PowerShell 7 的 `pwsh`）——这也是命令里 `&&` 不可用的原因。

## 3. 影响面与判定

- **被拦的表现**：该条命令**无输出**（等价于静默失败）；若落在验证链里，可能出现"部分步骤失败却被当通过"的假绿。
- **三号本批的结论未被污染**：关键项都做了**不经过 shell 的交叉验证**——用 `read` / `grep` 工具直接读文件核对
  （复原后 40 行注释**乱码 0 命中**、逐行读到的就是中文），与 shell 侧结论一致；
  测试计数（785 → 786 → 787）、构建产物、git 哈希也都彼此自洽。
- **并行会话那条被拦命令属"统计 + 汇总"批处理**：其输出可能残缺 → 若该批结论还要用，**建议重跑后再采信**。

## 4. 放行办法（船长操作；我方不擅动杀软设置）

1. 火绒主界面 →「**防护中心 → 系统防护**」→ 找到 **「隐藏执行PowerShell」** → 规则设置 → **例外 / 排除程序**；
2. 加入：`D:\Program Files\Deepseek Harness Desktop\DeepSeek Harness Desktop.exe`
   （**只排除 DSH 宿主这一个进程即可**，不影响该防护对其它程序的效力）；
3. 若该规则不支持"指定程序例外"，退一步加目录：`D:\Program Files\Deepseek Harness Desktop\`；
4. **不要**把 `powershell.exe` 整条放行——那等于关掉这条防护（无窗口 PowerShell 正是木马常用手法）；
5. 查历史拦截记录：火绒「安全日志」。

## 5. 我方护栏（自本日起执行）

- **哨兵命令**：每批开工先跑一条最短命令（打固定标记 + 时间戳）；**有输出**才继续跑四连验证。
- 任一命令出现 **空输出 / 非零退出 / 缺标记** → 判定"**疑似被安全软件拦截**"，**立即停手报告**，
  不把残缺结果当绿、也不在此时合入。
- 该护栏对所有并行会话同样适用（外壳共用、风险同源）。

## 6. 本次为定位该问题做过的实测（可复现）

一次性脚本与临时文件均放 `%TEMP%`、用后即删（仓库内 `_` 探针 0 个、无残留）。共测 **10 类动作，全部通过**：

| # | 动作 | 结果 |
|---|---|---|
| ① | 新起 Windows PowerShell 子进程 | ✅ |
| ② | `node.exe` | ✅ v26.7.0 |
| ③ | `npm` | ✅ 11.19.0 |
| ④ | 第三方二进制 `node_modules\@esbuild\win32-x64\esbuild.exe` | ✅ 0.21.5 |
| ⑤ | DSH 自带 `git.exe` | ✅ 2.55.0 |
| ⑥ | 仓库内 `tsc` | ✅ 5.9.3 |
| ⑦ | `cmd.exe` 子进程 | ✅ |
| ⑧ | 执行 `.ps1` 脚本文件（`-ExecutionPolicy Bypass`） | ✅ |
| ⑨ | node 起本地监听端口（网络防护触发点） | ✅ |
| ⑩ | 写用户临时目录文件 | ✅ |

> 结论：**拦截是"按弹窗确认"的间歇性事件**，不是固定黑名单——所以"点确认"不是可持续方案，
> 必须按 §4 加例外，或按 §5 用哨兵把静默失败显性化。
