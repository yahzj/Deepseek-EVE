## 一、执行摘要

### 1.1 总体判断

**项目不是“没有测试、缺乏结构”的原型，而是一套内容丰富、核心测试较强、工程护栏较多，但跨边界一致性仍有明显缺口的单机放置游戏。**

优点主要在规则核心、内容契约、种子随机与存档迁移基础；风险集中在：

- **保存是否真的按顺序提交。** 单次原子替换不能解决并发保存、恢复与账本更新的竞态。
- **同一份状态在不同入口是否得到相同处理。** 正常启动、导入、恢复、文件重连并没有形成统一装载事务。
- **时间推进是否独立于步长。** 加速剂到期、续用和训练完成之间缺少正确的事件时间轴。
- **资源数量是否守恒。** 小数体积逐轮取整、并行生产不计预留，分别造成产出损失和容量超限。
- **界面是否真正可操作。** 键盘用户无法等价使用部分图形节点、提示和弹层；严重提示仍会自动消失。
- **“护栏通过”是否等于功能通过。** 有的工具只检查键与类型，有的失败不设置退出码；通过读数的语义需要加强。

**推荐顺序：先存档可靠性与资源守恒，再时间轴正确性，然后补集成测试和界面可达性，最后做模块化、首包和维护成本优化。**

不建议先做全仓重写、统一所有状态机、换前端框架或全面调整游戏数值。这些动作会扩大回归面，又不能首先解决当前最危险的数据损失和错误结算问题。

### 1.4 严重性与证据标记

本报告使用以下口径，不依赖仓库自己的问题分级：

- **P1：高优先级缺陷。** 有数据损失风险、明显资源错误消耗、关键机制失效，建议下一次发布前处理。
- **P2：一般优先级缺陷。** 可复现的错误、持久化信息丢失、错误反馈或质量门禁失真。
- **P3：维护或体验改进。** 不直接证明玩家损失，但持续增加开发成本或降低体验。
- **静态已确认：** 已追踪具体输入与完整调用链；未声称发生过实机事故。
- **合成已复现：** 在当前代码上，用独立构造的内存状态执行真实函数并观察到结果。
- **待运行验证：** 原因或风险值得检查，但缺少当前环境下的实际交互、像素或性能证据。
- **产品建议：** 涉及体验、设计和规则选择，不能自动等同缺陷修复授权。

UI 章节另用 **HIGH / MEDIUM / LOW** 表示用户影响。HIGH 不自动表示整个游戏必须停止运行，但表示相关流程不应被认定为已满足可访问性验收。

## 三、架构现状与代码规模

### 3.1 当前架构

项目采用 npm 工作区组织，主要技术是 TypeScript、React 18、Electron 31、Vite 5、Vitest 2。

```text
桌面外壳：Electron 主进程 + 预加载桥
                           │
                           ▼
共享界面：React App + GameEngine + 存储适配
             ▲                         │
             │                         ▼
独立网页入口                  @whale/core 游戏规则
                                       ▲
                                       │
                              @whale/data 内容与上下文

@whale/ui：少量共享界面组件与样式
工具层：契约检查、经济仿真、迁移、界面读数、内容导入导出
```

这套分层值得保留：规则不依赖 React，桌面和网页复用渲染逻辑，数据目录可用于测试和仿真。

但“纯核心”和“确定性时间演算”的理想边界并不完全等于当前实现：

- 状态树在原地修改，不是不可变纯函数返回新状态。
- 不同规则模块之间存在大量状态读写和推进顺序耦合。
- 个别核心路径直接读取 `Date.now()`，例如 `salvaging.ts:305,757,865`。
- 训练等系统对时间步长敏感。
- “未来整体搬到服务器”需要检查墙钟注入、进程级临时状态、入口事务与权威命令校验，不能只换存储接口就视为完成。

```text
写同一个 save.json.tmp
→ 把该临时文件 rename 成 save.json
→ 不等待铁人账本更新
→ 返回保存成功
```

渲染层每次操作大量采用 `void this.persist()`。`persist()` 没有互斥，主进程处理器也没有队列。动作保存、定时保存、恢复与关页保存可重叠。

#### 触发过程

1. 保存 A 生成较旧快照。
2. 保存 B 生成较新快照。
3. 两个异步请求都截断/写入同一临时路径。
4. 一个请求先改名，另一个可能找不到临时文件；也可能形成旧请求晚提交。
5. 铁人账本另有异步读改写及共用临时路径，且保存回执没有等待它完成。

单次“写临时文件再改名”只提供单个替换动作的原子性，**不提供并发事务的先后顺序**。部分交错还有混合或不完整内容风险，但本次未进行文件损坏实测，不应把最坏结果写成已经发生。

#### 用户影响

- 界面操作成功，最新进度却没有稳定提交。
- 下次启动可能回退到较旧快照。
- `ENOENT` 或文件占用异常可能导致保存失败。
- 主档与铁人账本短时间不一致；进程退出可能把异步账本工作丢在半途。

#### 推荐修复边界

1. 主进程统一保存、恢复及需要一致性的账本提交队列。
2. 快照在入队时固定；回执对应该快照提交完成。
3. 保持队列失败后的可继续性：一个请求失败不能让后续全部挂死。
4. 给事务内部临时文件唯一名称，但**不以唯一临时文件替代提交队列**。
5. 明确账本失败后主档是否算保存成功，返回可区分的状态。
6. 网页绑定文件也应纳入同样的写入顺序检查，不仅修桌面路径。

#### 必补回归用例

- A/B 快照人为延迟，最终档必须符合确定的提交政策。
- 保存与恢复并发，结果不因文件写入耗时随机变化。
- 失败后下一次保存仍能正常提交。
- 铁人主档和账本回执关系明确。
- 关页/退出仅作为尽力保存，不能宣称异步任务一定完成。

**避免错误修法：** 单纯把临时文件名改成随机字符串；捕获 `ENOENT` 后当成功；只降低定时保存频率；只给某一个按钮加防抖。

### C02 · P1 · 网页重新连接文件不读档，可能用旧内存覆盖较新的文件

**证据状态：静态已确认；浏览器权限交互未实机验证。**

**主定位：** 渲染 `App.tsx:642–648`。

**相关定位：** `game/saveFileHandle.ts:143–155,185–195`；`game/storage.ts:155–168,411–416`。

#### 当前实现

- 权限未授予时，读取绑定文件返回 `null`。
- 启动选档只在 `storage.load()` 中比较文件与浏览器档的保存时刻。
- “重新连接”只申请权限、刷新状态、显示成功提示。
- 连接后保存直接把当前内存写到该文件，没有重读或冲突判定。

#### 触发场景

1. 浏览器重启后文件读写权限回到 `prompt`。
2. 启动只能读取浏览器内较旧档 A。
3. 绑定文件实际为较新档 B，例如曾被其他设备或应用更新。
4. 玩家点击重新连接并授权。
5. 下一次动作或定时保存把 A 覆盖 B。

无需假设 IndexedDB 与 localStorage 同时被清理，问题也成立。

#### 推荐处理

把重连视为**装载来源重新出现**，而非仅“权限恢复”：

- 权限授予后先暂停该文件写入。
- 读取、解析、校验文件档，比较当前内存与浏览器档。
- 文件较新或来源不同，展示明确选择：载入文件／保留当前并覆盖文件／取消。
- 选择完成后才恢复自动写入。
- 单看 `savedAtWallMs` 不足以处理系统时间回拨、跨设备时钟和不同档案，长期应增加档案身份与修订信息。
- 不用“连接成功”暗示“文件进度已载入”。

#### 回归验收

模拟 `prompt → granted`、文件 B 比内存 A 新，断言授权本身不覆盖 B；取消冲突处理仍保持写入暂停；无效文件不会把当前游戏变成新档并覆盖原文件。

**相邻风险，不另算正式问题：** 多标签页共享 localStorage，没有在所查路径中发现跨页写入锁或冲突协调。后续应检查单写者策略，不能假设两个标签页永远不会同时运行。

### C04 · P1 · 跨加速到期边界的训练不按事件时间轴结算

**证据状态：合成已复现。**

**主定位：** `core/engine.ts:184–204`。

**相关定位：** `training.ts:35–47`；`skillQueue.ts:78–89`；`simulation.ts:183`。

#### 根因

`advanceGame` 先把 `gameMs` 增加整段时间，再按整段末刻的加速状态计算本级训练门槛。队列进度保存的是经过时间，但门槛会随当前加速变化，历史进度因此被重新解释。

#### 精确复现场景

当前 `mining` 为 rank3，Lv1 基础时长 **465,000ms**，不是 60 秒。使用：

```text
gameMs = 0
mining 未训练
队列只练 mining Lv1
progressMs = 231,500
skillBoostUntilMs = 5,000
自动续用关闭
debugQuick = false
总推进 = 10,000ms
```

本次观察：

| 推进方式 | 结果 |
|---|---|
| 一次推进 10,000ms | 仍为 Lv0，进度 241,500ms |
| 分 10 次，每次 1000ms | 已达 Lv1，队列为空 |

同样的初态、总时间、内容与种子产生不同结果。未开启重复讨伐时，离线结算恰好走一次大推进，所以不是只有工具调用才触发。

#### 推荐实现方向

1. 把训练进度定义为稳定的基础训练工作量，而不是随当前倍率变化的完成门槛。
2. 从起刻到末刻分段，边界至少包含：效果到期、技能完成、自动续用、影响训练速度的技能升级。
3. 每段按该段有效倍率累计工作量，完成后消费真实经过时间并进入下一项。
4. 到期和完成同时发生时定义明确的边界先后关系。
5. 只切训练域时间轴，避免为了这一问题盲目把整个离线游戏改成每秒一拍，改变市场与任务刷新语义。

#### 验收性质

对训练相关投影比较：一次大步、等分小步、随机分片应一致，允许已声明的舍入误差。不要比较整个日志条数作为唯一标准，因为界面汇总、离线静默与日志合并可有有意差异。

**避免错误修法：** 只把某次 `syncBoostRenew` 挪前；只给离线固定 30 秒分片；只改显示预估时长；用当前门槛重置旧进度但不设计迁移。

### C05 · P2 · 小数残骸体积逐轮取整，读档继续截断

**相关定位：** `salvaging.ts:773–788,931–932`；`ai.ts:979–981`；`save.ts:501–503,601–603`。

#### 当前行为

普通残骸数量按 m³ 计量，计算结果可以是小数。主控调用 `addItem`，每次都 `Math.floor(units)`；副船则直接累加小数；读档再对货仓与仓库逐值取整。

本次合成执行：

- `addItem(state, wreckId, 0.3)` 返回 `true`，实际货仓增加 **0**。
- 货仓放入 0.9，序列化并读取后变成 **0**。

- 低量作业长期产出为零，不会把多轮余数累计成 1。

**方案 B：只存整数。** 在作业或统一数量层维护余数，累计足够时转整数，余数必须落档。

建议采用固定精度或最小体积单位，避免无约束浮点长期误差；但这涉及数量语义，实施前须明确，而不是简单删除所有 `Math.floor`。

#### 回归验收

- 十轮 0.3 应合计为 3，不能每轮为 0。
- 主控与副船同配置的有效产出一致。
- 合法数量保存往返不减少。
- 搬运、出售、回收与容量检查不创造或吞掉余数。
- 无效值、负数、非有限值仍拒绝。

### C10 · P2 · 存档往返工具可能发现问题仍以成功状态结束，且检查范围不足

**证据状态：静态已确认；本次输出证实失败样本仍伴随通过文案。**

**主定位：** `tools/save-roundtrip-audit.ts:27–38,49–77`。

#### 现有检查缺口

1. 只比较第一次归一后的状态与第二次归一后的状态，第一次已经丢失的内容不会被发现。
2. 数组只检查第 0 个元素。
3. 只检查键和类型，不比较数值、数组长度或内容。
4. 有丢键/变形时只打印失败文案，所查代码没有设置失败退出码。
5. 载入失败累计 `failed`，最终“通过”分支只看 `lost/typed`。

这不是要求所有版本都必须载入。v17 反例可以合法拒绝，但应作为**预期拒绝**单列，而不是“失败 1 份”之后又输出总体通过。

#### 推荐拆成三种检查

- **版本迁移：** 每种历史版本的预期接受/拒绝及迁移结果。
- **结构幂等：** 归一后再次归一不会继续丢字段或改类型。
- **领域保真：** 对合法当代状态，资源、进度、历史窗口、奖励标记、运行线和战斗字段按各自契约保值。

所有意外失败必须设置非零退出码。预期拒绝由 fixture 元信息声明。检查数组全元素，或基于明确的判别联合分类检查，不假设第一个代表全部。

#### 回归验收

故意构造第二个数组元素漏字段、48→24 历史、0.9→0 数量、新字段第一次读档被丢等变形，工具或领域测试必须报红；合法旧版本拒绝反例不误报。

## 六、代码健康与可维护性

### 6.1 应保留的基础

1. **核心与 React 分离。** 当前测试和工具可以直接调用规则，是最大资产。
2. **数据目录与上下文。** 多数内容引用能被批量检查，减少幽灵 id。
3. **种子随机。** 适合回归、复现与经济仿真，应继续保持。
4. **严格类型与少逃生标记。** 本次没有发现 `as any` 等常见掩盖手段。
5. **已有模块拆分。** 技能队列、战斗辅助、忙态与活动门禁等不是从零开始。
6. **正式工具多。** 内容、主题、迁移、经济、界面读数已有入口，不必全部重写。

### 6.2 H01 · 大型渲染引擎成为生命周期与业务协调中心

定位：`apps/desktop/src/renderer/src/game/engine.ts:1–9,1017–1144,1369–1824` 及后续玩家动作。

问题不是“超过某个行数就坏”，而是同一个类同时承担：

- 构造上下文与本地化。
- 启动、读档、离线结算。
- 保存、恢复、导入、导出、铁人账本。
- 高频心跳和通知。
- 全域玩家动作。
- 战斗预估和缓存。
- 界面一次性反馈与性能埋点。

后果是修改一个装载入口，其他入口很容易漏同步；C07、C08 便是具体表现。

**建议结构：** 先提取 `saveLifecycle`、`loadPipeline`、命令提交收尾、训练域时间轴等高内聚职责。保留现有对外 API 做薄转发，降低 UI 同时修改成本。

不建议建立“任意字符串 + 任意参数”的通用命令总线。若做命令统一，使用带判别字段的类型化命令，保持每条动作的明确输入输出。

### 6.3 H02 · 生产同类实现共享政策仍依赖手工同步

定位：`core/manufacturing.ts`、`industry.ts`、`lab.ts`。

开工校验、材料扣取、核心占用、取消退料、循环续做、产物容量、离线统计在多个模块存在同构逻辑。

**建议先抽政策，再考虑框架：**

- 批次材料事务：预检、扣料、失败回滚、退料。
- 核心占用与归还。
- 产物预留。
- 循环目标计数。
- 统一停因结果类型。

不要第一步就把精炼一转多与制造多料一物强行塞进同一个复杂万能状态机。规则差异必须保留，重复政策才需要共享。

### 6.4 H03 · 存档手工白名单缺少足够的价值保真约束

定位：`core/save.ts:380` 起的 `normalizeState`；`state.ts` 与 `types.ts`。

新增可选字段容易出现“写入成功、读档丢失”；数值清洗过于通用又会把合法小数等领域值改坏。

推荐：

1. 每个状态子域负责自己的版本化归一与测试。
2. 保留总存档外壳校验和历史迁移调度。
3. 给数量、时长、百分比、序号分别定义归一政策。
4. 用类型穷尽约束字段覆盖，同时测试合法值保真。
5. 加默认值不一定要求全局版本号增长；改变字段语义则需要明确迁移。
6. 归一与“内容 id 仍有效”的修复分开：后者依赖上下文，不应靠解析层猜。

### 6.5 H04 · 注释承担过多历史过程，现行契约与旧过程混在一起

例子：`ui/layoutStyles.ts:10–13` 仍描述早期临时工具路径，下面 `22–23` 才是当前正式生成入口；`Hint.tsx:11` 仍写旧的宽度/延迟，而提示实现已经是 380px/500ms；自动续用测试头注仍把 mining 描述成 rank1。

建议每个模块头只保留：职责、输入输出、关键不变量、必要设计理由和当前入口。完整讨论、已废止参数与过程日志留到文档或历史。

**不是删除所有注释。** 库存单位、退料账、时间边界这类业务依据应保留；已失效的具体读数尤其需要移除或变成可运行断言。

### 6.6 H05 · 大型公共出口增加耦合与误引入成本

定位：`packages/data/src/index.ts:5–152`；`packages/core/src/index.ts`。

公共聚合出口方便调用，但主进程只需本地化表却从 `@whale/data` 聚合入口导入。桌面主进程构建约 1.17MB，值得检查公共出口是否带入不必要依赖或初始化。

建议建立少量职责明确的子路径导出，例如存档、训练、内容上下文、本地化。使用构建依赖分析确认收益，不能仅凭文件行数判断打包器不能摇树。

### 6.7 H06 · 样式体系有单点来源，但维护成本偏高

当前有源码样式、经典生成样式、现代生成样式和冻结基准。生成链本次一致，是正面证据。

长期问题在：

- 基准本身超过一万行，只有部分选择器实际承担历史外壳覆盖。
- 大量追加修饰态容易发生特异性反噬。
- 新增规则需要检查源码、生成件和双布局。
- `--wui-xNNN` 一类编号令牌语义不够直观。

推荐顺序：先把共享基础、组件、外壳差异与特效样式明确分层；再把冻结基准缩成最小历史差异输入；新增令牌采用语义名，但不要一次性改名全仓上万处引用。

### 6.8 H07 · 文档与现状有明显漂移

- README 仍写早期 78 技能、25 艘船、281 市场卡，与本次内容检查的现状不同。
- README 的自动保存写每 15 秒；当前引擎采用 60 秒常量。
- 架构文档仍写当前结构 v28；代码为 v31。
- 文档目录中的固定文档份数也不等于本次盘点。

这会误导新接手 AI，让其把过时描述当验收目标。

推荐把“实时事实”尽量改为代码符号/工具入口，不维护容易过期的第二份计数。必须写快照时附日期、基线和统计范围。

**注意：** 本次工作区删除 `AGENTS.md` 是用户既有改动，不能把它判为本次审查发现的误删，更不能擅自恢复。

## 七、测试体系与质量门禁

### 7.1 现有测试优势

- 数量充足，领域覆盖面广。
- 战斗、市场、存档、工业、活动门禁、离线、虫洞等都有用例。
- 很多历史玩家报障已经转成确定性回归。
- 数据契约与行为测试并存。

### 7.2 当前最大的缺口：领域测试很多，边界组合测试不足

本次 3004 用例全通过仍能复现多项缺陷，说明下一步不应仅增加“同一种短技能又一条测试”，而应补：

| 性质 | 测试内容 | 对应风险 |
|---|---|---|
| 时间分片不变性 | 同初态、同总时间、不同分片的训练结果一致 | C04 |
| 幂等 | 同一时刻重复续用/修复/领奖不会重复消耗或奖励 | C03 |
| 资源守恒 | 扣料、在产、成品、退料、货仓与仓库合计正确 | C05、C06 |
| 并行预留 | 多线/多配方争用同一容量 | C06 |
| 保存事务 | 乱序耗时、失败、恢复并发 | C01 |
| 来源冲突 | 内存/浏览器/文件不同版本、权限恢复 | C02 |
| 装载入口一致 | 启动/导入/恢复均走相同修复与铁人判据 | C07 |
| 合法状态保真 | 值、数组、进度、去重标记保存不变 | C05、C09、C10 |
| 用户可见反馈 | 保存失败不显示最新备份成功 | C08 |

### 7.3 防止测试自洽但不正确

例子：`boost-autorenew-20261001.test.ts:58–65` 通过同一训练公式计算预期时长。这对检查乘区接线很有用，但无法独立证明该公式与时间语义正确，也未覆盖真实 rank5 单级超过一剂时长的边界。

推荐每个关键公式同时具备：

1. 少量独立人工推导的锚点断言。
2. 用真实内容表的边界组合。
3. 可泛化的性质断言。
4. 反例证明测试真能失败。

不要把所有预期值都从正在测试的函数再算一遍。

### 7.4 外壳集成测试建议

在不启动 Electron 的测试层，用依赖注入桥和时钟测：

- `save()` 返回 false / 抛异常 / 延迟。
- `readBackup()`、恢复和导出快照关系。
- 装载入口调用顺序。
- 加速与离线工作量。
- 取消文件选择、失权、重连来源冲突。

然后再用少量 Electron/浏览器端到端测试覆盖真实文件权限、用户手势与退出保存。不要把全部规则搬到端到端测试中，运行慢且定位困难。

### 7.5 持续集成缺口

定位：`.github/workflows/pages.yml:29–35`；`release.yml:49–71`。

当前网页部署链主要安装与构建；桌面发布链核版本、构建和打包。所查两条流程没有先运行核心测试、四包类型检查、内容检查、存档关键回归。

因此 main 上能构建的规则错误可能直接上线；本地钩子不能替代远端质量门禁。

建议增加一个可复用的质量检查流程，部署和发布依赖其成功。纯网页安装只含 React/Vite，运行核心测试需要适当安装根工作区依赖或独立质量作业，不能在现有 web-only 环境里假设 Vitest 与 tsx 存在。

### 7.6 工具治理

根 `typecheck` 没有纳入 `tools/` 和独立 `web/src`；工具能被 tsx 执行，不等于通过类型检查。源码中出现 ESLint 抑制注释，但本次未发现对应完整可执行的 ESLint 配置链。

推荐：

- 为常用正式工具建立 Node-only 的 TypeScript 配置。
- 浏览器源码、Node 工具、主进程使用不同环境类型。
- 加规则覆盖 hook 顺序与依赖、Promise 未处理、无效可访问性结构。
- 逐批修存量，不以全局关闭 strict 或大面积抑制换取全绿。
- 每个检查工具须具备稳定退出码、摘要、输入范围和必要前置条件。

### 8.4 具体 UI 改造建议

#### U01 · 给提示层增加可持续的详情入口

- 提示用于补充信息，关键开工条件、损失后果、材料不足原因不应只靠 hover。
- Hint 按钮获得焦点时展示同一内容；Escape 收起。
- 富卡内容复杂或可操作时，不应继续当不可聚焦 tooltip，改为可固定的详情面板。
- 触屏通过点击“详情”进入，避免第一下同时展示和执行操作。
- 复用现有提示数据来源，不新建第二份参数计算。

#### U02 · 弹层先统一行为，再统一皮肤

共享行为最低包含：

1. `role="dialog"` 或合适的原生对话框。
2. 标题关联与可访问名称。
3. 打开时移入焦点，关闭时还原触发点。
4. 背景交互隔离。
5. Escape 和明确关闭按钮。
6. 内容内部滚动和边界防滚。
7. 忙态、错误态和嵌套弹层规则。

不要只加 `aria-modal="true"` 就视为完成；声明与实际行为不匹配可能更误导。

#### U03 · 存档管理改为来源与状态明确的流程

建议展示：

```text
当前内存进度
上次成功保存时刻
浏览器保底是否可写
绑定文件是否授权、是否有待处理冲突
正在提交 / 提交成功 / 提交失败
```

操作建议：

- “连接文件”与“载入文件进度”分开命名。
- 最新保存失败时不显示“当前备份成功”。
- 导入/恢复在最终动作前说明会替换当前进度。
- 明确“导出成功”代表文件已写/分享已完成，不能泛指仅调用了 API。
- 无需强制自动备份，仍可通过确认、明确提示或撤销政策保护用户。

#### U04 · 生产页信息按决策任务组织

不是简单把所有读数放大，而是分成：

- **现在做什么：** 配方、启动、停止、循环目标。
- **是否能做：** 材料、核心、容量与预留。
- **做完得到什么：** 本批锁定产量、剩余时间。
- **历史效率：** 速率、收益预估、累计产出。

当前库存、运行中预留和真正可用空间应分开显示，避免容量超限修复后按钮仍给出假预期。

输入/输出两列适合配方转换，但窄窗口应可纵向排列，不用字号缩到极小来维持两列。

#### U05 · 新旧布局保持功能和可访问性一致

保留视觉差异可以，但键盘路径、保存告警、重要任务提示、核心状态不能因皮肤不同而缺席。

建议双布局共用语义组件与数据，只把布局容器作为差异。每次修共享行为至少检查两种布局。

#### U06 · 移动适配不应只依赖旋转和整体缩小

`App.tsx:175–177` 用逻辑宽 1200 和 `可见长边/1200` 的整体缩放。它可以容纳桌面布局，但物理触摸目标随之变小。

例如可见长边 800px 时比例约 0.667；逻辑 36px 的目标会变成约 24px，逻辑 12px 文本约为 8px。**这是计算示例，不是本次设备实测。**

建议后续：

- 先量真实触摸目标和可读文本，不按逻辑像素验收。
- 提供低密度移动模式或针对关键流程的自适应布局。
- 200% 缩放时内容可重排，不以硬裁防止一级页滚动。
- 竖屏旋转可继续作为兼容模式，不把它当全部响应式需求的唯一答案。

#### U07 · 排版与状态反馈

- 动态金额、计时、产量采用等宽数字，已有做法继续复用。
- 重要正文与控制标签不要落到 9～11px；HUD 图形内小注释不自动等于错误，但不适合承载唯一行动信息。
- 长名保留全文入口，截断后不能只有鼠标可见。
- 错误应说明“下一步做什么”，不要仅显示内部异常字符串。
- 关键数量输入在移动端测试系统键盘、字号和缩放行为。

#### U08 · 配色和动效

- 保留主题令牌，不重新造第二套颜色系统。
- 关键状态使用文字或图标冗余，不只靠红/黄/绿。
- 对照片/透明背景跑实际像素对比度读数，重点检查弱化、禁用和选中态。
- 逐帧 JavaScript 演出也要服从减少动效，不仅 CSS 动画停播。
- 把 `transition: all` 改成明确属性，属于低成本维护优化；不应优先于 C01～C06。

### 8.5 UI 后续验收边界

后续应分别记录：

- 键盘 Tab/Shift+Tab 的每个停止点。
- Enter/Space 可执行，Escape 可关闭。
- 对话框打开/关闭后焦点位置。
- 读屏名称、角色、状态与错误播报。
- 320px、200% 缩放、中英长文案、双布局。
- 减少动效、各主题实际像素色对。
- 用户观感验收单独记录，不用静态检查或截图取代产品判断。

## 九、性能、安全与部署

### 9.1 首包体积：存在风险，不等于已经测出卡顿

本次网页构建：

- 主 JavaScript：**2744.57kB，gzip 911.61kB**。
- 公共 CSS：114.68kB，gzip 27.32kB。
- 现代布局 CSS：235.12kB，gzip 37.77kB。
- 经典布局 CSS：248.21kB，gzip 39.50kB。
- Vite 报出超过 500kB 的块警告。

桌面构建：

- 主进程约 1171.57kB。
- 渲染主 JavaScript 约 4838.32kB。
- 桌面与网页构建配置/压缩不同，**不能用这两个大小直接比较端上速度**。

推荐：

1. 先分析包组成与加载时序。
2. 懒加载大型非首屏页面：虫洞、手册、战斗表现层、调试页等。
3. 避免“动态导入但又被静态导入”形成假拆包；本次桌面构建明确提示 `perf.ts` 属于这种情况。
4. 双语数据与核心规则是否必须全部首屏加载应测量后决定，不能贸然异步化上下文。
5. 建立首包、启动 CPU 时间、交互可用时刻的预算，预算值基于设备测量，不在审核中凭空拍数。

### 9.2 全局刷新与可变状态快照

`App.tsx:145` 通过强制刷新订阅引擎；`engine.ts:1017–1024` 通知全部监听器。战斗心跳与普通挂机心跳不同频率。

风险是某个全局字段变化让无关组件计算重跑。**本次未测 Profiler，不声称具体重渲染次数或长任务。**

建议：

- 先用现有性能 Hub 找最重页面和计算。
- 为领域视图提供明确修订号或稳定快照。
- 再考虑 `useSyncExternalStore` 与选择器订阅。
- 原地修改状态时，直接返回同一个对象会破坏引用比较；不能只是把当前订阅 API 换个 hook 名称。
- 缓存只读派生值要定义完整失效条件，避免把性能问题换成假读数。

### 9.3 懒挂载与虚拟滚动

已有 `ui/LazyMount.tsx`：进入视口后挂载，不再卸载；这是合理的渐进性能手段。

局限是整表滚过之后仍保留全部 DOM，并不等价于虚拟滚动。键盘或读屏也可能遇到尚未挂载的内容。

后续验证首屏、快速滚动、过滤、跳转定位、语言切换与键盘查找；只有持续 DOM 成本显著时再升级虚拟列表，不能忽略可达性与高度估计。

### 9.4 进程级临时状态需要清理责任

`core/consumables.ts:186–195` 使用模块级离线补剂计数。`simulation.ts:93–97` 开启后可能提前返回，异常路径也没有统一 `finally`。

本次没有证明特定线上奖励损失，因此列为维护风险：模拟器或测试进程运行多个状态时容易串上下文，在线日志可能被错误地视为离线。

建议把统计器显式传入，或至少用 `try/finally` 管理进入退出；对交错模拟、零结算时间、抛异常后的下一次在线推进补测试。

### 9.5 安全正面基础

- 预加载仅暴露明确保存、备份、导入导出等能力，没有公开任意 `ipcRenderer`。
- `contextIsolation: true`。
- 新窗口请求明确拒绝。
- 备份文件名使用约束模式，降低路径穿越面。
- 主档保存限制字符串类型及大小。
- 桌面与网页入口都有内容安全策略。
- 本次检索未发现渲染源码的 `dangerouslySetInnerHTML`、`eval` 等明显高危入口。

### 9.6 安全加固建议：不宣称已存在可利用漏洞

定位：`main/index.ts:272–295` 与各 IPC 处理器。

- `sandbox: false` 需要说明必要性；评估受支持版本中的沙箱预加载能力。
- 拒绝新窗口不等于拒绝当前窗口导航，应限制非应用地址的导航和校验敏感 IPC 调用来源。
- 导入文件在桌面 `readFile` 与网页 `File.text()` 前建议检查大小，避免巨大文件耗尽主线程和内存。
- JSON 归一对嵌套深度、大集合和异常键值应有预算，防止无意导入造成长时间无响应。
- Electron 31、Vite 5、Vitest 2 属于当前依赖基线；本次未查安全公告，不能写某个具体漏洞已命中。
- 建议在隔离环境运行依赖审计，按实际发布依赖、构建依赖和攻击面分级。
- 单机铁人账本与存档处在同一用户控制下，应定位为游戏纪律/误回滚保护，而非强安全承诺。

### 9.7 发布可靠性

- 质量检查必须成为部署前置条件，而不是“开发者应该手动跑”。
- 生产发布与开发分支修改分离。
- 构建日志保留体积和警告；不要单纯增大 `chunkSizeWarningLimit` 消除噪声。
- 对运行时升级进行存档导入、用户手势、权限与退出回归。
- GitHub Action 固定版本标签当前可用；是否锁定完整提交哈希属供应链防护选择，建议独立评估。

## 十、后续 AI 的分批工作流程

### 10.1 交接使用原则

本报告是待办与证据，不是无限修复授权。接手 AI 应：

1. 先核对当前基线是否仍是本次版本。
2. 核对工作区已有修改，区分用户、其他会话与自己。
3. 对选中的问题复跑最小合成例，再写修复。
4. 一批只解决同一根因，不顺手全仓重构。
5. 产品政策待定时列出影响，不能用“第三方审核”替代负责人决定。
6. 不使用个人真档做破坏性试验；合成状态与隔离用户目录优先。
7. 每批先有失败测试，修完后证明失败测试转绿且邻域不回归。
8. 无提交/推送授权时停在工作区交付。

用户允许忽略项目内部约定，不等于批准任意删除、覆盖、外发、推送或修改所有模块。仍应遵守当前会话和工具权限。

### 10.2 批次 A：存档提交可靠性

**目标：C01、C08。**

先做：

- 明确保存事务和回执语义。
- 找主档、恢复、导出、账本的全部写入者。
- 桥依赖可注入，测试延迟和失败。
- 主进程顺序队列，不掩盖失败。
- 最新提交失败则阻止“当前备份成功”。

不做：存档字段大改、铁人经济变化、全量重写存储。

交付：事务测试、核心测试、类型检查、构建、隔离文件系统压力测试及准确失败反馈。

### 10.3 批次 B：网页来源冲突

**目标：C02。依赖批次 A 的写入顺序概念，但不必等待所有平台同代码实现。**

- 权限、读档、冲突处理、写入启用分别建模。
- 重连期间暂停文件自动写。
- 比较文件、浏览器与内存，显示明确选择。
- 多标签页采取单写者或冲突检测政策。
- 真实浏览器手势及失权测试使用隔离配置。

必须决定：保存时间相同但内容不同怎么办；不同档案身份如何处理；自动选较新还是每次询问。

### 10.4 批次 C：技能加速与训练时间轴

**目标：C03、C04。**

建议同一批解决，因为补剂时刻和训练进度计量互相关联。

步骤：

1. 固化本报告真实 rank5 与临近完成反例。
2. 选定基础工作量单位。
3. 设计到期/完成/续用边界。
4. 新旧 progress 语义迁移或兼容策略。
5. 一次大步/小步/随机分片性质测试。
6. UI 预估与实际推进共用同一基础定义，但用独立锚点验证。

不做：改变全部技能等级系数、稀有剂价格或全离线市场刷新政策。

### 10.5 批次 D：库存数量政策

**目标：C05。**

先产出单位决策，再实现。查全：主控打捞、副船、仓库、卸货、市场出售、回收、容量、归一、统计。

交付判据是资源守恒，不是“页面终于显示大于零”。若新增余数落档，覆盖取消、切船、沉船、卖出与离线。

### 10.6 批次 E：工业产物预留

**目标：C06。**

在工业域建立按产物聚合的预留读数，复用开工与续做；异常交付策略明确，不丢料。图形页、普通工业页、活动栏容量口径一起对齐。

测试重点：并行、取消、不同配方、离线同时完成和循环续做，不只一条线到上限自停。

### 10.7 批次 F：装载生命周期与铁人导出

**目标：C07；同时检查启动、导入、恢复修复链。**

- 统一待装载状态的准备和判定。
- 明确在何时替换内存、何时提交、失败时是否保留旧状态。
- 不在校验未完成时先覆盖旧主档。
- 铁人判定所有入口一致。
- 导出是确定快照，不让导出本身立刻使快照非法。
- 保留移动浏览器用户手势链。

**相邻待验风险：** 当前 `restoreBackup()` 与启动/导入使用的修复链不完全相同。应通过具体旧字段/非法装配样本证明影响，不能先把所有历史修复函数盲目调用三遍。

### 10.8 批次 G：存档保真与检查工具

**目标：C09、C10。**

- 历史窗口常量共用。
- 区分预期拒绝与意外失败。
- 工具非零退出码。
- 全数组与数值投影检查。
- 当代合法状态包含新字段，不只读旧 fixture。

### 10.9 批次 H：UI 可达性

**目标：UI 表五项，先共享提示和对话框，再图形节点。**

- 先统一行为基础。
- 数量输入与关闭按钮有名称。
- 高影响动作有明确后果。
- 保存失败可持久查看/重试。
- 两套布局、两种语言、键盘与触屏均走通。

不把此批变成全面换配色、换字体、换图标或新建第二套组件库。

### 10.10 批次 I：质量门禁

- 增加远端质量作业，部署依赖它。
- 正式工具分环境类型检查。
- hook、异步错误、可访问性 lint 渐进接入。
- 预警有明确基线和到期管理。

### 10.11 批次 J：模块化与性能

最后处理：大型引擎、存档子域、生产政策、CSS 分层、页面懒加载和订阅范围。

每一次提取都要求行为回归；没有性能基线不承诺百分比提升。不要将“文件变小”当作“逻辑风险下降”的唯一验收标准。

## 十三、待产品负责人决定的事项

这些问题应在对应批次实现前决定，不需要在本次审核阶段阻塞报告交付。

| 事项 | 推荐 | 需要说明的影响 |
|---|---|---|
| 加速剂何时续用 | 到期边界或有限尾窗，保证幂等 | 现有“覆盖整个等级”不可用，提前是否浪费需明确 |
| 训练进度计量 | 基础工作量 | 老 `progressMs` 兼容和 UI 展示要处理 |
| 残骸计量 | 固定精度体积或最小单位 | 市场、仓库、货仓、回收、存档一起遵循 |
| 产物已满时完成批次 | 起线预留，异常完成不静默丢弃 | 等待交付/退料等兜底由产品选 |
| 文件重连冲突 | 新来源读取后明确选择 | 自动写暂停、当前进度如何保留 |
| 铁人导出语义 | 导出一个可说明的已提交快照 | 活跃游戏继续推进后快照自然变旧与导出自身变旧要区分 |
| 存档覆盖确认 | 展示替换对象与后果 | 不必强制自动备份，但应避免无感覆盖 |
| 手机旋转模式 | 保留兼容，增加适配能力 | 成本与可读性、触摸目标之间取舍 |
